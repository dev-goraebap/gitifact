# Git 기록 연결 요구사항

## 커밋된 최종 명세 추적
<!-- gitifact-req: R-wpeh3aib32 -->

프로젝트 참여자로서, 반복 편집 중의 초안과 영구 기록을 구분하기 위해 Git에 커밋된 최종 명세를 기준으로 변경 이력을 확인하고 싶다.

### 범위와 제약

작업 중 대화와 반복 수정은 초안 편집이다. 영구 이력은 Git에 커밋된 최종 버전으로 추적한다. 별도 승인 묶음과 note는 사용하지 않는다.

### 수용 조건

1. 조건: 요구사항을 여러 번 편집한 뒤 커밋을 준비합니다.
   기대 동작: 마지막 커밋 대비 최종 차이를 기록합니다. 수정 후 원복됐다면 새 변경 이유를 남기지 않습니다.

설계의 생성·수정·삭제·경로 이동도 Git의 최종 문서로 추적한다. 설계만 바뀐 경우 요구사항 변경으로 만들지 않으며 설계는 문서 전체를 변경 단위로 삼는다.

## 최소 변경 이유 저장
<!-- gitifact-req: R-r6sufs7aez -->

프로젝트 참여자로서, 요구사항과 설계가 바뀐 배경을 이해하기 위해 해당 변경에 연결된 실제 이유를 확인하고 싶다.

### 범위와 제약

기능별 history.jsonl에는 이유와 실제 요구사항 연결을 기록한다. before/after 원문·시각·작성자는 중복 저장하지 않고 Git에서 읽는다.

### 수용 조건

1. 조건: 최종 요구사항 변경에 설명할 이유가 있습니다.
   기대 동작: 실제 이유만 기록합니다. 이유가 없으면 누락을 드러내고 지어내지 않으며 커밋된 이유는 보존합니다.

설계 변경 이유는 해당 기능의 S-ID를 대상으로 구분해 연결한다. 요구사항과 같은 이유이면 함께 연결할 수 있다. 설계 원문·시각·작성자는 이유 파일에 복제하지 않고 Git에서 읽는다. 이유 누락은 경고하며 커밋을 막지 않는다.

## 커밋 권한과 관련 파일 범위
<!-- gitifact-req: R-w4xotddy7p -->

에이전트와 제품을 만드는 사용자로서, 내 작업과 커밋 의도를 지키기 위해 허용한 시점과 범위 안에서 관련 명세·이유·코드·테스트를 커밋하고 싶다.

### 범위와 제약

자동 기록은 자동 커밋 권한이 아니다. 관련 명세·이유·소스·테스트를 함께 커밋하는 것이 기본이며 분리 정책도 따른다.

### 수용 조건

1. 조건: 사용자 요청 또는 명시적 정책으로 커밋합니다.
   기대 동작: 정확한 파일과 실제 R-ID만 연결합니다. 기존 staging·무관한 변경을 보존하고 변경된 계획을 거부합니다. 훅·서명은 유지하고 푸시 권한을 추정하지 않습니다.

## 사실에 근거한 상태와 복구
<!-- gitifact-req: R-droz5whebf -->

프로젝트 참여자로서, 작업 결과를 정확히 판단하고 실패에 대응하기 위해 저장·커밋·구현·검증의 실제 상태와 복구에 필요한 정보를 구분해 확인하고 싶다.

### 범위와 제약

파일 저장·커밋 참조·구현 완료·테스트 통과는 각각 다른 사실이다. 실패한 Git 실행은 실제 HEAD와 index를 확인한다.

### 수용 조건

1. 조건: 커밋 결과가 불확실하거나 검증을 실행하지 않았습니다.
   기대 동작: 완료를 단정하지 않고 복구 상태나 미실행 범위를 알립니다. 커밋을 자동 reset하거나 다른 작업의 잠금을 삭제하지 않습니다.
