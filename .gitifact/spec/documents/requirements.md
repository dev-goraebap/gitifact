# 프로젝트 위키

기능 명세와 별도로 제품 설명과 구현 지침을 관리하고 에이전트가 참고하게 한다.

## 위키 페이지 저장
<!-- gitifact-req: R-y5tidh72gk -->

에이전트와 제품을 만드는 사용자로서, 사람과 에이전트가 같은 목적과 구현 기준을 참고할 수 있도록 제품 소개·구조·규칙을 기능 명세와 구분해 프로젝트 위키 한곳에 저장하고 싶다.

### 범위와 제약

위키는 `.gitifact/wiki/` 아래 Markdown 페이지이며 하위 폴더를 자유롭게 둔다. 폴더·파일 이름은 소문자·숫자·하이픈이고, 루트 페이지만 `README.md`·`ARCHITECTURE.md`처럼 대문자 이름을 쓸 수 있다. `README.md`가 진입 페이지다. 각 페이지는 frontmatter의 `id`(CLI가 발급한 `W-난수`), 최상위 제목, 본문으로 구성한다. ID는 경로·제목과 독립적이다. 이전의 product·guides 폴더와 `P-`·`G-` ID는 읽지도 쓰지도 않으며 정식 버전 전 규약이라 전환 도구를 두지 않는다.

무엇을 어떤 페이지로 나눌지는 CLI 지침의 운영 부분이 안내하고 프로젝트가 재정의할 수 있다. CLI는 형식만 검증한다.

### 수용 조건

1. 조건: 페이지의 파일 이름이나 폴더를 바꿉니다.
   기대 동작: ID가 같으므로 같은 페이지의 이력으로 이어지고 이동으로 기록됩니다. 다른 페이지에 ID를 재사용하지 않습니다.
2. 조건: frontmatter가 없거나 `W-` ID가 아닌 Markdown이 위키에 있습니다.
   기대 동작: CLI와 브라우저는 오류로 알리고 빈 정상 결과로 처리하지 않습니다.
3. 조건: 위키 폴더에 Markdown이 아닌 파일이 있습니다.
   기대 동작: 기록으로 읽지 않고 무시합니다. 문서가 참조할 파일은 에셋 폴더에 둡니다.

## 에이전트의 위키 참조
<!-- gitifact-req: R-hjteu77gki -->

에이전트와 제품을 만드는 사용자로서, 제품의 목적과 기존 구현 기준에 맞는 제안을 받기 위해 에이전트가 요구사항과 설계를 작성하기 전에 위키의 진입 페이지와 관련 페이지를 읽고 반영해 주기를 원한다.

### 범위와 제약

에이전트는 요구사항·설계를 정리하기 전에 `README.md`와 작업 영역에 맞는 페이지를 읽고 따른다. 별도 포함 규칙 메타데이터는 두지 않으며 어떤 페이지가 관련되는지는 폴더·제목으로 판단한다. `init`은 위키를 만들지 않는다.

### 수용 조건

1. 조건: 사용자가 새 기능의 요구사항이나 설계 작성을 요청합니다.
   기대 동작: 에이전트는 진입 페이지에서 대상 사용자·원칙·범위 밖을 확인하고 관련 페이지의 규칙을 설계에 반영합니다. 요청이 범위 밖이나 원칙과 어긋나면 진행 전에 알립니다.
2. 조건: 프로젝트에 위키가 아직 없습니다.
   기대 동작: 에이전트는 없다고 보고 진행하며, 사용자가 원하면 대화에서 파악한 내용으로 진입 페이지를 만들어 저장합니다.
3. 조건: 대화에서 구현 기준이 새로 생기거나 바뀝니다.
   기대 동작: 에이전트는 해당 페이지를 고치자고 제안하고, 동의를 받으면 저장합니다. 새 최상위 폴더나 진입 페이지의 구조 변경은 사용자와 정한 뒤 합니다.

## 페이지 변경 이력
<!-- gitifact-req: R-rtualqkge6 -->

프로젝트 참여자로서, 현재 결정의 배경을 이해하고 이후 변경을 판단하기 위해 위키 페이지의 변경 내용과 이유를 확인하고 싶다.

### 범위와 제약

위키 페이지의 변경은 요구사항과 같은 방식으로 Git에 남는다. 커밋 시점의 변경 전후를 비교하고 변경 이유를 페이지 ID에 연결해 `.gitifact/wiki/history.jsonl` 하나에 쌓는다.

### 수용 조건

1. 조건: 페이지를 수정하거나 옮기고 커밋합니다.
   기대 동작: 활동 페이지에 종류(위키)·추가·변경·이동·제거와 변경 전후 본문, 기록된 이유가 나타납니다. 이유가 없으면 미기록 상태를 안내합니다.
2. 조건: 이미 커밋된 페이지 변경 이유를 고치거나 지우려 합니다.
   기대 동작: 요구사항의 이유와 같이 거부합니다. 과거 원문은 Git 커밋에서 읽습니다.

## 브라우저 위키 열람
<!-- gitifact-req: R-oh4oevufr3 -->

프로젝트 참여자로서, 제품을 이해하고 작업에 필요한 기준을 찾기 위해 브라우저에서 제품 개요를 읽고 위키를 탐색하고 싶다.

### 범위와 제약

브라우저의 첫 메뉴는 제품 개요이며 현재 명세의 요약을 대시보드로 보여 주고, 제품 문서 보기는 위키의 진입 페이지(`README.md`)를 읽기 페이지로 연다. 위키 메뉴("프로젝트 위키")는 저장소 호스팅의 파일 탐색기처럼 왼쪽에 위키 전체의 트리를, 오른쪽에 고른 폴더의 내용 또는 고른 페이지를 보여 준다. 문서 본문의 상대 링크와 이미지는 브라우저 링크 요구사항에 따라 해당 페이지·기능·에셋으로 연결한다.

### 수용 조건

1. 조건: 사용자가 제품 개요 메뉴를 엽니다.
   기대 동작: 요약 타일과 최근 활동이 바로 보이고, 진입 페이지가 있으면 제품 문서 보기로 그 페이지의 읽기 화면에 들어갑니다. 없으면 요약만 보여 주고 위키가 비어 있다고 안내합니다.
2. 조건: 사용자가 프로젝트 위키 메뉴를 엽니다.
   기대 동작: 트리나 폴더 목록에서 폴더를 고르면 그 내용이, 파일을 고르면 그 페이지가 같은 자리에 열립니다. 현재 위치가 경로로 보이고 상위 폴더로 돌아갈 수 있습니다. 페이지를 옮겨도 펼쳐 둔 트리는 그대로입니다. 없는 ID로 들어오면 찾을 수 없음 상태와 목록 링크를 보여 줍니다.

## 에셋 파일 관리
<!-- gitifact-req: R-rir7dn3eez -->

문서를 쓰는 사용자로서, 그림과 첨부 파일을 문서와 함께 저장소에 두기 위해 Markdown이 아닌 파일을 한곳에 모아 관리하고 싶다.

### 범위와 제약

에셋은 `.gitifact/assets/` 아래에 두고 하위 폴더는 자유롭다. ID나 이력은 없고 Git 이력만 남는다. 문서는 상대 경로로 에셋을 참조한다. 권장은 확장자 png·jpg·gif·webp·svg·pdf, 파일당 1MB, 전체 50MB이며 이를 넘어도 저장·커밋은 막지 않는다.

### 수용 조건

1. 조건: 문서와 함께 에셋을 커밋합니다.
   기대 동작: 에셋 경로를 커밋 대상으로 선택할 수 있고, 위키·명세와 같은 커밋에 담깁니다.
2. 조건: 권장 크기·확장자를 넘거나 어떤 문서도 참조하지 않는 에셋이 있습니다.
   기대 동작: `spec working`이 경고로 알리고 저장·커밋은 진행됩니다.
3. 조건: 브라우저가 에셋을 요청합니다.
   기대 동작: 이미지는 본문에 표시하고 그 밖의 파일은 다운로드로 제공합니다. 에셋 폴더 밖의 파일은 제공하지 않습니다.

## 문서 사이의 상대 링크
<!-- gitifact-req: R-dzowfm436d -->

문서를 쓰는 사용자로서, 에디터와 GitHub에서 쓰던 파일 링크 방식을 바꾸지 않고도 브라우저에서 문서 사이를 오가기 위해 저장소 상대 경로 링크를 그대로 쓰고 싶다.

### 범위와 제약

위키 페이지·요구사항·설계 본문의 링크는 그 파일 기준 상대 경로다. CLI는 원문을 바꾸지 않고, 브라우저가 링크를 그릴 때 대상을 해석한다. 대상이 없는 링크는 저장·커밋을 막지 않고 경고한다.

### 수용 조건

1. 조건: 링크 대상이 저장소에 없습니다.
   기대 동작: `spec working`이 문서 경로·링크·해석한 대상을 담은 경고를 냅니다.
2. 조건: 에셋 파일 이름을 바꿉니다.
   기대 동작: 참조하던 링크가 경고로 드러나고, 사용자는 문서를 고쳐 해소합니다.
