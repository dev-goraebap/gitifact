# 에이전트 작업 흐름

## 제품 대화에서 요구사항 식별
<!-- gitifact-req: R-wqv343j4kd -->

에이전트와 제품을 만드는 사용자로서, 별도의 기록 방법을 배우지 않고 개발에 집중하기 위해 대화에서 드러난 요구사항을 에이전트가 정리해 주기를 원한다.

### 범위와 제약

사용자는 방법론이나 기록 명령을 배우지 않고 제품 개발에 집중한다. 에이전트가 대화에서 제품 동작과 제약을 식별해 기록하며 CLI가 다른 앱의 대화를 감시하지 않는다.

### 수용 조건

1. 조건: 사용자가 기능이나 제품 제약을 요청합니다.
   기대 동작: 에이전트는 관련 명세를 정리합니다. 단순 함수 이름 변경·푸시 같은 작업 지시는 제품 요구사항으로 등록하지 않습니다.

새 기능을 정리할 때 에이전트는 요구사항을 바탕으로 구현 설계도 함께 작성한다. 기존 문서를 읽고 필요한 부분을 갱신하며 사용자가 요구사항만 요청한 경우는 따른다.

## 필요한 질문과 점진적 정리
<!-- gitifact-req: R-7seqwcdwlq -->

에이전트와 제품을 만드는 사용자로서, 개발 흐름을 이어 가면서 의도를 정확히 전달하기 위해 필요한 질문에만 답하고 작업하는 영역부터 요구사항을 구체화하고 싶다.

### 범위와 제약

초기 대화에서 대상 사용자·목적·핵심 흐름·실패 조건을 파악한다. 이미 설명한 내용을 반복 질문하거나 기록 승인 절차를 강제하지 않는다.

### 수용 조건

1. 조건: 제품 의미가 모호합니다.
   기대 동작: 결정에 필요한 질문을 하고 독립적인 작업은 진행합니다. 일반 유지보수에서는 변경하는 영역부터 정리합니다.

## 요청에 따른 기존 기능 도출
<!-- gitifact-req: R-dbet7z7kpa -->

기존 프로젝트의 유지보수자로서, 앞으로의 변경을 판단할 기준을 마련하기 위해 이미 있는 코드와 자료에서 요구사항을 도출하고 확인하고 싶다.

### 범위와 제약

코드·테스트·문서·Git·대화에서 기존 요구사항을 도출할 수 있다. 특정 문서 폴더나 DDD 구조는 필수가 아니다.

### 수용 조건

1. 조건: 사용자가 기존 기능 정리를 요청합니다.
   기대 동작: 관측 동작과 사용자 의도를 구분하고 불확실한 내용은 질문합니다. 조사·미조사 범위를 알리며 승인이나 구현 완료를 소급하지 않습니다.

## 작업 중 임시 입력 파일의 위치와 정리
<!-- gitifact-req: R-jzujq3ruxn -->

에이전트와 제품을 만드는 사용자로서, 에이전트가 남긴 파일 중 무엇을 지워도 되는지 직접 가려내지 않기 위해 명세 저장·커밋에 쓴 입력 파일이 프로젝트에 쌓이지 않고 저절로 정리되기를 원한다.

### 범위와 제약

입력 파일의 위치는 CLI가 정해 명세 조회 결과로 알려 준다. 기본은 프로젝트 밖의 운영체제 임시 폴더이고, 그곳에 쓸 수 없는 환경에서는 Git이 무시하는 `.gitifact/tmp/`를 쓴다. CLI는 자신이 알려 준 폴더 안의 파일만 지운다. 빌드·테스트 로그처럼 gitifact 명령과 무관한 에이전트 산출물은 범위에 넣지 않는다.

### 수용 조건

1. 조건: 에이전트가 명세를 조회합니다.
   기대 동작: 결과에 저장·커밋 입력 파일 경로가 포함되고 그 폴더가 준비됩니다.
2. 조건: 운영체제 임시 폴더에 쓸 수 없는 환경입니다.
   기대 동작: `.gitifact/tmp/`를 경로로 알려 주며 Git 상태에 새 파일이 나타나지 않습니다.
3. 조건: 알려 준 경로의 입력으로 저장이나 커밋이 성공합니다.
   기대 동작: CLI가 입력 파일을 지우고 결과에 삭제 여부를 표시합니다.
4. 조건: 저장·커밋이 실패했거나 dry-run이거나 결과가 불확실한 커밋입니다.
   기대 동작: 입력 파일을 남겨 원인을 고친 뒤 같은 입력으로 다시 실행할 수 있게 합니다.
5. 조건: 입력 파일이 알려 준 폴더 밖에 있습니다.
   기대 동작: 명령이 성공해도 그 파일을 지우지 않습니다.
6. 조건: 알려 준 폴더에 7일 넘게 지난 파일이 있습니다.
   기대 동작: 다음 조회 때 그 파일을 정리합니다.
7. 조건: 에이전트에게 명세의 일부만 필요합니다.
   기대 동작: stamp만, 한 기능만, ID·제목 목록만 조회할 수 있습니다. 저장·커밋 입력은 표준 입력으로도 넘길 수 있습니다.

## 기록을 보여 달라는 요청에 브라우저 열기
<!-- gitifact-req: R-7fev4w3qb3 -->

개발 도구에 익숙하지 않은 사용자로서, 요구사항과 프로젝트 현황을 읽기 쉬운 화면으로 확인하기 위해 보여 달라고 말하면 에이전트가 브라우저 주소를 알려 주기를 원한다.

### 범위와 제약

지침 블록과 작업 흐름 문서가 이 요청을 `browser` 명령과 연결한다. 명령은 URL을 출력한 뒤 서버로 계속 실행되므로 에이전트는 백그라운드로 실행한다. 기본 브라우저를 자동으로 여는 기능은 포함하지 않는다. CLI는 에이전트가 지침을 따르는지 검증하지 않는다.

### 수용 조건

1. 조건: 사용자가 요구사항·프로젝트 현황·변경 이력·패치노트를 보여 달라고 합니다.
   기대 동작: 에이전트는 `browser`를 백그라운드로 실행하고 출력된 URL을 알려 줍니다. 명세 JSON을 읽어 채팅에 요약하는 것으로 대신하지 않습니다.
2. 조건: 같은 대화에서 이미 띄운 서버가 실행 중입니다.
   기대 동작: 새로 띄우지 않고 그 URL을 다시 알려 줍니다.

## 프로젝트별 운영 지침 재정의
<!-- gitifact-req: R-uywsfp34va -->

자기 방식으로 위키와 명세를 운영하려는 사용자로서, gitifact의 저장 형식은 그대로 두면서 무엇을 어떻게 쓸지는 우리 팀 기준으로 바꾸기 위해 CLI 지침의 운영 부분을 프로젝트 안에서 대체하고 싶다.

### 범위와 제약

`gitifact docs <topic>`은 CLI가 정한 형식 부분 뒤에 운영 지침을 붙여 출력한다. `.gitifact/overrides/<topic>.md`가 있으면 내장 운영 지침 대신 그 파일이 실린다. 형식 부분과 `spec save`의 검증은 재정의와 무관하다. 기본 상태에는 재정의 파일이 없고 템플릿을 미리 만들지 않는다. CLI는 재정의 파일의 내용을 판정하지 않는다.

### 수용 조건

1. 조건: 사용자가 `gitifact docs <topic> --eject`를 실행합니다.
   기대 동작: 내장 운영 지침이 `.gitifact/overrides/<topic>.md`로 복사되고 첫 줄에 이 파일의 역할이 적힙니다. 이미 있으면 덮어쓰지 않습니다. 초기화되지 않은 위치에서는 거부합니다.
2. 조건: 재정의 파일을 고친 뒤 `gitifact docs <topic>`을 실행합니다.
   기대 동작: 형식 부분 뒤에 고친 내용이 그대로 실립니다. `spec working`의 `overrides`에 그 topic이 나타납니다.
3. 조건: 재정의 파일을 지우거나 비웁니다.
   기대 동작: 내장 지침으로 돌아갑니다. 비어 있는 파일은 `EMPTY_OVERRIDE` 경고로 알립니다.
