# 에이전트 작업 흐름 설계

## 개요

사용자는 평소처럼 에이전트와 제품을 만든다. AGENTS.md 등의 GITIFACT 블록과 `gitifact docs`가 대화의 요구사항을 정리하고 CLI로 저장하는 절차를 안내한다. 별도 대화 수집 서버나 에디터 감시 기능은 두지 않는다.

## 구조와 책임
<!-- gitifact-ref: R-wqv343j4kd -->

- 에이전트는 자연어와 프로젝트 지침을 해석하고 제품 요구사항과 단순 작업 지시를 구분한다.
- 지침 블록은 시작 시 확인할 환경과 요청 분류·규칙의 요약을, `gitifact docs`의 주제별 문서는 명세 작성과 커밋 시점의 대조 절차를 제공한다.
- CLI는 ID 발급, 형식 검증, 파일 저장과 Git 연결을 수행한다. 사용자 의도나 구현의 적합성을 자동 판정하지 않는다.
- requirements.md에는 원하는 동작을, design.md에는 구현 구조와 처리 방식을 정리한다. 이력은 Git에 커밋된 최종 내용을 기준으로 한다.

## 처리 흐름
<!-- gitifact-ref: R-7seqwcdwlq -->

1. 현재 저장소·브랜치·Git 상태, 적용되는 프로젝트 지침, 지정 CLI와 기록 형식을 확인한다.
2. spec working과 관련 원문을 읽는다. 새 프로젝트는 대상 사용자·목적·핵심 흐름·실패 조건을 대화로 파악한다.
3. 관련 요구사항을 기존 기능에 추가하거나 새 기능으로 묶는다. 새 기능에는 구현 방향을 담은 설계를 함께 작성하되 요구사항만 요청받으면 따른다.
4. working의 stamp로 spec save를 실행한다. 신규 ID를 받은 뒤 필요한 설계 참조를 보완한다.
5. 구현하면서 영향받는 명세를 갱신하고, 커밋 요청을 받으면 최종 diff와 검증 결과를 대조해 spec commit으로 연결한다.

### 기존 프로젝트 도출
<!-- gitifact-ref: R-dbet7z7kpa -->

일반 유지보수에서는 변경 영역부터 기록한다. 사용자가 기존 기능 정리를 요청하면 코드·테스트·문서·Git·대화를 조사하고 응집된 기능별로 정리한다. 조사한 구현과 사용자 의도를 구분하며, 미조사 영역을 완료로 표시하지 않는다. 특정 docs 폴더나 DDD 구조를 요구하지 않는다.

## 오류 처리와 검증

제품 의미가 모호하면 필요한 질문을 하고 독립적으로 가능한 작업은 계속한다. CLI 오류나 누락 참조 경고는 원문을 확인해 해결한다. 저장에 실패했다고 형식 검증을 우회하거나 기존 기록을 삭제하지 않는다. CLI 테스트는 파일과 커밋 동작을 검증하며, 모든 에이전트가 자연어 지침을 동일하게 따르는 것까지 보장하지 않는다.

## 사용자 스토리 작성과 배포
<!-- gitifact-ref: R-obomewrs7e -->

`gitifact docs spec`의 작성 규칙과 Markdown·save 예시가 사용자 역할·목표·이유를 담은 스토리를 안내한다. 수용 조건은 조건·기대 동작 형식을 유지한다. 새 요구사항과 요청받은 개정 범위에 적용하며 기존 ID·확정 제약을 보존하고 모르는 동기는 만들지 않는다. 별도 제약은 범위와 제약 절에, 내부 구현 방식은 설계에 둔다.

CLI 패키지가 지침 Markdown을 포함하고 init이 쓰는 블록과 docs 명령으로 사용자 프로젝트에 전달한다. 우리 저장소의 AGENTS.md나 명세를 사용자에게 배포하는 방식에 의존하지 않는다. 패키지 설치·블록 갱신과 사용자 문단 보존 검사는 전달 경로를 검증하며, 독립 에이전트의 실제 작성 행동은 별도 검증 대상이다. 특정 문형을 CLI 파서로 강제하지 않는다.

## 작업 중 임시 입력 파일
<!-- gitifact-ref: R-jzujq3ruxn -->

원칙은 파일 생성을 없애는 것이 아니라, 생겨도 한곳에 모이고 저절로 사라지게 하는 것이다. 새 명령을 만들지 않고 에이전트가 이미 실행하는 흐름에 싣는다.

- `spec working`과 `spec changes`의 응답에 `inputs.save`·`inputs.commit` 경로를 싣는다. 에이전트는 저장 전에 stamp를 얻으려고 working을 반드시 실행하므로 경로를 따로 물어볼 필요가 없다. spec 계약의 version은 올리지 않는 필드 추가다.
- 경로는 `apps/cli/src/adapters/filesystem/agent-inputs.ts`가 정한다. 기본은 `os.tmpdir()/gitifact/<저장소 실제 경로 SHA-256 앞 16자>`다. 폴더를 만들고 시험 파일 쓰기에 실패하면 `.gitifact/tmp/`를 쓰고, 그 안에 `*` 한 줄짜리 `.gitignore`를 만든다. 폴더가 자기 자신까지 무시하므로 Git 상태와 커밋 대상에 나타나지 않는다. 두 곳 모두 실패하면 inputs를 생략하고 조회는 계속한다.
- save가 성공하거나 commit의 outcome이 `committed`이면 입력 파일이 위 두 폴더 중 하나의 바로 아래 일반 파일일 때만 지우고 `inputRemoved`를 싣는다. 실패·dry-run·불확실한 커밋은 파일을 남긴다. 삭제 실패는 명령 결과를 바꾸지 않는다.
- working·changes 실행 때 선택된 폴더에서 수정 시각이 7일 지난 파일을 지운다. 하위 폴더와 `.gitignore`는 건드리지 않는다.
- `--file -`는 표준 입력을 같은 1 MiB 한도로 읽는다. working의 `--stamp`는 stamp와 inputs만, `--feature <폴더>`는 한 기능의 명세만(제품·지침 제외, 없는 기능은 오류), `--ids`는 본문 없이 ID·제목·경로만 낸다.
- 지침 블록·workflow·spec·commit 문서는 입력을 inputs 경로에 쓰고 조회 결과와 docs 출력을 파일로 보관하지 않도록 안내한다. 여러 줄 한국어 본문은 Windows 셸 인자에서 깨지기 쉬워 파일 생성을 0으로 만들지는 않는다.

테스트는 fixture의 TEMP·TMP·TMPDIR을 임시 저장소 안으로 돌려 실제 사용자 임시 폴더를 쓰지 않는다. 쓸 수 없는 임시 폴더는 이 변수를 일반 파일로 가리켜 흉내 내고, 기간 정리는 폴더와 시계를 주입해 시험한다.

## 기록 보기 요청
<!-- gitifact-ref: R-7fev4w3qb3 -->

블록 규칙과 workflow 문서에 "요구사항·프로젝트 현황·변경 이력·패치노트를 보여 달라"는 요청을 `browser` 실행과 연결하는 문장을 둔다. 명령 목록의 한 줄만으로는 에이전트가 이 말을 명령과 연결하지 못했다. `browser`는 URL을 출력한 뒤 종료하지 않으므로 백그라운드 실행을 명시한다. 이미 띄운 서버가 있으면 URL을 다시 알린다. 기본 브라우저를 자동으로 여는 `--open`은 논의만 하고 범위에서 뺐다.

## 주요 설계 결정

진입 지침은 블록 하나로 유지하고 상세는 주제별 docs로 나눈다. 사용자가 기록 방법론이나 여러 스킬의 호출 순서를 배울 필요를 줄이기 위해서다. 모든 채팅을 요구사항으로 저장하지 않고 유지할 제품 동작과 제약만 정리한다. 초안 수정마다 승인·note·별도 사건을 만들지 않으며 자동 기록을 커밋 권한으로 해석하지 않는다.

임시 입력 파일에서 기각한 대안은 다음과 같다.

| 대안 | 기각 이유 |
| :--- | :--- |
| 경로·정리 전용 `gitifact tmp`·`tmp clean` 명령 | 에이전트가 먼저 실행해야 한다는 것을 기억해야만 쓰인다. 기억하지 못하면 지금과 같아진다. 경로는 어차피 실행하는 working에 싣고 정리는 자동으로 한다. |
| 외부 경로를 쓰고 작업 후 지우라고 지침에만 적기 | 삭제가 에이전트의 성실함에 달린다. 샌드박스가 작업 폴더 밖 쓰기를 막으면 다시 프로젝트 안에 쓰고, Windows의 `~`·공백 경로 해석 문제도 있다. |
| 추적되는 `.gitifact/.gitignore`에 `/tmp/` 등록 | 대체 경로가 작업 도중 처음 생길 때 새 미추적 파일이 diff에 끼고, 팀에 적용하려면 커밋이 필요하다. CLI가 엄격히 검사하는 폴더에 예외도 늘어난다. |
| 작업 단위로 임시 파일을 나누고 실행 중 작업을 보호 | CLI에는 작업 개념이 없어 상태 파일과 잠금이 또 생긴다. 성공 시 삭제와 기간 정리로 충분하다. |

## 문서 문체 지침
<!-- gitifact-ref: R-wkp2oca6xx -->

문체는 `writing.md` 한 파일이며 `docs writing`으로만 읽는다. spec·design·wiki 문서는 "문체는 `gitifact docs writing`을 따른다" 한 줄로 가리키고 규칙을 복사하지 않는다. 블록의 규칙 목록에도 같은 한 줄을 둔다.

문체를 세 문서에 나눠 적는 안은 같은 규칙이 세 벌이 되어 이후 수정 때 어긋나므로 기각했다. 위키 형식 문서(`wiki.md`) 안의 한 절로 두는 안은 요구사항만 쓰는 세션이 위키 문서를 읽어야 전문을 보게 되고, 위키 형식 문서가 전 문서의 문체까지 안게 되어 기각했다. 기본 위키 방침(`wiki.default.md`)에 두는 안은 프로젝트가 고칠 수 있다는 장점이 있으나, README가 이미 있는 기존 프로젝트에는 영영 닿지 않고 운영 방침은 wiki topic 출력에만 실려 요구사항·설계 작성에 닿지 않으므로 기각했다.

CLI는 문체를 검사하지 않는다. 사용자에게 보이는 문구와 인용·코드는 문체 교정 대상이 아니므로 지침 본문에 그 예외를 적는다.

## 위키 운영 방침
<!-- gitifact-ref: R-uywsfp34va -->

지침 topic은 workflow·spec·design·wiki·writing·commit이며 각각 `<topic>.md` 하나로 번들된다. `wiki.default.md`는 기본 위키 방침으로, README가 없을 때 싣는 내용이자 `init`이 README를 만드는 템플릿이다. `docs.ts`의 `renderDoc`은 wiki topic에서만 프로젝트 루트(`.gitifact/config.json`이 있는 가장 가까운 상위 폴더)의 README를 읽어 frontmatter와 제목을 떼고, 코드 블록 밖의 제목을 한 단계 낮춰 "운영 방침" 제목 아래에 붙인다. 1MiB를 넘거나 비어 있으면 기본 방침을 쓰고 제목에 기본값임을 밝힌다. `init`은 새 설정을 만든 뒤 `.gitifact/wiki/`가 없을 때만 README를 `wx`로 쓴다. 블록은 "요구사항·설계·코드를 바꾸기 전에 `docs wiki`를 확인한다"와 "위키 운영 방식을 바꾸려면 README를 `spec save`로 고친다"를 안내한다.

처음에는 모든 topic을 형식/운영 두 파일로 나누고 `.gitifact/overrides/<topic>.md`로 대체하게 했으나(`--eject`), 프로젝트마다 달라야 하는 것은 위키 방식뿐이어서 사용자 결정으로 README 방식으로 바꿨다(2026-09-18). README를 일반 페이지로 두고 에이전트가 직접 읽게 하는 안은 읽기를 빠뜨릴 수 있고 README가 없을 때의 기본이 없어 기각했다. 옛 `.gitifact/overrides/` 파일은 삭제로만 커밋할 수 있다.
