# 에이전트 작업 흐름 설계

## 개요

사용자는 평소처럼 에이전트와 제품을 만든다. gitifact-workflow 스킬이 대화의 요구사항을 정리하고 CLI로 저장하는 절차를 안내한다. 별도 대화 수집 서버나 에디터 감시 기능은 두지 않는다.

## 구조와 책임
<!-- gitifact-ref: R-wqv343j4kd -->

- 에이전트는 자연어와 프로젝트 지침을 해석하고 제품 요구사항과 단순 작업 지시를 구분한다.
- 스킬은 시작 시 확인할 환경, 요청 분류, 명세 작성, 커밋 시점의 대조 절차를 제공한다.
- CLI는 ID 발급, 형식 검증, 파일 저장과 Git 연결을 수행한다. 사용자 의도나 구현의 적합성을 자동 판정하지 않는다.
- requirements.md에는 원하는 동작을, design.md에는 구현 구조와 처리 방식을 정리한다. 이력은 Git에 커밋된 최종 내용을 기준으로 한다.

## 처리 흐름
<!-- gitifact-ref: R-7seqwcdwlq -->

1. 현재 저장소·브랜치·Git 상태, 적용되는 프로젝트 지침, 지정 CLI와 기록 형식을 확인한다.
2. spec working과 관련 원문을 읽는다. 새 프로젝트는 대상 사용자·목적·핵심 흐름·실패 조건을 대화로 파악한다.
3. 관련 요구사항을 기존 기능에 추가하거나 새 기능으로 묶는다. 새 기능에는 구현 방향을 담은 설계를 함께 작성하되 요구사항만 요청받으면 따른다.
4. working의 stamp로 spec save를 실행한다. 신규 ID를 받은 뒤 필요한 설계 참조를 보완한다.
5. 구현하면서 영향받는 명세를 갱신하고, 커밋 요청을 받으면 최종 diff와 검증 결과를 대조해 spec commit으로 연결한다.

### 기존 프로젝트 도출
<!-- gitifact-ref: R-dbet7z7kpa -->

일반 유지보수에서는 변경 영역부터 기록한다. 사용자가 기존 기능 정리를 요청하면 코드·테스트·문서·Git·대화를 조사하고 응집된 기능별로 정리한다. 조사한 구현과 사용자 의도를 구분하며, 미조사 영역을 완료로 표시하지 않는다. 특정 docs 폴더나 DDD 구조를 요구하지 않는다.

## 오류 처리와 검증

제품 의미가 모호하면 필요한 질문을 하고 독립적으로 가능한 작업은 계속한다. CLI 오류나 누락 참조 경고는 원문을 확인해 해결한다. 저장에 실패했다고 형식 검증을 우회하거나 기존 기록을 삭제하지 않는다. CLI 테스트는 파일과 커밋 동작을 검증하며, 모든 에이전트가 자연어 지침을 동일하게 따르는 것까지 보장하지 않는다.

## 주요 설계 결정

진입 스킬은 하나로 유지한다. 사용자가 기록 방법론이나 여러 스킬의 호출 순서를 배울 필요를 줄이기 위해서다. 모든 채팅을 요구사항으로 저장하지 않고 유지할 제품 동작과 제약만 정리한다. 초안 수정마다 승인·note·별도 사건을 만들지 않으며 자동 기록을 커밋 권한으로 해석하지 않는다.
