기존 프로젝트의 유지보수자로서, 앞으로의 변경을 판단할 기준을 마련하기 위해 이미 있는 코드와 자료에서 요구사항을 도출하고 확인하고 싶다.

### 범위와 제약

- 코드·테스트·문서·Git·대화에서 기존 요구사항을 도출할 수 있다.
- 특정 문서 폴더나 DDD 구조는 필수가 아니다.
- 도출은 사용자가 요청할 때만 한다. 승인이나 구현 완료를 소급하지 않는다.

### 기본 흐름

1. 사용자가 기존 기능 정리를 요청한다.
2. 에이전트가 코드·테스트·문서·Git 이력을 조사한다.
3. 에이전트가 관측한 동작과 사용자 의도를 구분해 요구사항 초안을 만든다.
4. 에이전트가 조사한 범위와 조사하지 않은 범위를 알리고 초안을 확인받는다.
5. 사용자가 확인한 내용을 요구사항으로 저장한다.

### 대체 흐름

- **A1. 의도가 불확실한 동작** (3단계에서)
  1. 에이전트가 그 동작이 의도인지 질문한다.
  2. 답을 받기 전에는 요구사항으로 확정하지 않는다.
- **A2. 사용자가 초안 일부를 고침** (4단계에서)
  1. 에이전트가 고친 내용을 반영하고 다시 확인받는다.

### 수용 조건

1. 경로: 기본 흐름
   조건: 사용자가 기존 기능 정리를 요청합니다.
   기대 동작: 관측 동작과 사용자 의도를 구분하고, 조사·미조사 범위를 알리며, 승인이나 구현 완료를 소급하지 않습니다.
2. 경로: 기본 흐름, A1
   조건: 코드에서 의도인지 알 수 없는 동작을 발견합니다.
   기대 동작: 질문하고, 답을 받기 전에는 요구사항으로 확정하지 않습니다.
3. 경로: 기본 흐름
   조건: 프로젝트에 문서 폴더나 DDD 구조가 없습니다.
   기대 동작: 코드와 Git 이력만으로 도출을 진행합니다.
