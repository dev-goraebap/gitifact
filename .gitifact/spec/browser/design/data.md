## 커밋별 변경 계산

변경은 커밋마다 바뀐 파일만 읽어 계산한다(history/commit-changes.ts). `git log --stdin --no-walk --raw` 한 번이 커밋 100개가 바꾼 파일·blob을 알려 주고, `git cat-file --batch` 한 번이 그 커밋들의 양쪽(커밋과 첫 부모)에서 바뀐 기능 폴더의 requirements.md·design.md·history.jsonl 전부와 바뀐 위키 페이지·위키 history.jsonl만 `<커밋>:<경로>`로 읽는다. 이 부분 저장소를 비교한 결과는 저장소 전체를 비교한 결과와 같다. 새 이유는 그 커밋에서 바뀐 기록만 가리킬 수 있고, 바뀐 기록은 모두 바뀐 파일 안에 있기 때문이다. 기능 폴더를 통째로 읽는 이유는 요구사항 없이 설계나 이유 파일만 있는 부분 저장소를 파서가 거부하기 때문이다. 부모 쪽에서 레거시 `tryce.json`이 지워지면 부모를 빈 저장소로 보고 boundary를 켠다. 커밋 쪽에 레거시 파일이 있거나 부분 읽기가 실패하면 그 커밋만 예전 방식(양쪽 저장소 전체를 읽어 비교)으로 읽어, 드문 이력도 예전과 같이 읽거나 예전과 같이 실패한다.

예전 방식은 커밋마다 저장소 전체를 두 번 읽어 파싱했다. Windows에서 git 프로세스는 하는 일과 무관하게 한 번에 약 80ms라 페이지 하나가 git 37~39회였고 저장소가 클수록 느려졌다. 체크아웃의 작성자 집계는 기능마다·위키 페이지마다 `git log`를 띄우던 것(기능 22·페이지 63이면 85회)을, 저장소를 건드린 커밋을 `--name-only`로 한 번 거는 것으로 바꿨다. 기능별 상한 2000커밋은 유지하며, 병합 커밋은 파일 목록이 없어 작성자 집계에 들지 않는다. 두 실제 저장소(safety-solution-webapp, 이 저장소)의 전체 이력에서 기능별 작성자·최근 커밋과 페이지별 최근 커밋이 예전 방식과 모두 같았다. 체크아웃 읽기 안의 여러 읽기는 나란히 돌리되 실패는 모두 끝난 뒤 알린다. 먼저 실패를 돌려주면 요청이 끝난 뒤에도 git 프로세스가 프로젝트에서 돌았다.

### 병합과 작성자

first-parent만 읽으면 작업 브랜치의 원본 커밋이 빠지고 병합 담당자가 작성자로 표시된다. 원본 커밋은 자신의 첫 부모와 비교해 작성자·시각·이유를 그대로 유지한다. 두 부모를 가진 병합은 `git show --remerge-diff`로 자동 병합 결과와 실제 커밋의 차이를 읽는다. 전체 파일 문맥에서 변경된 줄이 속한 요구사항 ID 또는 설계·위키 ID를 찾아, 해당 기록의 첫 부모 대비 변경만 병합 활동으로 남긴다. 한 파일 안에서 자동으로 합쳐진 다른 요구사항까지 병합 담당자의 작업으로 표시하지 않는다. 상세 전후 본문은 가상 병합 결과가 아니라 실제 첫 부모와 병합 커밋에서 읽는다.

브랜치에서 가져온 변경 이유는 원본 커밋에 둔다. 병합 이유는 어느 부모에도 없던 이유만 연결하며, 이미 되돌린 작업의 이유가 병합에 들어와도 새 변경으로 검사하지 않는다. Git이 재병합 비교를 지원하지 않는 세 부모 이상 병합은 각 부모와 비교해 모두와 다른 기록을 남긴다. 이 경우 같은 기록 안의 자동 합성과 수동 수정을 구분하지 못한다. 스쿼시·리베이스는 현재 계보의 커밋 작성자를 사용하고 사라진 원본 작성자를 추정하지 않는다.

색인 형식은 2다. 이전 색인의 병합 담당자·중복 변경·검색 행을 다음 서버 조회 때 재생성한다. Git 커밋과 프로젝트 문서는 바꾸지 않는다. Git의 재병합 비교가 실패하면 이력을 조용히 누락하지 않고 조회 오류로 돌려준다. 일반 병합, 같은 요구사항의 자동 합성, 충돌 해결, 병합 중 추가·삭제·이동, 브랜치의 자체 되돌리기, 스쿼시, SHA-256과 색인 재생성을 임시 저장소에서 검사한다.

## 이력 색인

이력은 로컬 SQLite 색인(history/history-index.ts)에서 거르고 세고 찾는다. 커밋은 바뀌지 않으므로 커밋의 변경은 한 번 읽어 영구히 두고, HEAD마다 그 커밋들의 순서(계보)만 더한다. 새 HEAD는 `git rev-list --full-history --date-order HEAD -- <기록 경로>`로 모든 부모를 따라 원본 작업 커밋을 읽고, 색인에 없는 커밋만 100개씩 읽어 넣는다. 같은 커밋은 한 번만 포함하고 자식이 부모보다 먼저 오게 정렬한다. pull 뒤에는 새 커밋만, 브랜치를 오가면 대개 아무것도 읽지 않는다. 계보는 최근 HEAD 네 개까지 둔다. 질의는 계보와 변경을 잇는 SQL이며 git을 부르지 않는다.

파일은 `<git 공용 폴더>/gitifact/index.sqlite`다(2026-09-19 사용자 결정). 작업 폴더에도 `git status`에도 나타나지 않아 사용자에게 새 폴더가 생기지 않고, worktree끼리 함께 쓴다. `.gitifact/data/`(안에 `.gitignore`)에 두는 안은 에디터 트리에 폴더가 보이고 worktree마다 따로 만들며 `init`의 예외가 필요해 기각했다. 서버 메모리에만 두는 안은 서버를 띄울 때마다 전체를 다시 읽어 기각했다. JSON 파일 안은 결국 메모리에 올려 직접 거르고 찾아야 해 기각했다. SQLite는 Node 24에 내장된 `node:sqlite`라 패키지 의존성이 늘지 않는다.

연결은 쓸 때마다 열고 닫는다. 서버가 요청 사이에 파일을 잡지 않아 테스트가 저장소를 지울 수 있고, 같은 저장소의 서버 둘은 SQLite 잠금(`BEGIN IMMEDIATE`, busy_timeout 5초)으로 차례를 지킨다. 같은 커밋을 둘이 쓰면 먼저 쓴 쪽이 남는다(`INSERT OR IGNORE`). 형식 번호(`PRAGMA user_version`)가 다르면 표를 지우고 다시 만들고, 파일이 손상돼 열리지 않으면 지우고 한 번 다시 만든다. 그래도 안 되면(읽기 전용 저장소 등) 그 프로세스 동안 메모리 DB를 쓴다. 표는 commits(커밋별 boundary), changes(변경별 목록 JSON·전후 본문 JSON·필터 열), lineage(HEAD별 커밋 순서), heads, checkouts(검색 행이 어느 체크아웃인지), search(FTS5)다.

요약은 전체 이력의 종류별 건수, 최신 변경 기준 22일 안의 커밋별 날짜·건수, 최신 커밋 셋과 각각의 변경 12개까지다. 21일 막대는 브라우저가 커밋별 건수를 자기 시간대의 날짜로 나눠 센다.

잰 값(safety-solution-webapp: 변경 332건, 이 저장소: 202건). 색인이 없을 때 첫 이력 요청 292ms·538ms, 서버를 다시 띄운 뒤 첫 요청 60ms·99ms, 다음 페이지·필터·요약·단건 9~18ms, 검색 14~35ms. 브라우저에서 활동 목록이 보이기까지 약 0.9~1.0초(대부분 체크아웃 읽기)다. 예전 방식과의 동등성은 실제 CLI로 만든 이력(이동·삭제·위키 이동·설계 삭제·이유)과 두 실제 저장소의 전체 이력에서 순서·종류·이유·전후 본문을 모두 대조해 확인했다.
