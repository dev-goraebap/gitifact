## 커밋별 변경 계산

변경은 커밋마다 바뀐 파일만 읽어 계산한다(`apps/cli/src/adapters/cache/commit-changes.ts`). 문서가 파일 하나씩이므로 커밋의 변경은 그 커밋이 바꾼 문서 파일 안의 문서다. `git log --stdin --no-walk --raw` 한 번이 커밋 100개가 바꾼 기록 파일(기능 `index.md`, `requirements/*.md`, `design/*.md`, 위키 `*.md`, `.gitifact/history.jsonl`)과 blob을 알려 주고, `git cat-file --batch` 한 번이 그 커밋들의 양쪽(커밋과 첫 부모)에서 바뀐 문서 파일과 그 기능 폴더의 `index.md`(기능 S-ID를 알기 위해)만 `<커밋>:<경로>`로 읽는다. 양쪽 문서는 ID로 비교해 경로가 달라지면 이동, 제목·설명·본문·`order`·`requirements`·`sources` 중 하나가 다르면 변경으로 본다. ID를 알려고 함께 읽은 `index.md`는 그 커밋에서 바뀌지 않았으면 변경에 넣지 않는다. 그 커밋에서 파싱되지 않는 파일은 이력 전체를 실패시키지 않고 빠진다.

이유는 커밋이 `.gitifact/history.jsonl`에 더한 줄이다. 한 묶음의 커밋에 대해 `git log -p -U0` 한 번으로 이 파일의 패치를 읽으므로 비용이 파일 크기와 함께 늘지 않는다. 같은 H-ID의 줄을 지우고 다시 쓴 것은 옛 이유를 고친 것이라 새 이유로 보지 않는다. 이유는 `docs`에 그 문서 ID가 있는 변경에 붙는다.

0.8.0 마이그레이션 커밋(`Gitifact-Migration: 0.8.0` 트레일러)이 이력을 나눈다. HEAD에서 닿는 가장 새 마이그레이션 커밋의 조상은 0.7 파서로 읽고(`legacy-changes.ts`, 트리는 아래 "0.7 트리 읽기"), 마이그레이션 커밋 자체는 이력에 보이지 않으며, 그 뒤는 현재 형식으로 읽는다. 마이그레이션이 R-·S-·W- ID를 유지하므로 요구사항의 이력은 전환 전후로 이어진다. 0.7에서 기능마다 파일 하나(S-ID)였던 설계는 D- 문서가 되어 이력이 마이그레이션에서 새로 시작한다. 0.7 쪽은 양쪽 저장소 전체를 읽어 비교한다. 마이그레이션 전 이력은 끝이 있고 캐시에 한 번만 읽히기 때문이다. 0.7 파서가 읽지 못하는 쪽은 빈 저장소로 본다. 마이그레이션 커밋이 생기기 전에 현재 형식으로 읽어 둔 커밋은 그 위에 마이그레이션 커밋이 생기면 다시 읽는다. 0.7 파일 경로(`requirements.md`·`design.md`·폴더별 `history.jsonl`)도 기록 경로에 넣어 두며, 0.7 파서와 함께 1.0.0에서 지운다.

Windows에서 git 프로세스는 하는 일과 무관하게 한 번에 약 80ms다. 커밋마다 저장소 전체를 두 번 읽어 파싱하던 0.7의 첫 구현은 페이지 하나가 git 37~39회였고 저장소가 클수록 느려졌다. 체크아웃의 작성자 집계는 기능마다·위키 페이지마다 `git log`를 띄우던 것(기능 22·페이지 63이면 85회)을, 저장소를 건드린 커밋을 `--name-only`로 한 번 거는 것으로 바꿨다(`server/checkout/checkout-reader.ts`). 기능별 상한 2000커밋은 유지하며, 병합 커밋은 파일 목록이 없어 작성자 집계에 들지 않는다. 마이그레이션 커밋은 문서를 모두 다시 쓰지만 누구의 작업도 아니므로 작성자·최근 커밋 집계에서 뺀다. 두 실제 저장소(safety-solution-webapp, 이 저장소)의 0.7 형식 전체 이력에서 기능별 작성자·최근 커밋과 페이지별 최근 커밋이 예전 방식과 모두 같았다. 체크아웃 읽기 안의 여러 읽기는 나란히 돌리되 실패는 모두 끝난 뒤 알린다. 먼저 실패를 돌려주면 요청이 끝난 뒤에도 git 프로세스가 프로젝트에서 돌았다.

### 병합과 작성자

first-parent만 읽으면 작업 브랜치의 원본 커밋이 빠지고 병합 담당자가 작성자로 표시된다. 원본 커밋은 자신의 첫 부모와 비교해 작성자·시각·이유를 그대로 유지한다. 두 부모를 가진 병합은 `git show --remerge-diff`로 자동 병합 결과와 실제 커밋이 다른 파일을 찾고, 그 파일의 문서만 첫 부모 대비 변경을 병합 활동으로 남긴다. 다른 문서 파일에서 자동으로 합쳐진 변경과, 한 문서 안에서 충돌 없이 자동으로 합쳐진 변경은 병합 담당자의 작업으로 표시하지 않는다. 병합이 손댄 문서는 첫 부모와의 차이 전체를 보이므로 같은 문서 안의 자동 합성과 수동 수정은 구분하지 않는다. 상세 전후 본문은 가상 병합 결과가 아니라 실제 첫 부모와 병합 커밋에서 읽는다.

브랜치에서 가져온 변경 이유는 원본 커밋에 둔다. 병합 이유는 어느 부모에도 없던 이유만 연결하며, 이미 되돌린 작업의 이유가 병합에 들어와도 새 변경으로 검사하지 않는다. Git이 재병합 비교를 지원하지 않는 세 부모 이상 병합은 각 부모와 비교해 모두와 다른 기록을 남긴다. 이 경우 같은 기록 안의 자동 합성과 수동 수정을 구분하지 못한다. 0.7 파서로 읽는 마이그레이션 전 병합도 재병합 비교 없이 같은 방식이라, 한 요구사항 안의 자동 합성이 병합 담당자의 것으로 보일 수 있다. 스쿼시·리베이스는 현재 계보의 커밋 작성자를 사용하고 사라진 원본 작성자를 추정하지 않는다.

Git 커밋과 프로젝트 문서는 바꾸지 않는다. Git의 재병합 비교가 실패하면 이력을 조용히 누락하지 않고 조회 오류로 돌려준다. 일반 병합, 같은 요구사항의 자동 합성, 충돌 해결, 병합 중 추가·삭제·이동, 브랜치의 자체 되돌리기, 스쿼시, 세 부모 병합, 두 브랜치에서 더한 이유 줄의 합치기, SHA-256과 캐시 재생성을 임시 저장소에서 검사한다(`apps/cli/test/merge-history.test.mjs`).

## 캐시와 질의

이력과 작업 폴더 문서는 SQLite 캐시(`apps/cli/src/adapters/cache/`)에서 거르고 세고 찾는다. 브라우저 서버와 CLI의 조회 명령(`docs list`·`search`·`show`·`history` 등)이 같은 파일을 쓴다. 커밋은 바뀌지 않으므로 커밋의 변경은 한 번 읽어 영구히 두고, HEAD마다 그 커밋들의 순서(계보)만 더한다. 새 HEAD는 `git rev-list --full-history --date-order HEAD -- <기록 경로>`로 모든 부모를 따라 원본 작업 커밋을 읽고, 캐시에 없는 커밋만 100개씩 읽어 넣는다. 같은 커밋은 한 번만 포함하고 자식이 부모보다 먼저 오게 정렬한다. pull 뒤에는 새 커밋만, 브랜치를 오가면 대개 아무것도 읽지 않는다. 계보는 최근 HEAD 네 개까지 둔다. 질의는 계보와 변경을 잇는 SQL이며 git을 부르지 않는다.

작업 폴더 문서는 에이전트가 파일을 직접 고치므로, 읽을 때마다 `.gitifact/spec`·`.gitifact/wiki` 아래 파일의 수정 시각·크기를 캐시가 마지막에 본 값과 견주어 달라진 파일만 다시 파싱한다(`documents.ts`). 문서 행에는 프론트매터와 파싱한 문서를, 참조 행에는 설계의 `requirements`·`sources`를 역조회용으로, 검색 행에는 제목·위치·설명·본문을 넣는다. 1MB를 넘는 문서 파일은 읽지 않고 문제로 알리며, 파일 2만 개에서 훑기를 멈춘다.

파일은 작업 폴더의 `.gitifact/cache/index.db`다. CLI가 캐시 폴더 안에 내용이 `*`인 `.gitignore`를 만들어 Git에서 빼며 프로젝트의 루트 `.gitignore`는 건드리지 않는다. `.gitifact` 폴더가 없으면 캐시 폴더를 만들지 않는다. worktree마다 캐시가 따로라 새 worktree에서는 이력을 처음 한 번 다시 읽는다. 0.7 브라우저는 이력 색인을 `<git 공용 폴더>/gitifact/index.sqlite`에 두었으나(2026-09-19 사용자 결정, 결정 0009), 0.8.0에서 CLI와 브라우저가 캐시 하나를 함께 쓰기로 하며 이 위치로 옮겼다. 결정 0009의 위치 서술은 낡았고 대체 결정은 아직 없다. 옛 파일은 CLI가 지우지 않으며 마이그레이션 지침(`guide show migrate`)이 지워도 된다고 안내한다. 서버 메모리에만 두는 안은 서버를 띄울 때마다 전체를 다시 읽어 기각했다. JSON 파일 안은 결국 메모리에 올려 직접 거르고 찾아야 해 기각했다. SQLite는 Node 24에 내장된 `node:sqlite`라 패키지 의존성이 늘지 않는다.

연결은 쓸 때마다 열고 닫는다. 서버가 요청 사이에 파일을 잡지 않아 테스트가 저장소를 지울 수 있다. WAL 모드라 CLI와 서버가 읽기와 쓰기를 나란히 하고, 쓰기는 SQLite 잠금(`BEGIN IMMEDIATE`, busy_timeout 5초)으로 차례를 지킨다. 같은 커밋을 둘이 쓰면 먼저 쓴 쪽이 남는다(`INSERT OR IGNORE`). 형식 번호(`PRAGMA user_version`, 지금 2)가 다르면 표를 지우고 다시 만들고, 파일이 손상돼 열리지 않으면 지우고 한 번 다시 만든다. 그래도 안 되면(읽기 전용 저장소 등) 그 프로세스 동안 메모리 DB를 쓴다. 표는 files(읽은 작업 폴더 파일의 수정 시각·크기·문제), documents(작업 폴더 문서), doc_references(프론트매터의 ID 참조), commits(읽은 커밋과 읽은 방식: 현재 형식·0.7·마이그레이션), changes(변경별 목록 JSON·전후 본문 JSON·필터 열), lineage(HEAD별 커밋 순서), heads, search(FTS5)다.

0.7 커밋은 양쪽 저장소를 통째로 비교하므로 한 건마다 트리 둘이 필요하다. 커밋마다 따로 읽으면 `ls-tree`와 `cat-file`이 커밋당 네 번 뜨고, Windows에서 git 프로세스는 하는 일과 무관하게 약 80ms라 이 저장소에서 트리 하나에 120ms가 들었다(파싱은 2ms). 그래서 `store-reader.readBundles`가 배치의 0.7 커밋과 그 부모의 트리 목록을 8개씩 동시에 받고, 거기 나온 blob 전체를 `cat-file --batch` 한 번으로 읽는다. 이어진 커밋은 대부분 같은 blob을 가리켜 중복이 사라진다. 동시 실행만으로는 거의 줄지 않았다. `ls-tree`는 동시에 돌리면 2.5배 빨라지지만 `cat-file`은 8건 기준 625ms에서 571ms에 그쳤다. 읽지 못한 트리는 빈 저장소로 본다.

요약은 전체 이력의 종류별 건수, 최신 변경 기준 22일 안의 커밋별 날짜·건수, 최신 커밋 셋과 각각의 변경 12개까지다. 21일 막대는 브라우저가 커밋별 건수를 자기 시간대의 날짜로 나눠 센다.

0.7 형식의 `.git` 안 색인에서 잰 값(safety-solution-webapp: 변경 332건, 이 저장소: 202건). 색인이 없을 때 첫 이력 요청 292ms·538ms, 서버를 다시 띄운 뒤 첫 요청 60ms·99ms, 다음 페이지·필터·요약·단건 9~18ms, 검색 14~35ms. 브라우저에서 활동 목록이 보이기까지 약 0.9~1.0초(대부분 체크아웃 읽기)였다. 예전 방식과의 동등성은 실제 CLI로 만든 이력(이동·삭제·위키 이동·설계 삭제·이유)과 두 실제 저장소의 전체 이력에서 순서·종류·이유·전후 본문을 모두 대조해 확인했다. 지금 캐시에서는 이 저장소(커밋 55개 중 42개가 0.7)의 캐시가 빈 상태의 첫 이력 조회가 8.6초였고, 0.7 트리를 배치로 읽게 한 뒤 2.85초다. 커밋 읽기 단계만 보면 7.3초에서 1.4~1.9초로 줄었고, 새 형식 커밋 12개는 원래 185ms였다.
