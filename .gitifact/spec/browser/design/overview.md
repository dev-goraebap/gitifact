## 개요

명세 이력·요구사항·참여자를 연결하는 읽기 전용 브라우저다. React·Astryx로 UI를 구성하고 TanStack Router가 경로·선택·필터를, TanStack Query가 서버 조회 상태를 관리한다. 목록을 대체하는 상세 페이지는 경로 계층(`/features/<S-ID>`, `/contributors/<이메일>`)으로 구분하고, 같은 화면 안의 검색·탭 선택은 URL 검색 인자에 둔다. 브라우저는 파일이나 Git 명령을 직접 실행하지 않는다.

요구사항과 설계는 같은 이력에서 종류를 구분하고 공통 원문을 중복 저장하지 않는다. 이력과 작업 폴더 문서는 CLI와 함께 쓰는 SQLite 캐시 `.gitifact/cache/index.db`에 두며(결정 0011), 작업 폴더 문서는 요청 때마다 바뀐 파일만 다시 읽는다. 집계 차트는 라이브러리 없이 SVG·ProgressBar로 그리고, 문서의 다이어그램만 mermaid를 번들에 담는다(결정 0008). 편집·승인 UI와 작업 파일 표시는 범위 밖이다.

| 파일 | 다루는 것 |
| :--- | :--- |
| data | 커밋별 변경 계산, 병합 커밋의 작성자, 캐시와 질의 |
| interface | 서버 구조와 API 계약, 조회 캐시 |
| ui | 메뉴와 경로, 화면별 구성 |
| document | 문서 본문 렌더링과 문서 링크 해석 |
| search | 검색 창과 서버 검색 |
| errors | 골격 화면과 조회 상태, 검사 범위 |

## 결정

| 결정 | 이유 | 기각한 안 |
| :--- | :--- | :--- |
| 이력은 모든 부모를 따라 읽고, 병합에는 담당자가 손댄 문서만 남긴다(`--remerge-diff`) | first-parent만 읽으면 작업 브랜치의 원본 커밋이 빠지고 병합 담당자가 작성자로 보인다 | first-parent만 읽기 |
| 이력과 문서를 SQLite 캐시에 두고 한 번 읽은 커밋은 다시 읽지 않는다 | 필터·검색·건수를 전체 이력 기준으로 SQL로 답하고, 서버를 다시 띄워도 읽은 커밋을 다시 읽지 않는다 | 서버 메모리에만 두기(띄울 때마다 전체를 다시 읽음), JSON 파일(결국 메모리에 올려 직접 거르고 찾아야 함) |
| git 호출은 묶음 단위로 한다: 커밋 100개씩, 0.7 트리는 배치로, 작성자 집계는 `git log` 한 번 | Windows에서 git 프로세스는 하는 일과 무관하게 한 번에 약 80ms라 호출 수가 곧 시간이다 | 커밋·문서마다 git 호출, 동시 실행만 늘리기(`cat-file`은 8건에서 625→571ms), `git log --raw`로 0.7 트리 잇기(1.0.0에 지울 코드에 복잡도) |
| 로컬 서버에 HTTP 프레임워크를 넣지 않는다 | 느린 원인은 git 프로세스와 파일 읽기이고 라우팅·JSON은 1ms도 걸리지 않는다. 보안 검사는 제품 고유라 어차피 직접 짜야 하고, CLI는 런타임 의존성 없이 파일 하나로 번들된다 | express·Fastify |
| 체크아웃은 통째로 보내 화면이 거르고, 이력은 서버가 전체에 조건을 걸어 50건씩 준다 | 불러온 페이지만 거르면 커밋이 많은 프로젝트에서 필터가 오래된 변경을 찾지 못한다 | 체크아웃과 이력 첫 페이지를 한 응답에 싣고 화면이 거르기 |
| 커밋의 소스 변경 목록은 서버 메모리에만 둔다(200커밋) | 페이지를 열 때 커밋 하나만 읽으면 되고, 캐시 표를 늘리면 형식 번호가 바뀌어 캐시 전체를 다시 만든다 | SQLite 캐시에 저장 |
| 명세 조회의 staleTime은 무한이고 새로고침 버튼으로만 다시 읽는다 | 여러 화면이 한 조회를 함께 써서, 짧으면 화면을 옮길 때마다 불러온 페이지가 전부 다시 요청된다 | 짧은 staleTime(5초) |
| 제품 개요는 최근 커밋의 변경 이유를 본문으로 삼는다 | 제품이 기록하는 것이 변경 이유이고, 요약 타일은 그것을 보이지 않았다 | 기능 지도가 이끄는 개요, 수치 대시보드 다듬기 |
| 작업 중 변경 표시는 명세 Query 캐시와 Git 상태 응답으로만 판단한다 | 셸이 명세 API를 부르면 명세 저장소가 없는 프로젝트의 Git·소개 화면에서 503 오류가 남는다 | 셸에서 명세를 조회 |
| 활동 타임라인은 커밋 하나를 한 항목으로, 변경 이유마다 한 덩어리로 보인다 | 이유가 기록마다 저장되어 기록을 한 줄씩 늘어놓으면 같은 문단이 되풀이된다 | 커밋으로만 묶고 이유를 모아 보이기(어느 이유가 어느 기록의 것인지 잃음) |
| 활동의 상세는 커밋 페이지(`/activity/<커밋>`)다 | 읽을 것이 두 벌의 원문이라 넓은 폭이 필요하고, 소스 변경은 문서가 아니라 커밋에 속한다 | 서랍 유지·넓히기(한 서랍에 계속 쌓임), 목록+상세 2단(타임라인 이유 문단의 폭을 잃음) |
| diff 표를 직접 그린다 | 줄 번호와 양쪽 줄을 행마다 맞추고 지운 쪽·더한 쪽, 접기, 단어 표시가 필요하다 | Astryx CodeBlock(강조 줄이 한 색뿐) |
| diff 보기는 화면 폭이 정한다(1024px 이상 좌우) | 좁은 화면의 좌우 보기는 양쪽이 너무 좁고, 넓은 화면의 통합 보기는 오른쪽을 비운다. 폭마다 알맞은 보기가 하나다 | 통합·좌우 전환 장치 |
| 검색창은 입력을 자기 상태로 들고 URL에는 replace로 반영한다 | 입력을 URL에 직접 묶으면 라우터의 비동기 갱신이 한글 조합 중 이전 값을 되돌려 쓴다 | 입력을 `q`에 직접 묶기 |
| 불러온 활동 페이지를 다른 화면에 다녀와도 남긴다 | 돌아왔을 때 읽던 범위를 지킨다 | 첫 페이지만 남기고 다시 더보기(다시 그리는 시간 차이는 작고 읽던 범위를 잃음) |
| 한 줄 자르기는 CSS로 한다 | Astryx Text의 `maxLines`는 툴팁을 위해 요소마다 크기를 재서 긴 목록에서 레이아웃을 수백 번 강제한다 | Text `maxLines` |
| 기능 목록은 40행까지 기능 단위로 페이지를 나누고 기능당 요구사항 12개까지 보인다 | 한 기능이 페이지에 걸쳐 끊기지 않고, 요구사항이 많은 기능 하나가 페이지를 덮지 않는다 | 행 수로 나누기, 기능 수로 나누기 |
| 기능 목록의 정렬은 화면이 하고 `useTableSortable`은 머리만 맡는다 | 플러그인이 평평한 행 배열을 다시 늘어놓으면 기능과 요구사항 묶음이 흩어진다 | 플러그인 정렬 |
| 기능 상세는 모든 요구사항·설계를 이어 보이고 들어온 절에 빗금을 깐다 | 앞뒤 맥락을 가리지 않는다 | 들어온 요구사항만 보이기, 요구사항 골라 보기 필터(Tokenizer), 설계 파일 하나와 이전·다음 |
| 기능 상세 목차는 1200px 이상에서 본문 오른쪽에 고정하고 좁으면 위에 둔다 | 데스크톱에서 위쪽 목차는 공간을 많이 차지한다 | 왼쪽 목차(앱 메뉴 옆에 한 겹 더), 접는 목차(눌러야 보이고 위치 표시가 없음) |
| 문서 스타일은 Astryx 토큰과 읽기 영역의 CSS로만 맞춘다 | 디자인 체계를 하나로 둔다 | Tailwind 기반 fumadocs 스타일 들여오기 |
| 다이어그램은 번들된 mermaid가 원문을 그 자리에서 그린다 | 오프라인으로 동작하고, 원문이 저장소에서 바로 읽힌다 | CDN 로딩, 그림을 이미지로 미리 굽기 |
| 알림은 렌더링된 인용에서 표지를 떼어 그린다 | 원문을 미리 고치면 Markdown 인스턴스가 쪼개져 제목 id와 목차가 어긋난다 | 원문을 미리 고쳐 넣기 |
| 검색은 서버가 캐시의 검색 행에서 한다 | 지난 변경까지 찾으려면 브라우저가 이력 전체를 내려받아야 한다 | 체크아웃을 브라우저에 두고 찾기 |
| 색 조합은 stone 소스를 extends하고 색 토큰만 명시한다 | 글꼴·모서리·아이콘·컴포넌트 재정의를 물려받고, 채도 높은 강조색을 선택 표시·진행 막대·버튼에만 둔다 | 강조색 하나에서 유도(`color.accent` 시드. stone은 링크·메뉴 글자가 강조 토큰을 써서 색이 화면 전체로 번짐) |

## 미결

- `/api/v1/change`(`changeOptions`)와 이력 쿼리의 `id` 조건은 서버와 계약에 있지만 쓰는 화면이 없다. 지울지는 계약을 정할 때 결정한다.
