## 메뉴와 경로

왼쪽 메뉴는 Astryx SideNav의 resizable 옵션으로 200~400px 사이에서 너비를 조절하고 localStorage에 유지한다. 메뉴 순서는 제품 개요·기능별 요구사항·프로젝트 위키·활동·참여자·Git 상태다. 브라우저는 제품 개요(`/product`)에서 시작한다. `/`는 검색 인자가 없으면 `/product`로, 있으면 같은 인자를 붙여 `/activity`로 리다이렉트한다. 0.5.0 전에는 활동이 `/`였으므로 저장해 둔 활동 링크가 필터와 선택을 잃지 않게 했다. CLI 로컬 서버가 정적 앱과 API를 제공한다. 현재 원문은 작업 폴더에서, 이력의 전후·작성자·시점은 Git에서 읽되 둘 다 로컬 캐시(data 설계의 캐시와 질의 절)를 거친다.

미커밋 내용은 문장 대신 표시로 알린다. 셸은 `useWorkingChanges`로 명세 Query 캐시의 `working`을 읽어 Git 상태 메뉴에 경고 StatusDot을 붙이고, Git 상태 페이지는 같은 값으로 상단 Banner에 "제품 개요·기능별 요구사항·위키 화면은 작업 중인 내용이고 활동은 커밋된 내용"임을 설명한다. 이 훅은 명세 API를 스스로 호출하지 않고, 모든 페이지가 이미 읽는 Git 상태 응답의 `.gitifact/` 아래 변경 경로를 두 번째 출처로 본다. 처음 구현은 셸에서 명세를 조회했으나 gitifact 저장소가 없는 프로젝트의 Git·소개 화면에서 503 오류가 콘솔에 남아 캐시 읽기로 바꿨고, 캐시만으로는 Git 페이지에 바로 들어올 때 표시가 비어 상태 경로를 더했다.

## 활동 타임라인

기능 S-ID, 요구사항 R-ID, 설계 D-ID, 위키 W-ID를 각각 비교해 추가·변경·제거·이동을 표시한다(0.8.0 마이그레이션 전 이력의 설계는 기능 S-ID로 비교한다). 화면 이름은 추가·변경·제거·이동이며 저장 형식의 created·modified·deleted·moved는 바꾸지 않는다. 목록은 왼쪽 세로 선 위에 작성자 아바타가 놓이는 타임라인이며 한 항목이 커밋 하나다. 항목의 머리는 작성자·상대 시각·기록 수와 커밋 해시·커밋 제목이고, 본문은 기록된 이유마다 한 덩어리다. 기록 수는 그 항목이 지금 보이는 기록의 수다. 서버는 커밋별 전체 건수를 주지 않고 페이지는 커밋 중간에서도 끊기므로, 걸친 커밋은 다음 페이지를 불러오면 한 항목으로 합쳐지며 수도 함께 올라간다(이 저장소의 50a421b는 6 → 25). 이유는 한 번만 적고 그 이유로 바뀐 기록을 한 줄씩 아래에 둔다. 이유가 없으면 미기록 상태를 안내한다. 이유는 기록마다 저장되므로 기록을 한 줄씩 늘어놓으면 같은 문단이 되풀이된다. 이 저장소의 이력 209건은 서로 다른 (커밋, 이유) 묶음이 81개뿐이고 한 이유가 최대 26건을 덮는다. 한 커밋이 여러 이유를 기록하는 경우도 34개 커밋 중 24개라, 커밋으로만 묶고 이유를 모아 보이는 안은 어느 이유가 어느 기록의 것인지를 잃어 기각했다. 날짜가 바뀌는 자리에는 날짜 표시를 두고 그 자리에서 세로 선을 끊는다. 제목을 열면 상세 서랍(Astryx Dialog)에서 변경 내용과 이유를 확인한다. 변경 내용은 그때 받아 오며, 받는 동안 본문 자리에 글줄 모양 골격을, 실패하면 그 자리에 오류를 보인다. 한 번 받은 변경은 세션 동안 다시 묻지 않는다. 변경 전·후가 모두 있으면 `ChangeDiff`가 git diff처럼 보인다. 먼저 바뀐 프론트매터 항목을 값이면 `이전 → 이후`로, 목록(`requirements`·`sources`)이면 빠진 항목과 더해진 항목만 보인다. ID로 가리킨 요구사항·문서는 지금의 제목으로 읽는다. 이어서 본문을 원문 줄 단위로 비교해(`shared/lib/diff`, 최장 공통 부분열) 지운 줄은 빨강, 더한 줄은 초록 바탕에 옛·새 줄 번호를 붙인다. 바뀐 줄은 n번째 지운 줄과 n번째 더한 줄을 짝지어 단어 단위로 다시 비교하고 다른 단어를 진한 바탕으로 표시한다. 남는 글자가 4분의 1 미만인 짝은 통째로 바뀐 줄로 두는데, 거의 모든 단어에 표시가 붙으면 읽을 것이 없어서다. 변경에서 3줄보다 먼 무변경 구간은 "바뀌지 않은 N줄 펼치기"로 접는다. 통합 보기가 기본이며 1024px 이상에서는 좌우 보기로 바꿀 수 있고, 고른 보기는 서랍 폭처럼 그 브라우저의 localStorage(`gitifact-diff-view`)에 남는다. 비교 계산은 서랍을 열 때 브라우저가 한다. 추가·제거처럼 한쪽만 있으면 렌더링한 본문 하나만 보여준다. 표는 줄 번호와 양쪽 줄을 행마다 맞추려고 직접 그린다. Astryx CodeBlock은 강조 줄이 한 색뿐이고 지운 쪽·더한 쪽, 접기, 단어 표시가 없다. 이전의 겹침 비교 슬라이더(변경 후 위에 변경 전을 겹치고 손잡이로 드러냄)는 긴 문서에서 무엇이 바뀌었는지 찾으려면 손잡이를 끌며 두 본문을 번갈아 읽어야 해서 01 7장의 합의대로 바꿨다. 선택은 URL의 selected에 저장한다. 이전의 같은 명세 연결 그래프는 읽기에 방해가 되어 2026-09-15에 제거했다.

본문은 1024px 중앙 컬럼이며 스크롤은 콘텐츠 카드가 담당한다. 제목은 스크롤로 사라지고 필터 줄은 상단 바 아래에 고정된다. 종류·기능·작성자·검색 필터는 서버가 전체 이력에 적용하고, 목록 아래에 "전체 N건 중 M건"을 알린다. 조건을 바꾸는 동안에는 이전 결과를 유지한다. 검색창(`SearchFilter`)은 입력 중인 글자를 자기 상태로 들고 URL의 `q`에는 replace로 따라 반영한다. 입력을 URL에 직접 묶었을 때는 라우터의 비동기 갱신이 한글 조합 도중 이전 값을 되돌려 써서 "검색"이 "ㄱ거검검ㅅ새색색"처럼 쌓였다. 필드가 보낸 값이 늦게 돌아오는 것은 무시하고, 필드가 보내지 않은 값(뒤로가기, `q`가 담긴 링크)이 오면 그 값으로 바꾼다. 같은 검색창을 활동·기능별 요구사항·참여자가 함께 쓴다. 더보기는 기존 목록에 다음 50건을 추가하며 실패 시 재시도할 수 있다. 불러온 페이지는 다른 화면에 다녀와도 남긴다. 커밋 항목은 memo 컴포넌트이며 이벤트·기능 객체의 동일성으로 비교하므로 더보기 때 새 커밋만 그린다(기록 243건까지 한 번에 80~114ms로 일정하고, 다른 화면에 다녀와 그리는 데 260~375ms). 한 줄 자르기는 CSS로 한다. Astryx Text의 maxLines는 잘렸을 때 툴팁을 띄우려고 요소마다 크기를 재는데, 줄마다 두 번 쓰여 334줄이면 레이아웃을 668번 강제했다. 다른 화면에 다녀올 때 2,899ms가 걸렸고 그중 2.7초가 이 측정이었으며, 지금은 약 0.4~0.5초다. 첫 페이지만 남기고 다시 더보기를 시키는 안은 돌아올 때 약 230ms로 차이가 작은 반면 읽던 범위를 잃어 기각했다. 서랍은 목록이 아니라 키로 변경을 받아 오므로 목록에 없는 변경의 링크도 연다. 목록에 있는 항목이면 받는 동안 제목을 먼저 보인다.

## 요구사항 목록과 기능 상세

기능별 요구사항 메뉴(`/features`)의 목록은 활동 페이지와 같은 1024px 중앙 컬럼의 Astryx Table이며 한 행에 제목·설계 없음 표시·한 줄 설명, 요구사항 수와 가장 많은 기능 대비 ProgressBar, AvatarGroup 참여자(3명 초과는 +N), 상대 시각을 둔다. 그 아래에 그 기능의 요구사항이 번호·제목·설계로 가는 링크만 담은 낮은 행으로 이어진다(`data-row`로 구분). 기능 8개에 요구사항이 39개인데 설명은 하나뿐이라 목록이 제목·개수·아바타만 보이고 정작 내용인 요구사항은 한 줄도 없었다. 행은 `model/feature-rows.ts`가 기능·요구사항·나머지 세 종류로 만들고, 페이지는 40행을 넘기 전까지 기능을 담되 한 기능을 쪼개지 않는다. 행으로 나누면 한 기능이 페이지에 걸쳐 끊기고, 기능 수로 나누면 도입 커밋처럼 요구사항 200개짜리 기능 하나가 페이지를 덮는다. 그래서 한 기능은 요구사항 12개까지 보인 뒤 "요구사항 N개 더"로 상세에 잇는다. 페이지는 `page` 검색 인자이며 숫자라 주소가 `?page=2`로 읽힌다. 페이지 매김은 카드 바닥에 붙는 푸터에 둔다. 한 페이지가 40행이라 화면보다 길고, 다음 페이지로 가는 길을 끝까지 내려가야 찾게 둘 이유가 없다. sticky만으로는 스크롤할 것이 있을 때만 붙어, 마지막 페이지처럼 짧은 화면에서는 표 바로 아래 화면 중간에 머물렀다. 그래서 푸터가 든 칸을 카드 높이까지 늘이고(`min-height:100%`와 `flex:1`) `margin-block-start:auto`로 그 바닥에 붙인다. 늘이는 것은 푸터가 있는 화면만 요구하므로 다른 화면은 그대로다. 기능 행은 빗금(`repeating-linear-gradient`)을 깐다. 그 아래 요구사항 행이 평범한 줄이라 묶음의 머리에는 자기 바탕이 필요하고, 배경 이미지라 hover 바탕이 아래로 비친다. 묶음 사이는 마지막 요구사항 행의 아래 여백으로 벌린다(`:has(+ tr[data-row=feature])`). 선 하나로는 행 구분선과 구별되지 않아 묶음이 끝난 것으로 읽히지 않았다. 빈 자리에는 빗금이 없으므로 빗금이 다시 시작하는 것이 곧 다음 묶음이다. 제목 아래에 설명을 두면 설명이 있는 행만 높아져 훑어 내려가는 열의 리듬이 깨지므로 한 줄에 모으고 긴 설명은 자른다. 설계는 있는 것이 기본이라 없을 때만 제목 옆 Token으로 표시하고 전용 열을 두지 않는다. 요구사항 수는 숫자만으로는 다른 기능과 견줄 수 없어 막대를 함께 둔다. 필터 줄에는 검색과 설계 여부·참여자 Selector가 있고 값은 `design`·`author` 검색 인자다. 정렬은 2026-09-20 사용자 요청으로 필터 줄의 Selector에서 열 머리로 옮겼다. 견줄 값이 있는 세 열(기능 이름·요구사항 수·최근 변경)만 `sortable`이고 참여자는 아바타뿐이라 제공하지 않는다. `useTableSortable`은 머리의 표시와 조작만 맡고 실제 정렬은 화면이 한다. 행이 묶여 있어 플러그인이 평평한 행 배열을 다시 늘어놓으면 묶음이 흩어지기 때문이다. 순서는 기능에만 적용하고 요구사항은 문서가 준 자리를 지킨다. 상태는 `sort`(열)와 `dir`(방향)이며 기본인 최근 변경 내림차순은 주소에 쓰지 않는다(저장 순서는 작업 위치를 말해 주지 않는다). 처음 누른 열은 그 열이 읽히는 방향으로 열린다. 이름은 오름차순, 개수와 날짜는 내림차순이다. 플러그인의 기본 주기는 항상 오름차순부터라 최근 변경을 누르면 가장 오래된 것이 먼저 오는데, 그건 그 열을 보려는 이유가 아니다. 좁혀지면 개수 옆에 전체 개수를 덧붙인다. 상세로 갈 때와 목록으로 돌아올 때 네 인자를 그대로 넘긴다. 서버가 `.gitifact/spec`과 위키를 건드린 커밋을 Git 로그 한 번으로 읽어 기능 폴더마다(최대 2000개, 마이그레이션 커밋 제외) contributors와 updatedAt을 응답에 담는다. 행이나 제목을 열면 `/features/<S-ID>` 경로로 이동해 같은 컬럼의 상세 페이지를 그리고 페이지 제목과 필터 줄은 숨긴다. 없는 S-ID는 찾을 수 없음 상태와 목록 링크를 보여준다. 상세의 요구사항 탭은 제목·본문·수용 조건을, 설계 탭은 고른 설계 파일 하나의 제목·설명·다루는 요구사항·참고 문서·본문과 그 문서의 변경을 표시한다. 설계가 없으면 미작성 상태를 안내한다. 메뉴 이름은 2026-09-17에 제품 기능에서 요구사항으로, 2026-09-18에 기능 단위 목록임을 드러내도록 기능별 요구사항으로 바꿨다. 경로는 유지했다. 페이지 이동 버튼이 있는 목록은 바깥 page와 안쪽 column·content·featureTable의 flex 축소를 막아 본문 길이만큼 높이가 늘어나게 한다. 높이가 화면 크기로 줄면 행들이 부모 밖으로 넘치고, sticky 헤더가 부모의 끝에 닿아 화면 위로 밀려난다. 짧은 페이지는 min-height와 여백 자동 분배로 푸터를 바닥에 유지한다.

기능 상세의 탭은 요구사항·설계다. 기능 소개(`index.md` 본문)는 짧아 탭을 따로 두지 않고 요구사항 탭 맨 위에 한 번 둔다. 요구사항 목차는 1200px 이상에서 본문 오른쪽의 14rem 열로 두어 스크롤을 따라오게 하고, IntersectionObserver로 읽는 구간(상단 바 아래부터 화면 위쪽 45%)에 든 첫 요구사항을 목차에 표시한다. 그보다 좁으면 목차가 요구사항 위에 오고 표시는 하지 않는다(2026-09-22 사용자 결정, 데스크톱에서 위쪽 목차가 공간을 많이 차지해서). 기각: 왼쪽 목차(앱 메뉴 옆에 한 겹 더 생김), 접는 목차(보려면 눌러야 하고 위치 표시가 없음). 요구사항을 골라 보는 필터(Tokenizer)도 시도했으나 사용자 판단으로 뺐다. 요구사항 본문의 상대 링크는 기능 폴더가 아니라 그 요구사항 파일(`requirements/<slug>.md`)의 경로를 기준으로 해석한다. selected·tab은 URL 검색 인자에 저장하고, 어느 절을 보러 왔는지는 프래그먼트가 가리킨다. 모든 요구사항·설계 제목에는 형광펜처럼 글자 위로 지나가는 표시(`<mark>`)를 그어 절이 한눈에 나뉘게 하고, 링크로 들어온 요구사항 절에는 기능 목록의 기능 행과 같은 빗금 바탕을 깐다(2026-09-22 사용자 결정). 설계는 한 번에 하나만 보이므로 빗금 대신 목차가 알린다. 처음에는 들어온 절의 제목에만 형광펜을 그었는데, 그 구분감을 기본으로 삼자는 사용자 의견으로 바꿨다. 그보다 앞의 절 옆 세로 줄은 긴 절에서 어느 줄을 읽으라는 말을 하지 못해 2026-09-20에 뺐다. 들어온 요구사항만 남기는 안은 앞뒤 맥락이 가려져 기각했다. 설계 탭은 요구사항 탭과 같은 배치로, 목차 자리에 그 기능의 설계 파일을 `order` 순으로 두고 본문에는 고른 파일 하나만 그린다. 고른 파일은 `selected`의 D-ID이며 없으면 첫 파일이다. 그래서 설계 파일마다 `?tab=design&selected=<D-ID>` 주소가 있다. 목차는 읽는 파일을 모든 폭에서 `aria-current`로 표시하고, 본문 아래에는 이전·다음 파일로 가는 링크를 둔다. 설계 파일은 축마다 따로 쓰여 길고(browser의 ui 파일은 9절이다) 한 번에 한 축을 읽으므로, 모두 이어 붙이던 방식은 목차 없이 긴 스크롤만 남겨 바꿨다. 요구사항 탭은 이어 읽는 방식을 유지한다(들어온 요구사항만 남기는 안을 기각한 이유와 같다). 본문 아래 "이 문서의 변경"(`DocumentHistory`)은 이력 API의 `id` 조건으로 그 문서의 변경 5건을 최신순으로 받아 이유(없으면 커밋 제목)·변경 종류·시각·작성자·커밋을 한 줄씩 보이고, 각 줄은 활동의 그 변경을 연다. 더 있으면 활동으로 잇는다. `docs history`와 같은 내용이다. `model/design-sections.ts`는 프론트매터 `requirements`에 그 요구사항을 적은 설계를 `order` 순으로 모두 모으며 본문은 읽지 않는다. 요구사항 절은 그 설계들의 제목을 모두 링크로 보이고, 기능 목록의 요구사항 행은 자리가 한 칸이라 첫 설계로 간다. 예전 주소처럼 설계 탭의 `selected`가 요구사항 ID이면 그 요구사항을 다루는 첫 설계를 연다. 밖에서 붙여 넣은 주소의 프래그먼트는 절이 그려지기 전에 읽히므로 브라우저가 스크롤하지 못한다. 그래서 대상이 바뀔 때 그 절을 직접 화면에 올린다. 이전의 `?feature=` 진입은 리다이렉트하지 않는다. 설계 프론트매터의 `requirements`는 현재 전체 기능에서 찾아 해당 요구사항으로 연결한다. 삭제된 참조는 현재 명세에 없다고 표시한다. 과거 설계의 링크도 현재 요구사항으로 연결한다. Markdown은 실행 지시가 아닌 데이터로 렌더링한다.

## 제품 개요

`/product`는 체크아웃과 이력 요약(`/api/v1/history/summary`)으로 그린다. 머리는 프로젝트 이름(Git 상태 응답의 체크아웃 폴더 이름)과 한 줄 규모(기능·요구사항·위키 페이지·참여자), 미커밋 Token, 최근 변경 시각이다. 오른쪽 끝에는 최근 21일의 변경을 일자별로 센 막대를 인라인 SVG로 둔다. 계열이 하나라 범례 대신 "최근 21일 변경 · 전체 활동 N건"으로 센 범위를 밝힌다.

그 아래가 좌우 두 장의 차트 카드(전체 이력의 변경 종류 비율, 참여자별 커밋)이고 두 카드는 높이가 같다(Grid `align="stretch"`). 참여자가 많아 범례가 두 줄이 되면 한쪽 카드만 길어지던 것을 2026-09-19 사용자 요청으로 맞췄다. 마지막이 "최신 활동"이다. 활동 화면의 타임라인 컴포넌트를 그대로 써서 두 화면이 같게 읽힌다. 커밋은 셋까지 싣고 커밋마다 기록은 10개까지 보인 뒤 "기록 N건 더"로 활동에 잇는다. 도입 커밋처럼 기록 수백 개를 만든 커밋이 화면을 덮지 않게 하기 위해서다. 기록 수는 가려진 것을 포함한 커밋 전체 수이므로 10개를 보이고 "기록 15건 더"라면 그 커밋은 25건이다. 나머지는 활동 타임라인이 맡는다. 활동으로 가는 링크는 이 절의 제목 옆 하나뿐이다. 이력 요약은 체크아웃과 다른 조회라 화면이 그려진 뒤에도 오는 중일 수 있다. 답이 오기 전에는 건수와 빈 상태 대신 같은 타임라인 골격과 막대 자리를 둔다. "전체 활동 0건"이나 "커밋된 명세 활동이 아직 없습니다"는 사실과 반대를 말하기 때문이다.

2026-09-19 사용자 요청으로 요약 타일 다섯 개와 페이지 제목을 걷어내고 변경 이유를 본문으로 삼았다. 타일이 이끌던 화면에는 제품이 기록하는 이유가 없었고 제목은 메뉴·이동 경로와 같은 말을 세 번째로 되풀이했다. 같은 요청에서 기능 현황 카드(살펴볼 곳·최근 손댄 기능)를 뺐고 차트 두 장은 그대로 두었다. 기능 전체 표는 기능별 요구사항 화면이 그린다. 위키 README는 위키 운영 방침이라 개요가 싣거나 링크하지 않는다. 위키에서 README를 읽을 때는 첫 블록이 이미지이면 워드마크와 겹치므로 그 한 장만 빼고, 상대 경로 이미지·링크는 문서 링크 절의 규칙으로 해석한다.

## Git 상태

Git 상태 페이지도 같은 중앙 컬럼과 헤더의 새로고침 버튼을 쓰며 헤더에 마지막 관측 시각을 "조회"로 표시한다. 브랜치·HEAD·저장소를 MetadataList로, Staged·Unstaged·Untracked·충돌 집계를 한 줄로, 변경 경로를 Table로 보여준다. 표의 상태 열은 porcelain 두 글자 코드를 Staged·Unstaged·Untracked·충돌 Token으로 풀어 표시하고 원래 코드는 옆 열에 둔다. 변경이 없으면 빈 상태 일러스트를, 관측 한계와 gitifact 검사 미실행 안내는 하단 상태 줄에 둔다. 미커밋 명세 변경이 있으면 본문 맨 위에 경고 Banner를 둔다.

## 설정과 색 조합

WORKSPACE 그룹의 마지막 메뉴인 `/settings`에서 화면 모드(시스템·라이트·다크)와 색 조합을 고른다. 선택은 shared/lib/appearance가 localStorage(`gitifact-appearance`)에 저장하고 useSyncExternalStore로 구독하며, 다른 탭의 변경도 storage 이벤트로 따른다. 서버나 프로젝트에는 아무것도 보내지 않는다. 저장값이 깨져 있으면 기본값(시스템·스톤)을 쓰고 저장소를 쓸 수 없으면 그 페이지 동안만 유지한다. AppProviders가 Astryx Theme의 theme와 mode에 반영한다.

라이트 모드의 글자색은 모든 조합에서 거의 검정보다 한 단계 밝힌다(스톤 `#25252a`→`#3a3a40`, 세이지 `#3b4439`, 올리브 `#36372e`, 슬레이트 `#36415a`, 클레이 `#473b34`). 2026-09-19 사용자가 라이트 모드의 글자와 로고가 너무 어둡다고 해 SandboxHr의 값을 따랐다. 워드마크는 글자색으로 그려지므로 함께 밝아진다. 다크 모드는 그대로다. 그래서 스톤도 prebuilt 테마를 그대로 쓰지 않고 stone 소스를 extends해 글자 토큰 두 개만 바꾼다. 첫 화면은 전역 CSS가 가져오는 stone theme.css로 그려지고 바뀐 글자 토큰은 런타임에 주입된다. 나머지 조합(세이지 & 크림, 올리브 & 웜그레이, 슬레이트 & 블루, 샌드 & 클레이)은 stone 소스를 extends해 글꼴·모서리·아이콘·컴포넌트 재정의를 물려받고 색 토큰 16개만 라이트·다크 쌍으로 명시한다. 값은 Gentask의 팔레트와 hoho-hr의 Halo · Olive 토큰(OKLCH를 hex로 변환)에서 가져왔다. 강조색 하나에서 나머지를 유도하는 방식(color.accent 시드)은 기각했다. stone은 링크와 메뉴 글자가 강조색 토큰을 글자색으로 쓰기 때문에 색이 글자·메뉴·바탕 전체로 번진다. 그래서 글자용 강조 토큰(`--color-text-accent`·`--color-icon-accent`)은 조합의 글자색을 따르고, 채도 높은 강조색은 선택 표시·진행 막대·버튼에만 나타난다. 설정 카드의 미리보기는 라이트·다크 각각의 바탕·표면·강조 점·글자 선을 축소판으로 그린다.

## 화면 확대

루트 글자 크기는 1920px까지 100%이고 그 위로는 뷰포트에 비례해 2560px에서 18px에 닿는다. Astryx의 spacing·size-element 토큰은 px로 배포되므로 같은 16px 기준값을 rem으로 다시 선언해 글자와 간격이 함께 커진다. 페이지별 zoom이나 root font-size 변경은 두지 않는다.

## 시작하기 안내

GITIFACT 메뉴에서 소개 다음에 `/getting-started`를 둔다. `pages/getting-started`는 소개와 같은 64rem 중앙 컬럼, PageHeader와 DocumentBody를 사용한다. 페이지 제목은 화면 문구 카탈로그에서 읽고 Markdown의 최상위 제목은 표시할 때 제거해 중복하지 않는다. 소개의 GitHub CLI 안내 링크는 앱 안에서 이 경로로 연결한다.

한국어·영어 원본은 `packages/intro/<lang>/getting-started.md`다. packages/intro의 공개 export를 shared/i18n이 가져와 localDocument로 제공한다. 소개와 같은 언어별 문서 방식으로 번들하므로 별도 HTTP 조회나 명세 저장소에 의존하지 않는다. 현재 CLI 도움말·내장 지침으로 확인한 사용 흐름을 한국어로 작성한 뒤 영어판을 만들었으며 npm README도 영어 원문과 일치시킨다. 입력 JSON의 상세 형식은 복제하지 않고 docs spec·commit으로 안내한다. 사용자용 명령 예시는 npx로 통일한다. 처음 도입·업데이트에는 @latest를 쓰고 일상 예시는 npx gitifact로 짧게 적는다. --yes와 버전 고정은 에이전트 블록에서 관리한다. 프로젝트 설치 예시는 별도 절에 두며 에이전트용 docs의 gitifact 약칭은 유지한다.

메뉴 순서, 소개 링크, 키보드 이동, 직접 진입·새로고침과 모바일 두 테마를 검사한다. 명세가 없는 임시 Git 저장소에서도 실제 CLI 서버가 안내를 제공하는지 확인한다.

## GitHub 저장소 바로가기

BrowserShell의 SideNav footer에서 버전 표시 옆에 GitHub 로고와 이름을 둔다. 기존 SvgIcon과 Hugeicons의 GithubIcon을 사용하고 외부 이미지를 가져오지 않는다. 링크는 고정된 제품 저장소 주소를 가리키며 target="_blank"와 rel="noopener noreferrer"로 새 탭에서 연다. 현재 체크아웃의 Git 원격 주소를 사용하지 않는다.

모바일 탐색에서도 같은 footer를 사용한다. 링크는 세션 조회 성공 여부와 무관하게 표시하고 새 탭 안내 툴팁은 현재 표시 언어를 따른다.
