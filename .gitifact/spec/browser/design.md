# 명세 브라우저 설계

## 개요

명세 이력·요구사항·참여자를 연결하는 읽기 전용 브라우저다. React·Astryx로 UI를 구성하고 TanStack Router가 경로·선택·필터를, TanStack Query가 서버 조회 상태를 관리한다. 목록을 대체하는 상세 페이지는 경로 계층(`/features/<S-ID>`, `/contributors/<이메일>`)으로 구분하고, 같은 화면 안의 검색·탭·드로어 선택은 URL 검색 인자에 둔다. 브라우저는 파일이나 Git 명령을 직접 실행하지 않는다.

## 구조와 데이터
<!-- gitifact-ref: R-5eehizubwl -->

왼쪽 메뉴는 Astryx SideNav의 resizable 옵션으로 200~400px 사이에서 너비를 조절하고 localStorage에 유지한다. 메뉴 순서는 제품 개요·기능별 요구사항·프로젝트 위키·활동·참여자·Git 상태다. 브라우저는 제품 개요(`/product`)에서 시작한다. `/`는 검색 인자가 없으면 `/product`로, 있으면 같은 인자를 붙여 `/activity`로 리다이렉트한다. 0.5.0 전에는 활동이 `/`였으므로 저장해 둔 활동 링크가 필터와 선택을 잃지 않게 했다. CLI 로컬 서버가 정적 앱과 API를 제공한다. 현재 원문은 작업 폴더에서, 이력의 전후·작성자·시점은 Git에서 읽되 이력은 로컬 색인(이력 색인 절)을 거친다.

미커밋 내용은 문장 대신 표시로 알린다. 셸은 `useWorkingChanges`로 명세 Query 캐시의 `working`을 읽어 Git 상태 메뉴에 경고 StatusDot을 붙이고, Git 상태 페이지는 같은 값으로 상단 Banner에 "제품 개요·기능별 요구사항·위키 화면은 작업 중인 내용이고 활동은 커밋된 내용"임을 설명한다. 이 훅은 명세 API를 스스로 호출하지 않고, 모든 페이지가 이미 읽는 Git 상태 응답의 `.gitifact/`·`.tryce/` 아래 변경 경로를 두 번째 출처로 본다. 처음 구현은 셸에서 명세를 조회했으나 gitifact 저장소가 없는 프로젝트의 Git·소개 화면에서 503 오류가 콘솔에 남아 캐시 읽기로 바꿨고, 캐시만으로는 Git 페이지에 바로 들어올 때 표시가 비어 상태 경로를 더했다.

Query 키에는 origin·서버 세션·worktree를 포함한다. API 요청은 세션 헤더를 보내며 응답 형식과 세션을 검증한다. 명세 조회의 staleTime은 무한이고 갱신은 헤더의 새로고침 버튼뿐이다. 5초였을 때는 명세 화면 다섯이 이 조회 하나를 함께 쓰는 탓에 화면을 옮길 때마다 불러온 페이지가 전부 다시 요청됐다. 더보기를 두 번 누른 뒤 활동으로 돌아오면 3회·약 2초가 들었고 더 불러올수록 늘었다. 지금은 0회다.

API와 계약은 다음과 같다. 모두 세션 헤더가 필요하고 응답은 계약 형식과 세션을 검증한다.

| 경로 | 계약 | 내용 |
| :--- | :--- | :--- |
| `/api/v1/specs` | browser-specs v4 | 체크아웃(현재 기능·위키·참여자·미커밋 여부) 전체 |
| `/api/v1/history?head&offset&limit&kind&document&feature&author&q` | browser-history v1 | 조건에 맞는 변경 한 페이지와 전체 건수 |
| `/api/v1/history/summary?head` | browser-history-summary v1 | 종류별 건수, 최근 3주 커밋별 건수, 최신 커밋 셋 |
| `/api/v1/change?key` | browser-change v1 | 변경 하나의 목록 정보와 전후 본문 |
| `/api/v1/search?q&head` | browser-search v1 | 체크아웃과 지난 변경의 검색 결과 |

v3까지는 체크아웃이 이력의 첫 페이지에 실렸고 화면은 불러온 페이지만 거르고 셌다. 필터가 불러온 범위에만 걸려, `.gitifact` 커밋이 10개인 프로젝트는 첫 페이지에 이력 325건·1.9MB가 한 번에 오는 반면 커밋이 많은 프로젝트는 필터가 오래된 변경을 찾지 못했다. 2026-09-19 사용자가 "DB를 쓸 때처럼 전체를 대상으로 검색·페이징해야 한다"고 해 v4에서 체크아웃과 이력을 나눴다. 체크아웃은 저장 규약의 상한(파일 2000개·16MB)이 있어 통째로 보내고 화면이 거른다. 이력은 끝이 없어 서버가 거르고 세며 50건씩 준다. 목록 이벤트의 before·after는 id·title·specId·path만 담고 본문은 change로 받는다. 이력 쿼리는 HEAD를 받으므로 같은 HEAD의 답은 바뀌지 않고, 브라우저는 HEAD·조건별로 세션 동안 보관한다. 쿼리 스키마도 계약 패키지에 두어 서버와 브라우저가 같은 규칙을 쓴다. FSD의 entities는 조회를, pages/product는 화면 구성과 검색 상태를 담당한다.

## 서버 구조
<!-- gitifact-ref: R-5eehizubwl -->

`apps/cli/src/server/`는 역할별로 나눈다. `browser-server.ts`는 시작·종료와 연결만 맡는다. `http/guard.ts`는 모든 요청의 공통 검사(Host·Origin·교차 사이트·경로 탈출·본문 거부·보안 헤더), `http/router.ts`는 경로 표 디스패치, `http/respond.ts`는 JSON·오류 응답, `http/static-files.ts`는 앱 파일이다. 경로는 `routes/`의 세 표(project: 세션·상태·패치노트, record: 체크아웃·이력·요약·변경·검색, asset: 저장소 에셋)이고, 한 줄에 메서드·경로·세션 필요 여부·쿼리 스키마·처리 함수를 둔다. 라우터가 경로 → 메서드(405와 Allow) → 쿼리(중복 키·스키마, 400) → 세션(409) 순으로 거른 뒤 처리 함수를 부르고, 처리 함수가 던진 HttpError는 그 상태로, 그 밖의 오류는 503과 이유로 답한다. `checkout/`은 작업 폴더 체크아웃과 작성자 집계, `history/`는 커밋별 변경 계산(commit-changes)·SQLite 파일(index-database)·색인과 질의(history-index)·검색 글 다듬기(search-text)다.

express·Fastify 같은 프레임워크는 넣지 않았다(2026-09-19 사용자 결정). 느린 원인은 HTTP가 아니라 git 프로세스와 파일 읽기였고, 라우팅·JSON은 1ms도 안 걸린다. 보안 검사는 제품 고유라 프레임워크를 써도 직접 짜야 하며, CLI는 런타임 의존성 없이 파일 하나로 번들된다. 라우팅 정리는 경로 표와 계약의 zod 스키마로 충분했다.

## 활동 타임라인
<!-- gitifact-ref: R-tkl3lrrlpu, R-hsflueyc4b -->

변경은 커밋마다 바뀐 파일만 읽어 계산한다(history/commit-changes.ts). `git log --stdin --no-walk --raw` 한 번이 커밋 100개가 바꾼 파일·blob을 알려 주고, `git cat-file --batch` 한 번이 그 커밋들의 양쪽(커밋과 첫 부모)에서 바뀐 기능 폴더의 requirements.md·design.md·history.jsonl 전부와 바뀐 위키 페이지·위키 history.jsonl만 `<커밋>:<경로>`로 읽는다. 이 부분 저장소를 비교한 결과는 저장소 전체를 비교한 결과와 같다. 새 이유는 그 커밋에서 바뀐 기록만 가리킬 수 있고, 바뀐 기록은 모두 바뀐 파일 안에 있기 때문이다. 기능 폴더를 통째로 읽는 이유는 요구사항 없이 설계나 이유 파일만 있는 부분 저장소를 파서가 거부하기 때문이다. 부모 쪽에서 레거시 `tryce.json`이 지워지면 부모를 빈 저장소로 보고 boundary를 켠다. 커밋 쪽에 레거시 파일이 있거나 부분 읽기가 실패하면 그 커밋만 예전 방식(양쪽 저장소 전체를 읽어 비교)으로 읽어, 드문 이력도 예전과 같이 읽거나 예전과 같이 실패한다.

예전 방식은 커밋마다 저장소 전체를 두 번 읽어 파싱했다. Windows에서 git 프로세스는 하는 일과 무관하게 한 번에 약 80ms라 페이지 하나가 git 37~39회였고 저장소가 클수록 느려졌다. 체크아웃의 작성자 집계는 기능마다·위키 페이지마다 `git log`를 띄우던 것(기능 22·페이지 63이면 85회)을, 저장소를 건드린 커밋을 `--name-only`로 한 번 거는 것으로 바꿨다. 기능별 상한 2000커밋은 유지하며, 병합 커밋은 파일 목록이 없어 작성자 집계에 들지 않는다. 두 실제 저장소(safety-solution-webapp, 이 저장소)의 전체 이력에서 기능별 작성자·최근 커밋과 페이지별 최근 커밋이 예전 방식과 모두 같았다. 체크아웃 읽기 안의 여러 읽기는 나란히 돌리되 실패는 모두 끝난 뒤 알린다. 먼저 실패를 돌려주면 요청이 끝난 뒤에도 git 프로세스가 프로젝트에서 돌았다.

요구사항 R-ID와 설계 S-ID를 각각 비교해 추가·변경·제거·이동을 표시한다. 화면 이름은 추가·변경·제거·이동이며 저장 형식의 created·modified·deleted·moved는 바꾸지 않는다. 목록은 왼쪽 세로 선 위에 작성자 아바타가 놓이는 타임라인이며 한 항목이 커밋 하나다. 항목의 머리는 작성자·상대 시각·기록 수와 커밋 해시·커밋 제목이고, 본문은 기록된 이유마다 한 덩어리다. 기록 수는 그 항목이 지금 보이는 기록의 수다. 서버는 커밋별 전체 건수를 주지 않고 페이지는 커밋 중간에서도 끊기므로, 걸친 커밋은 다음 페이지를 불러오면 한 항목으로 합쳐지며 수도 함께 올라간다(이 저장소의 50a421b는 6 → 25). 이유는 한 번만 적고 그 이유로 바뀐 기록을 한 줄씩 아래에 둔다. 이유가 없으면 미기록 상태를 안내한다. 이유는 기록마다 저장되므로 기록을 한 줄씩 늘어놓으면 같은 문단이 되풀이된다. 이 저장소의 이력 209건은 서로 다른 (커밋, 이유) 묶음이 81개뿐이고 한 이유가 최대 26건을 덮는다. 한 커밋이 여러 이유를 기록하는 경우도 34개 커밋 중 24개라, 커밋으로만 묶고 이유를 모아 보이는 안은 어느 이유가 어느 기록의 것인지를 잃어 기각했다. 날짜가 바뀌는 자리에는 날짜 표시를 두고 그 자리에서 세로 선을 끊는다. 제목을 열면 상세 서랍(Astryx Dialog)에서 변경 내용과 이유를 확인한다. 변경 내용은 그때 받아 오며, 받는 동안 본문 자리에 글줄 모양 골격을, 실패하면 그 자리에 오류를 보인다. 한 번 받은 변경은 세션 동안 다시 묻지 않는다. 변경 전·후가 모두 있으면 변경 후 본문 위에 변경 전 본문을 겹쳐 두고, 세로 손잡이를 오른쪽으로 끌수록 변경 전이 같은 자리에서 드러난다(이미지 비교 슬라이더 방식). 변경 전 층은 테마의 background-yellow 황색 배경(다크에서는 어두운 올리브)이며 바깥쪽 모서리만 둥글고, 두 본문은 한 그리드 셀을 공유해 높이는 둘 중 큰 쪽이다. 변경 전·변경 후 버튼으로 한쪽을 바로 볼 수 있고 손잡이는 화살표·Home·End 키로도 움직인다. 추가·제거처럼 한쪽만 있으면 본문 하나만 보여준다. Astryx ResizeHandle은 1px 루트 안에서만 포인터를 받아 겹침 비교에 맞지 않았으므로 손잡이는 직접 구현했다. 선택은 URL의 selected에 저장한다. 이전의 같은 명세 연결 그래프는 읽기에 방해가 되어 2026-09-15에 제거했다.

본문은 1024px 중앙 컬럼이며 스크롤은 콘텐츠 카드가 담당한다. 제목은 스크롤로 사라지고 필터 줄은 상단 바 아래에 고정된다. 종류·기능·작성자·검색 필터는 서버가 전체 이력에 적용하고, 목록 아래에 "전체 N건 중 M건"을 알린다. 조건을 바꾸는 동안에는 이전 결과를 유지한다. 검색창(`SearchFilter`)은 입력 중인 글자를 자기 상태로 들고 URL의 `q`에는 replace로 따라 반영한다. 입력을 URL에 직접 묶었을 때는 라우터의 비동기 갱신이 한글 조합 도중 이전 값을 되돌려 써서 "검색"이 "ㄱ거검검ㅅ새색색"처럼 쌓였다. 필드가 보낸 값이 늦게 돌아오는 것은 무시하고, 필드가 보내지 않은 값(뒤로가기, `q`가 담긴 링크)이 오면 그 값으로 바꾼다. 같은 검색창을 활동·기능별 요구사항·참여자가 함께 쓴다. 더보기는 기존 목록에 다음 50건을 추가하며 실패 시 재시도할 수 있다. 불러온 페이지는 다른 화면에 다녀와도 남긴다. 커밋 항목은 memo 컴포넌트이며 이벤트·기능 객체의 동일성으로 비교하므로 더보기 때 새 커밋만 그린다(기록 243건까지 한 번에 80~114ms로 일정하고, 다른 화면에 다녀와 그리는 데 260~375ms). 한 줄 자르기는 CSS로 한다. Astryx Text의 maxLines는 잘렸을 때 툴팁을 띄우려고 요소마다 크기를 재는데, 줄마다 두 번 쓰여 334줄이면 레이아웃을 668번 강제했다. 다른 화면에 다녀올 때 2,899ms가 걸렸고 그중 2.7초가 이 측정이었으며, 지금은 약 0.4~0.5초다. 첫 페이지만 남기고 다시 더보기를 시키는 안은 돌아올 때 약 230ms로 차이가 작은 반면 읽던 범위를 잃어 기각했다. 서랍은 목록이 아니라 키로 변경을 받아 오므로 목록에 없는 변경의 링크도 연다. 목록에 있는 항목이면 받는 동안 제목을 먼저 보인다.

## 이력 색인
<!-- gitifact-ref: R-5eehizubwl, R-tkl3lrrlpu, R-fqlesmxflt -->

이력은 로컬 SQLite 색인(history/history-index.ts)에서 거르고 세고 찾는다. 커밋은 바뀌지 않으므로 커밋의 변경은 한 번 읽어 영구히 두고, HEAD마다 그 커밋들의 순서(계보)만 더한다. 새 HEAD는 `git rev-list --first-parent HEAD -- <기록 경로>` 한 번으로 계보를 얻고, 색인에 없는 커밋만 100개씩 읽어 넣는다. pull 뒤에는 새 커밋만, 브랜치를 오가면 대개 아무것도 읽지 않는다. 계보는 최근 HEAD 네 개까지 둔다. 질의는 계보와 변경을 잇는 SQL이며 git을 부르지 않는다.

파일은 `<git 공용 폴더>/gitifact/index.sqlite`다(2026-09-19 사용자 결정). 작업 폴더에도 `git status`에도 나타나지 않아 사용자에게 새 폴더가 생기지 않고, worktree끼리 함께 쓴다. `.gitifact/data/`(안에 `.gitignore`)에 두는 안은 에디터 트리에 폴더가 보이고 worktree마다 따로 만들며 `init`의 예외가 필요해 기각했다. 서버 메모리에만 두는 안은 서버를 띄울 때마다 전체를 다시 읽어 기각했다. JSON 파일 안은 결국 메모리에 올려 직접 거르고 찾아야 해 기각했다. SQLite는 Node 24에 내장된 `node:sqlite`라 패키지 의존성이 늘지 않는다.

연결은 쓸 때마다 열고 닫는다. 서버가 요청 사이에 파일을 잡지 않아 테스트가 저장소를 지울 수 있고, 같은 저장소의 서버 둘은 SQLite 잠금(`BEGIN IMMEDIATE`, busy_timeout 5초)으로 차례를 지킨다. 같은 커밋을 둘이 쓰면 먼저 쓴 쪽이 남는다(`INSERT OR IGNORE`). 형식 번호(`PRAGMA user_version`)가 다르면 표를 지우고 다시 만들고, 파일이 손상돼 열리지 않으면 지우고 한 번 다시 만든다. 그래도 안 되면(읽기 전용 저장소 등) 그 프로세스 동안 메모리 DB를 쓴다. 표는 commits(커밋별 boundary), changes(변경별 목록 JSON·전후 본문 JSON·필터 열), lineage(HEAD별 커밋 순서), heads, checkouts(검색 행이 어느 체크아웃인지), search(FTS5)다.

요약은 전체 이력의 종류별 건수, 최신 변경 기준 22일 안의 커밋별 날짜·건수, 최신 커밋 셋과 각각의 변경 12개까지다. 21일 막대는 브라우저가 커밋별 건수를 자기 시간대의 날짜로 나눠 센다.

잰 값(safety-solution-webapp: 변경 332건, 이 저장소: 202건). 색인이 없을 때 첫 이력 요청 292ms·538ms, 서버를 다시 띄운 뒤 첫 요청 60ms·99ms, 다음 페이지·필터·요약·단건 9~18ms, 검색 14~35ms. 브라우저에서 활동 목록이 보이기까지 약 0.9~1.0초(대부분 체크아웃 읽기)다. 예전 방식과의 동등성은 실제 CLI로 만든 이력(이동·삭제·위키 이동·설계 삭제·이유)과 두 실제 저장소의 전체 이력에서 순서·종류·이유·전후 본문을 모두 대조해 확인했다.

## 요구사항 목록과 기능 상세
<!-- gitifact-ref: R-xqf3xsumye -->

기능별 요구사항 메뉴(`/features`)의 목록은 활동 페이지와 같은 1024px 중앙 컬럼의 Astryx Table이며 한 행에 제목·설계 없음 표시·한 줄 설명, 요구사항 수와 가장 많은 기능 대비 ProgressBar, AvatarGroup 참여자(3명 초과는 +N), 상대 시각을 둔다. 그 아래에 그 기능의 요구사항이 번호·제목·설계로 가는 링크만 담은 낮은 행으로 이어진다(`data-row`로 구분). 기능 8개에 요구사항이 39개인데 설명은 하나뿐이라 목록이 제목·개수·아바타만 보이고 정작 내용인 요구사항은 한 줄도 없었다. 행은 `model/feature-rows.ts`가 기능·요구사항·나머지 세 종류로 만들고, 페이지는 40행을 넘기 전까지 기능을 담되 한 기능을 쪼개지 않는다. 행으로 나누면 한 기능이 페이지에 걸쳐 끊기고, 기능 수로 나누면 도입 커밋처럼 요구사항 200개짜리 기능 하나가 페이지를 덮는다. 그래서 한 기능은 요구사항 12개까지 보인 뒤 "요구사항 N개 더"로 상세에 잇는다. 페이지는 `page` 검색 인자이며 숫자라 주소가 `?page=2`로 읽힌다. 페이지 매김은 카드 바닥에 붙는 푸터에 둔다. 한 페이지가 40행이라 화면보다 길고, 다음 페이지로 가는 길을 끝까지 내려가야 찾게 둘 이유가 없다. sticky만으로는 스크롤할 것이 있을 때만 붙어, 마지막 페이지처럼 짧은 화면에서는 표 바로 아래 화면 중간에 머물렀다. 그래서 푸터가 든 칸을 카드 높이까지 늘이고(`min-height:100%`와 `flex:1`) `margin-block-start:auto`로 그 바닥에 붙인다. 늘이는 것은 푸터가 있는 화면만 요구하므로 다른 화면은 그대로다. 기능 행은 빗금(`repeating-linear-gradient`)을 깐다. 그 아래 요구사항 행이 평범한 줄이라 묶음의 머리에는 자기 바탕이 필요하고, 배경 이미지라 hover 바탕이 아래로 비친다. 묶음 사이는 마지막 요구사항 행의 아래 여백으로 벌린다(`:has(+ tr[data-row=feature])`). 선 하나로는 행 구분선과 구별되지 않아 묶음이 끝난 것으로 읽히지 않았다. 빈 자리에는 빗금이 없으므로 빗금이 다시 시작하는 것이 곧 다음 묶음이다. 제목 아래에 설명을 두면 설명이 있는 행만 높아져 훑어 내려가는 열의 리듬이 깨지므로 한 줄에 모으고 긴 설명은 자른다. 설계는 있는 것이 기본이라 없을 때만 제목 옆 Token으로 표시하고 전용 열을 두지 않는다. 요구사항 수는 숫자만으로는 다른 기능과 견줄 수 없어 막대를 함께 둔다. 필터 줄에는 검색과 설계 여부·참여자 Selector가 있고 값은 `design`·`author` 검색 인자다. 정렬은 2026-09-20 사용자 요청으로 필터 줄의 Selector에서 열 머리로 옮겼다. 견줄 값이 있는 세 열(기능 이름·요구사항 수·최근 변경)만 `sortable`이고 참여자는 아바타뿐이라 제공하지 않는다. `useTableSortable`은 머리의 표시와 조작만 맡고 실제 정렬은 화면이 한다. 행이 묶여 있어 플러그인이 평평한 행 배열을 다시 늘어놓으면 묶음이 흩어지기 때문이다. 순서는 기능에만 적용하고 요구사항은 문서가 준 자리를 지킨다. 상태는 `sort`(열)와 `dir`(방향)이며 기본인 최근 변경 내림차순은 주소에 쓰지 않는다(저장 순서는 작업 위치를 말해 주지 않는다). 처음 누른 열은 그 열이 읽히는 방향으로 열린다. 이름은 오름차순, 개수와 날짜는 내림차순이다. 플러그인의 기본 주기는 항상 오름차순부터라 최근 변경을 누르면 가장 오래된 것이 먼저 오는데, 그건 그 열을 보려는 이유가 아니다. 좁혀지면 개수 옆에 전체 개수를 덧붙인다. 상세로 갈 때와 목록으로 돌아올 때 네 인자를 그대로 넘긴다. 서버가 기능마다 `.gitifact`와 `.tryce` 폴더 경로로 Git 로그(최대 2000개)를 읽어 contributors와 updatedAt을 응답에 담는다. 행이나 제목을 열면 `/features/<S-ID>` 경로로 이동해 같은 컬럼의 상세 페이지를 그리고 페이지 제목과 필터 줄은 숨긴다. 없는 S-ID는 찾을 수 없음 상태와 목록 링크를 보여준다. 상세의 요구사항 탭은 제목·본문·수용 조건을, 설계 탭은 문서 전체를 표시한다. 설계가 없으면 미작성 상태를 안내한다. 메뉴 이름은 2026-09-17에 제품 기능에서 요구사항으로, 2026-09-18에 기능 단위 목록임을 드러내도록 기능별 요구사항으로 바꿨다. 경로는 유지했다.

selected·tab은 URL 검색 인자에 저장하고, 어느 절을 보러 왔는지는 프래그먼트가 가리킨다. 그 절의 제목에는 형광펜처럼 글자 위로 지나가는 표시를 남긴다(`<mark>`). 절 옆의 세로 줄은 긴 절에서 "여기 무언가 있다"만 말하고 어느 줄을 읽으라는 말은 하지 못해 2026-09-20 사용자 지적으로 바꿨다. 설계 절의 id는 Astryx Markdown이 제목에 붙이는 것을 그대로 쓰고, `model/design-sections.ts`가 ref 주석 위의 제목을 문서 순서로 outline과 맞춰 요구사항 → 절 id를 만든다. 글이 어긋나는 짝은 버린다. 엉뚱한 절로 보내는 것이 링크가 없는 것보다 나쁘다. 요구사항 39개 중 38개가 어떤 절에 연결된다. 밖에서 붙여 넣은 주소의 프래그먼트는 절이 그려지기 전에 읽히므로 브라우저가 스크롤하지 못한다. 그래서 대상이 바뀔 때 그 절을 직접 화면에 올린다. 이전의 `?feature=` 진입은 리다이렉트하지 않는다. 설계의 R-ID 참조는 현재 전체 기능에서 찾아 해당 요구사항으로 연결한다. 삭제된 참조는 현재 명세에 없다고 표시한다. 과거 설계의 링크도 현재 요구사항으로 연결한다. Markdown은 실행 지시가 아닌 데이터로 렌더링한다.

## 제품 개요
<!-- gitifact-ref: R-oh4oevufr3 -->

`/product`는 체크아웃과 이력 요약(`/api/v1/history/summary`)으로 그린다. 머리는 프로젝트 이름(Git 상태 응답의 체크아웃 폴더 이름)과 한 줄 규모(기능·요구사항·위키 페이지·참여자), 미커밋 Token, 최근 변경 시각이다. 오른쪽 끝에는 최근 21일의 변경을 일자별로 센 막대를 인라인 SVG로 둔다. 계열이 하나라 범례 대신 "최근 21일 변경 · 전체 활동 N건"으로 센 범위를 밝힌다.

그 아래가 좌우 두 장의 차트 카드(전체 이력의 변경 종류 비율, 참여자별 커밋)이고 두 카드는 높이가 같다(Grid `align="stretch"`). 참여자가 많아 범례가 두 줄이 되면 한쪽 카드만 길어지던 것을 2026-09-19 사용자 요청으로 맞췄다. 마지막이 "최신 활동"이다. 활동 화면의 타임라인 컴포넌트를 그대로 써서 두 화면이 같게 읽힌다. 커밋은 셋까지 싣고 커밋마다 기록은 10개까지 보인 뒤 "기록 N건 더"로 활동에 잇는다. 도입 커밋처럼 기록 수백 개를 만든 커밋이 화면을 덮지 않게 하기 위해서다. 기록 수는 가려진 것을 포함한 커밋 전체 수이므로 10개를 보이고 "기록 15건 더"라면 그 커밋은 25건이다. 나머지는 활동 타임라인이 맡는다. 활동으로 가는 링크는 이 절의 제목 옆 하나뿐이다. 이력 요약은 체크아웃과 다른 조회라 화면이 그려진 뒤에도 오는 중일 수 있다. 답이 오기 전에는 건수와 빈 상태 대신 같은 타임라인 골격과 막대 자리를 둔다. "전체 활동 0건"이나 "커밋된 명세 활동이 아직 없습니다"는 사실과 반대를 말하기 때문이다.

2026-09-19 사용자 요청으로 요약 타일 다섯 개와 페이지 제목을 걷어내고 변경 이유를 본문으로 삼았다. 타일이 이끌던 화면에는 제품이 기록하는 이유가 없었고 제목은 메뉴·이동 경로와 같은 말을 세 번째로 되풀이했다. 같은 요청에서 기능 현황 카드(살펴볼 곳·최근 손댄 기능)를 뺐고 차트 두 장은 그대로 두었다. 기능 전체 표는 기능별 요구사항 화면이 그린다. 위키 README는 위키 운영 방침이라 개요가 싣거나 링크하지 않는다. 위키에서 README를 읽을 때는 첫 블록이 이미지이면 워드마크와 겹치므로 그 한 장만 빼고, 상대 경로 이미지·링크는 문서 링크 절의 규칙으로 해석한다.

## 오류 처리와 검증
<!-- gitifact-ref: R-5eehizubwl -->

첫 조회의 골격 화면은 200ms 뒤에 나타나고 한번 보이면 최소 300ms 유지한 뒤 본문이 페이드인한다. 골격은 화면별로 실제 배치(활동은 세로 선·아바타·세 줄, 요구사항·참여자는 표 행, 제품 개요는 머리·카드 두 장·변경 이력, 위키는 트리·경로 줄·본문)를 본떠 교체 순간 레이아웃이 바뀌지 않게 한다. 위키 골격은 탐색기의 클래스를 그대로 써서 트리 폭과 경로 줄 높이가 실제와 같고, 트리 행(38px)과 폴더 목록 행(48px)도 실제 간격에 맞춘다. 페이지(`/wiki/$id`)는 제목·정보 세 칸·문단으로, 폴더(`/wiki`)는 테두리 있는 목록과 README 상자로 그린다. 2026-09-19 전까지 위키 골격은 지침 화면 시절의 열 배치 클래스를 쓰고 있었는데 그 클래스가 이미 지워져 모양 없이 그려졌다. 재조회 중 기존 내용을 유지하며 빈 결과·검색 결과 없음·조회 실패를 구분한다. HEAD·원문이 조회 중 바뀌거나 세션이 교체되면 다시 조회하도록 알린다.

계약 fixture로 선택·탭·필터·더보기·누락 참조·모바일·오류·대시보드 집계·위키 탐색기(트리·폴더 목록·페이지)·미커밋 표시를 검사하고, 실제 Git 저장소와 패키징된 서버로 조회를 확인한다. 성능은 실제 측정값으로 보고한다.

Git 상태 페이지도 같은 중앙 컬럼과 헤더의 새로고침 버튼을 쓰며 헤더에 마지막 관측 시각을 "조회"로 표시한다. 브랜치·HEAD·저장소를 MetadataList로, Staged·Unstaged·Untracked·충돌 집계를 한 줄로, 변경 경로를 Table로 보여준다. 표의 상태 열은 porcelain 두 글자 코드를 Staged·Unstaged·Untracked·충돌 Token으로 풀어 표시하고 원래 코드는 옆 열에 둔다. 변경이 없으면 빈 상태 일러스트를, 관측 한계와 gitifact 검사 미실행 안내는 하단 상태 줄에 둔다. 미커밋 명세 변경이 있으면 본문 맨 위에 경고 Banner를 둔다.

## 화면 확대

루트 글자 크기는 1920px까지 100%이고 그 위로는 뷰포트에 비례해 2560px에서 18px에 닿는다. Astryx의 spacing·size-element 토큰은 px로 배포되므로 같은 16px 기준값을 rem으로 다시 선언해 글자와 간격이 함께 커진다. 페이지별 zoom이나 root font-size 변경은 두지 않는다.

## 문서 읽기
<!-- gitifact-ref: R-wa3wnknrlt -->

위키 페이지·요구사항 본문·설계·활동 전후 본문·소개는 shared/ui/document의 DocumentBody로 렌더링한다. Astryx Markdown은 문단을 680px로 제한하면서 표·코드·구분선은 전체 폭으로 그려 오른쪽 끝이 어긋나므로, 읽기 영역을 48rem 한 폭으로 묶고 contentWidth를 100%로 둔다. 크기는 Astryx 글자 토큰을 읽기 영역에서 재정의해 맞춘다. 본문 16px·줄 간격 1.8, 코드 14px, 제목은 어느 단계에서도 본문보다 크게 잡고 위 간격을 아래보다 넓게 준다. 표는 테두리·둥근 모서리·옅은 머리글 행과 내부 가로 스크롤, 인용은 옅은 바탕과 왼쪽 선, 인라인 코드는 테두리 있는 칩, 링크는 테마상 글자색과 같으므로 밑줄로 구분한다. 지침 미리보기 열과 기능 설명 한 줄은 좁은 자리라 compact 표시를 유지한다.

코드 펜스는 `components.code`를 우리 렌더러로 바꿔 받는다. 언어가 `mermaid`면 다이어그램으로 그리고 나머지는 Astryx CodeBlock 그대로다. Astryx는 이 슬롯을 바꾸면 자기 감싸개까지 내주므로 블록 사이 간격은 document.module.css의 클래스가 대신 준다. stone 테마의 구문 색은 모두 회색 계열이라 하이라이팅이 보이지 않으므로, GitHub 라이트·다크 값을 한 쌍으로 묶은 구문 테마(shared/ui/document/syntax.ts)를 앱 전체에 SyntaxTheme으로 적용한다. 일반 식별자·구두점·주석·배경은 테마 토큰을 써서 모든 색 조합과 어울린다. Astryx 토크나이저가 모르는 언어(markdown·text 등)는 색 없이 나온다. Tailwind 기반인 fumadocs 스타일을 들여오는 안은 디자인 체계가 둘이 되어 기각했다.

다이어그램은 mermaid 11이며 `import('mermaid')`로만 불러 자기 청크에 남는다. 다이어그램이 없는 문서는 그 청크를 내려받지 않고, 파일은 패키지에 함께 담겨 있어 네트워크를 쓰지 않는다. mermaid는 색을 SVG 안에 써 넣어 `var(--color-*)`를 스스로 읽지 못하므로, 그리기 직전에 그 자리에서 토큰으로 칠한 탐침 요소의 계산된 색(`rgb(…)`)을 읽어 themeVariables로 넘기고 화면 모드·색 조합이 바뀌면 다시 그린다. `securityLevel: 'strict'`로 원문의 click 지시를 거부한다. 라벨은 `htmlLabels: false`로 SVG 텍스트로 그린다. 종류별 설정만으로는 꺼지지 않아 최상위 설정도 함께 준다. 폭이 열보다 넓은 그림은 열에 맞춰 축소되는데, foreignObject 안의 HTML 라벨은 축소를 따르지 않아 상자 밖으로 삐져나오기 때문이다. mermaid는 그림을 문서에 넣어 크기를 재므로, 그 자리를 화면 밖 고정 위치의 요소 하나로 지정한다. 기본값인 `<body>`에 재면 문서가 잠깐 뷰포트보다 커져 스크롤바가 생겼다 사라지고 화면이 좌우로 흔들린다. 재는 요소를 숨기면(visibility:hidden) 폭이 0으로 측정되므로 화면 밖에 두되 숨기지 않는다. 글꼴이 도착하기 전에 재면 상자가 작게 잡히므로 `document.fonts.ready`를 기다린다. 문법이 잘못된 펜스는 문서 전체를 잃지 않도록 그 자리에만 원문 CodeBlock과 파서 메시지를 보여 준다. 렌더러가 만든 SVG는 문자열이라 그 자리에만 innerHTML로 넣으며, 이는 원문 Markdown의 HTML을 실행하지 않는다는 규칙과 별개다. CDN 로딩은 오프라인 동작과 어긋나 기각했고, 그림을 이미지로 미리 굽는 안은 원문이 저장소에서 바로 읽혀야 해 기각했다.

GitHub 알림(`> [!NOTE]` 등 다섯 종류)은 `components.blockquote`에서 가른다. Astryx는 인용 안의 내용을 이미 React 요소로 만들어 넘기므로, 첫 글자 뭉치에서 표지를 떼어 내고 남은 내용을 그대로 쓴다. 표지가 없으면 Astryx Blockquote 그대로다. Astryx는 Blockquote를 인용에만 쓰라고 하므로 알림 상자는 VStack·HStack·Text와 색 토큰(blue·green·purple·yellow·red)으로 짰다. 종류 이름은 다른 화면 문구와 같이 shared/i18n에 둔다. 원문을 미리 고쳐 넣는 안은 Markdown 인스턴스가 쪼개져 제목 id와 목차가 어긋나므로 기각했다.

## 문서 검색
<!-- gitifact-ref: R-fqlesmxflt -->

`mod+K`와 머리의 검색 버튼이 같은 창을 연다. 열림 여부는 `shared/lib/search`의 작은 저장소가 들고, 팔레트는 셸이 한 번 그리며 버튼은 헤더가 그린다. 두 위젯이 서로를 참조하지 않게 상태만 shared에 둔다.

Astryx CommandPalette를 쓴다. 입력 전의 "최근 변경" 목록은 체크아웃의 최근 변경일로 브라우저가 만든다. 입력한 뒤에는 서버(`/api/v1/search`)에 묻는다. 서버는 체크아웃을 읽을 때마다 기능·요구사항·설계·위키 페이지를 검색 행으로 넣고(체크아웃 stamp가 같으면 그대로 둔다), 이력 색인을 만들 때 변경마다 제목과 이유·메시지를 넣는다. 검색 행은 FTS5 trigram 표에 소문자로 두어 `LIKE '%…%'`가 세 글자부터 색인을 쓰고, 두 글자 이하와 `%`·`_`가 든 검색어는 훑어서 찾는다. 체크아웃은 제목 앞부분 → 제목 → 위치 → 본문 순으로 24개, 지난 변경은 HEAD의 계보에서 최신순으로 8개다. 결과 한 줄은 제목·위치·맞은 대목(서버가 자른다)이고 맞은 글자를 표시한다. 고르면 위키는 `/wiki/$documentId`, 요구사항과 설계는 기능 상세의 해당 탭, 변경은 `/activity?selected=<키>`로 보낸다. 새 검색이 나가면 이전 요청은 취소한다. Astryx 팔레트는 결과가 오기 전에 이미 보이는 목록을 제목으로 먼저 좁히고, 남는 게 없으면 빈 상태를 보인다. 입력 전 목록에서 첫 낱말을 치면 거의 늘 남는 게 없어, 결과가 올 때까지(약 0.5~0.7초) "검색할 문서가 없습니다" 그림이 번쩍였다. 입력칸의 change 이벤트로 "기다리는 중"을 세우고, 그동안의 빈 상태 자리에 결과 줄과 같은 모양의 골격을 둔다. 검색은 팔레트가 transition 안에서 부르므로 거기서 세운 상태는 결과가 온 뒤에야 보였다. 좁힌 부분 목록 자체는 팔레트의 동작이고 틀린 내용이 아니어서 그대로 둔다. 체크아웃을 브라우저에 두고 찾던 방식은 지난 변경까지 찾으려면 이력 전체를 내려받아야 해 서버 검색으로 옮겼다.

팔레트를 다루며 고친 것들이다. searchSource를 매 렌더 새로 만들면 선택 강조가 풀려 Enter가 아무것도 열지 못했으므로 한 번만 만든다. 강조가 없을 때 Enter가 죽어 있어, 입력의 keydown에서 강조가 없으면 첫 결과를 연다. 팔레트는 열릴 때와 타자마다만 검색하고 다시는 하지 않으므로, 문서를 읽기 전에 입력한 낱말이 빈 결과로 굳지 않도록 검색이 자료 도착을 기다렸다가 답한다. 디바운스로 밀린 약속은 버리지 않고 마지막 결과로 함께 끝낸다. 버리면 그 transition이 끝나지 않아 대기 표시가 계속 돌았다. 여는 목록과 검색은 큐를 나눈다. 같이 쓰면 타자가 여는 목록의 약속을 대신 답해 두 목록이 한꺼번에 보였다.

결과 영역은 22rem 고정이다. 결과 수에 맞추면 타자마다 창이 커졌다 작아졌다 했다. 읽는 중에는 결과 줄과 같은 규격의 골격을, 맞는 문서가 없으면 PageState의 검색 일러스트를 같은 자리에 둔다. 과거 시점의 본문 전문은 찾지 않는다. 필요해지면 changes 표의 전후 본문을 검색 행에 더하면 된다.

## 설정과 색 조합
<!-- gitifact-ref: R-jsncmqoqjm -->

WORKSPACE 그룹의 마지막 메뉴인 `/settings`에서 화면 모드(시스템·라이트·다크)와 색 조합을 고른다. 선택은 shared/lib/appearance가 localStorage(`gitifact-appearance`)에 저장하고 useSyncExternalStore로 구독하며, 다른 탭의 변경도 storage 이벤트로 따른다. 서버나 프로젝트에는 아무것도 보내지 않는다. 저장값이 깨져 있으면 기본값(시스템·스톤)을 쓰고 저장소를 쓸 수 없으면 그 페이지 동안만 유지한다. AppProviders가 Astryx Theme의 theme와 mode에 반영한다.

라이트 모드의 글자색은 모든 조합에서 거의 검정보다 한 단계 밝힌다(스톤 `#25252a`→`#3a3a40`, 세이지 `#3b4439`, 올리브 `#36372e`, 슬레이트 `#36415a`, 클레이 `#473b34`). 2026-09-19 사용자가 라이트 모드의 글자와 로고가 너무 어둡다고 해 SandboxHr의 값을 따랐다. 워드마크는 글자색으로 그려지므로 함께 밝아진다. 다크 모드는 그대로다. 그래서 스톤도 prebuilt 테마를 그대로 쓰지 않고 stone 소스를 extends해 글자 토큰 두 개만 바꾼다. 첫 화면은 전역 CSS가 가져오는 stone theme.css로 그려지고 바뀐 글자 토큰은 런타임에 주입된다. 나머지 조합(세이지 & 크림, 올리브 & 웜그레이, 슬레이트 & 블루, 샌드 & 클레이)은 stone 소스를 extends해 글꼴·모서리·아이콘·컴포넌트 재정의를 물려받고 색 토큰 16개만 라이트·다크 쌍으로 명시한다. 값은 Gentask의 팔레트와 hoho-hr의 Halo · Olive 토큰(OKLCH를 hex로 변환)에서 가져왔다. 강조색 하나에서 나머지를 유도하는 방식(color.accent 시드)은 기각했다. stone은 링크와 메뉴 글자가 강조색 토큰을 글자색으로 쓰기 때문에 색이 글자·메뉴·바탕 전체로 번진다. 그래서 글자용 강조 토큰(`--color-text-accent`·`--color-icon-accent`)은 조합의 글자색을 따르고, 채도 높은 강조색은 선택 표시·진행 막대·버튼에만 나타난다. 설정 카드의 미리보기는 라이트·다크 각각의 바탕·표면·강조 점·글자 선을 축소판으로 그린다.

## 문서 링크

문서 링크는 원문을 두고 렌더링 때 번역한다. `resolveDocumentLink.ts`가 문서의 저장소 경로(`from`)와 링크로 대상을 계산한다. 스킴이 있거나 `//`로 시작하면 외부(새 탭, noopener), `#`만 있으면 페이지 안 앵커, `/`로 시작하면 앱 경로다. 그 밖은 `from`의 폴더 기준으로 `.`·`..`를 풀어 저장소 상대 경로를 만들고, 위키 페이지 경로와 같으면 `/wiki/$documentId`, `spec/<기능>/requirements.md`·`design.md`면 `/features/$featureId`의 해당 탭, `.gitifact/assets/` 아래면 `/api/v1/assets/<인코딩한 경로>`로 바꾼다. 저장소 루트 위로 올라가거나 그 밖의 저장소 파일이면 "브라우저 밖" 상태다. href 없는 Astryx Link를 흐린 색과 점선 밑줄로 그리고 Tooltip을 붙이며, 클릭하면 clipboard에 저장소 경로를 복사하고 toast로 알린다. 대상이 없는 페이지·기능은 취소선 Text와 툴팁이다(비활성 button은 hover가 없어 툴팁이 뜨지 않아 링크 모양을 쓰지 않았다). 이미지는 같은 규칙으로 src를 바꾸고 해석되지 않으면 대체 텍스트만 보인다. 문서 경로는 `DocumentBody`의 `path`로 받아 context에 두고, `DocumentIndexProvider`가 첫 명세 응답의 페이지·기능 목록을 제공한다. 서버는 `.gitifact` 밖 파일을 제공하지 않는다.

설계 탭은 `sources`가 있으면 본문 위에 "참고 문서" 목록을 compact List로 그린다. 제목이 링크(위키 경로는 같은 해석 규칙, url은 새 탭)이고 설명에 note와 호스트 또는 상대 경로를 둔다. 카드 대신 행으로 둔 것은 디자인 시스템 지침의 조밀한 자료 규칙을 따른 것이다.

## 시작하기 안내

GITIFACT 메뉴에서 소개 다음에 `/getting-started`를 둔다. `pages/getting-started`는 소개와 같은 64rem 중앙 컬럼, PageHeader와 DocumentBody를 사용한다. 페이지 제목은 화면 문구 카탈로그에서 읽고 Markdown의 최상위 제목은 표시할 때 제거해 중복하지 않는다. 소개의 GitHub CLI 안내 링크는 앱 안에서 이 경로로 연결한다.

한국어·영어 원본은 `packages/intro/<lang>/getting-started.md`다. packages/intro의 공개 export를 shared/i18n이 가져와 localDocument로 제공한다. 소개와 같은 언어별 문서 방식으로 번들하므로 별도 HTTP 조회나 명세 저장소에 의존하지 않는다. 현재 CLI 도움말·내장 지침으로 확인한 사용 흐름을 한국어로 작성한 뒤 영어판을 만들었으며 npm README도 영어 원문과 일치시킨다. 입력 JSON의 상세 형식은 복제하지 않고 docs spec·commit으로 안내한다.

메뉴 순서, 소개 링크, 키보드 이동, 직접 진입·새로고침과 모바일 두 테마를 검사한다. 명세가 없는 임시 Git 저장소에서도 실제 CLI 서버가 안내를 제공하는지 확인한다.
