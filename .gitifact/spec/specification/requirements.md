# 기능 명세 관리

## 기능별 Markdown 명세
<!-- gitifact-req: R-errzmn5edh -->

프로젝트 참여자로서, 작업할 기능의 요구사항과 구현 방향을 함께 이해하기 위해 관련 명세를 기능별 Markdown 문서로 읽고 관리하고 싶다.

### 범위와 제약

관련 요구사항을 응집된 기능별 requirements.md로 정리한다. 코드 모듈이나 DDD 계층을 강제하지 않는다. 구현 설계는 같은 기능의 design.md에 정리하며 작업 문서는 현재 MVP 대상이 아니다.

### 수용 조건

1. 조건: 관련된 기능 요구사항이 추가됩니다.
   기대 동작: 기존 명세에 적합하면 함께 정리하고, 별도 기능이면 새 명세를 만듭니다. docs/specs에 중복 원본을 만들지 않습니다.

## 경로와 독립적인 식별자
<!-- gitifact-req: R-fypnjx6dju -->

프로젝트 참여자로서, 문서가 재구성돼도 같은 요구사항의 맥락을 잃지 않기 위해 제목이나 소속 기능이 바뀐 요구사항을 동일한 식별자로 추적하고 싶다.

### 범위와 제약

명세는 S-난수, 요구사항은 R-난수로 식별하며 난수는 소문자 base32 10자다. 기능 이름을 요구사항 ID에 포함하지 않는다.

### 수용 조건

1. 조건: 같은 요구사항의 제목이나 소속 기능이 바뀝니다.
   기대 동작: R-ID를 유지하고 새 위치에서도 같은 요구사항으로 추적합니다. 다른 요구사항에 ID를 재사용하지 않습니다.

## 읽기 쉬운 수용 조건
<!-- gitifact-req: R-obomewrs7e -->

프로젝트 참여자로서, 누구에게 왜 필요한 기능이며 어떤 결과를 충족해야 하는지 이해하기 위해 사용자 스토리와 읽기 쉬운 수용 조건으로 요구사항을 확인하고 싶다.

### 범위와 제약

요구사항은 제목·본문과 조건 및 기대 동작으로 표현한다. 현재 frontmatter는 사용하지 않는다.

### 수용 조건

1. 조건: 사용자가 요구사항 내용을 확인합니다.
   기대 동작: 기술적 JSON 구조 대신 제품 동작과 일반 텍스트 수용 조건을 읽을 수 있습니다.

2. 조건: 에이전트가 요구사항을 새로 작성하거나 요청받은 요구사항을 개정합니다.
   기대 동작: 수용 조건 앞에 실제 사용자 역할·목표·이유를 담은 사용자 스토리를 작성합니다. 수용 조건은 기존 조건·기대 동작 형식을 유지하며, 근거 없는 역할이나 동기를 만들어 넣지 않습니다. 기존 ID와 확정된 제약을 보존합니다.

## 유효한 저장과 오류 보존
<!-- gitifact-req: R-uvehohexvw -->

명세를 관리하는 사용자로서, 기록의 손상이나 다른 작업의 유실을 막기 위해 잘못되거나 오래된 입력은 저장 전에 거부되고 그 원인을 확인할 수 있기를 원한다.

### 범위와 제약

CLI는 ID·형식·참조와 원문 상태를 검사한다. 조회 오류나 손상을 빈 정상 결과로 처리하지 않는다.

### 수용 조건

1. 조건: 명세에 충돌한 ID·손상·오래된 저장 입력이 있습니다.
   기대 동작: 저장을 거부하고 원인을 알립니다. 다른 작업·원문을 덮어쓰거나 없는 요구사항을 만들어 성공으로 표시하지 않습니다.

## 기능별 구현 설계
<!-- gitifact-req: R-hbz77tj5kc -->

프로젝트 참여자로서, 요구사항을 어떻게 구현할지 이해하고 변경 시 영향을 판단하기 위해 기능별 요구사항과 연결된 구현 설계를 함께 읽고 관리하고 싶다.

### 범위와 제약

기능의 여러 요구사항을 구현하는 구조와 처리 방식을 같은 폴더의 design.md에 정리한다. 설계는 동일한 S-ID를 사용하며 별도 문단 ID를 발급하지 않는다.

### 수용 조건

1. 조건: 에이전트가 새 기능 명세를 작성합니다.
   기대 동작: 요구사항과 설계를 함께 작성하는 것을 기본으로 하며 단계별 승인을 강제하지 않습니다. 사용자가 요구사항만 요청하거나 기존 명세에 설계가 없으면 그대로 허용합니다. 빈 설계를 자동 생성하지 않습니다.

2. 조건: 에이전트가 설계를 작성하거나 개정합니다.
   기대 동작: 개요·구조와 데이터·처리 흐름·오류 처리와 검증·주요 결정·미결 사항 중 필요한 절을 사용합니다. 기존 설계의 영향받는 부분을 갱신하고 확정된 내용과 제안을 구분합니다. 관련 실제 R-ID를 연결하며 잘못된 참조 문법은 거부하고 현재 없는 참조는 경고합니다.

3. 조건: 설계를 저장·삭제하거나 기능 폴더가 바뀝니다.
   기대 동작: 저장·삭제는 명세 보호 절차를 따르고 같은 S-ID의 설계는 같은 문서로 추적합니다. tasks.md는 아직 관리하지 않습니다.

## 설계의 참고 문서 목록
<!-- gitifact-req: R-vaw2ychvkd -->

설계를 쓰는 에이전트와 읽는 참여자로서, 설계가 어떤 위키 페이지와 외부 자료에 근거했는지 한눈에 보기 위해 참고 문서를 본문 곳곳의 링크가 아니라 목록으로 관리하고 싶다.

### 범위와 제약

참고 문서는 design.md frontmatter의 `sources` 목록이다. 항목마다 `title`과 `path`(위키 페이지로 가는 상대 경로) 또는 `url` 중 하나, 선택적 `note`를 둔다. 외부 페이지의 제목이나 미리보기는 가져오지 않는다.

### 수용 조건

1. 조건: 설계를 저장하며 sources를 전달합니다.
   기대 동작: frontmatter에 기록되고 `spec working`이 함께 반환합니다. 형식이 맞지 않으면 저장을 거부합니다.
2. 조건: sources의 path가 없는 페이지를 가리킵니다.
   기대 동작: `MISSING_LINK_TARGET` 경고를 내고 저장은 진행됩니다.
3. 조건: 브라우저에서 설계 탭을 봅니다.
   기대 동작: 참고 문서가 카드 목록으로 보이고 위키 항목은 해당 페이지로, 외부 항목은 새 탭으로 연결됩니다.
