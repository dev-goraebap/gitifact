프로젝트 참여자로서, 요구사항을 어떻게 구현할지 이해하고 변경 시 영향을 판단하기 위해 기능별 요구사항과 연결된 구현 설계를 함께 읽고 관리하고 싶다.

### 범위와 제약

기능의 여러 요구사항을 구현하는 구조와 처리 방식을 같은 기능 폴더의 `design/` 아래에 정리한다. 설계는 관점마다 파일을 두고 파일마다 D-ID를 가지며, 설계가 하나라도 있으면 `overview.md`가 있어야 한다. 파일 안의 문단에는 별도 ID를 발급하지 않는다.

### 수용 조건

1. 조건: 에이전트가 새 기능 명세를 작성합니다.
   기대 동작: 요구사항과 설계를 함께 작성하는 것을 기본으로 하며 단계별 승인을 강제하지 않습니다. 사용자가 요구사항만 요청하거나 기존 명세에 설계가 없으면 그대로 허용합니다. 빈 설계를 자동 생성하지 않습니다.

2. 조건: 에이전트가 설계를 작성하거나 개정합니다.
   기대 동작: 개요(overview)·데이터·인터페이스·화면·오류 중 필요한 관점의 파일을 사용하고, 작은 기능은 개요 하나로 둡니다. 기존 설계의 영향받는 파일을 갱신하고 확정된 내용과 제안을 구분합니다. 파일이 설명하는 실제 R-ID를 프론트매터에 연결하며, 잘못된 참조 문법과 없는 요구사항을 가리키는 참조는 검사에서 거부합니다.

3. 조건: 설계 파일을 옮기거나 나누거나 지우고, 기능 폴더 이름이 바뀝니다.
   기대 동작: 같은 D-ID의 파일은 같은 문서로 추적하고, 지운 파일은 이력에 제거로 남습니다. tasks.md는 아직 관리하지 않습니다.
