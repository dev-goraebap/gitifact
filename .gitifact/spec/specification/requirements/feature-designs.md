프로젝트 참여자로서, 요구사항을 어떻게 구현할지 이해하고 변경 시 영향을 판단하기 위해 기능별 요구사항과 연결된 구현 설계를 함께 읽고 관리하고 싶다.

### 범위와 제약

- 기능의 여러 요구사항을 구현하는 구조와 처리 방식은 같은 기능 폴더의 `design/` 아래에 둔다.
- 설계는 관점마다 파일을 두고 파일마다 D-ID를 가진다. 파일 안의 문단에는 별도 ID를 발급하지 않는다.
- 설계가 하나라도 있으면 `overview.md`가 있어야 한다.
- 새 기능은 요구사항과 설계를 함께 쓰는 것이 기본이지만 단계별 승인을 강제하지 않고, 빈 설계를 자동으로 만들지 않는다.
- 본문에는 고른 결과만 규칙으로 쓰고, 결정의 맥락과 검토한 대안, 바뀐 경위는 결정기록에 둔다.
- tasks.md는 아직 관리하지 않는다.

### 기본 흐름

1. 에이전트가 새 기능의 요구사항을 쓴다.
2. 에이전트가 개요(overview)·데이터·인터페이스·화면·오류 중 필요한 관점의 설계 파일을 쓴다. 작은 기능은 개요 하나로 둔다.
3. 에이전트가 파일마다 그 파일이 설명하는 실제 R-ID를 프론트매터에 잇는다.
4. 에이전트가 확정된 내용과 제안을 구분해 쓰고 `check`로 확인한다.

### 대체 흐름

- **A1. 사용자가 요구사항만 요청하거나 기존 명세에 설계가 없음** (2단계에서)
  1. 에이전트는 설계 없이 요구사항만 둔다.
- **A2. 기존 설계를 개정함** (2단계에서)
  1. 에이전트가 먼저 그 설계의 결정기록을 읽는다.
  2. 덧붙이기 전에 파일 나누기와 그림 기준을 문서 전체에 다시 대조한다.
  3. 영향받는 파일을 고치고, 고른 맥락과 대안은 결정기록에 남긴다.
- **A3. 설계가 나눌 만큼 커짐** (A2의 2단계에서)
  1. 에이전트가 옮기기만 하는 커밋으로 먼저 나눌지 사용자에게 묻는다.
  2. `overview.md`에 `##` 절이 7개 이상이면 `check`와 `changes list`가 나눌지 검토하라는 경고를 보인다. 종료 코드와 커밋은 막지 않는다.
- **A4. 참조가 잘못됨** (4단계에서)
  1. 잘못된 참조 문법이나 없는 요구사항을 가리키는 참조를 `check`가 거부한다.
- **A5. 설계 파일을 옮기거나 나누거나 지우거나, 기능 폴더 이름이 바뀜** (4단계 뒤)
  1. 같은 D-ID의 파일은 같은 문서로 추적한다.
  2. 지운 파일은 이력에 제거로 남는다.

### 수용 조건

1. 경로: 기본 흐름
   조건: 에이전트가 새 기능 명세를 작성합니다.
   기대 동작: 요구사항과 필요한 관점의 설계를 함께 쓰고, 파일마다 설명하는 R-ID를 프론트매터에 잇습니다.
2. 경로: 기본 흐름, A1
   조건: 사용자가 요구사항만 요청하거나 기존 명세에 설계가 없습니다.
   기대 동작: 그대로 허용하고 빈 설계를 자동 생성하지 않습니다.
3. 경로: 기본 흐름, A2
   조건: 에이전트가 기존 설계를 개정합니다.
   기대 동작: 먼저 그 설계의 결정기록을 읽고, 영향받는 파일을 갱신하며, 본문에는 고른 결과만 쓰고 맥락과 대안은 결정기록에 남깁니다.
4. 경로: 기본 흐름, A2, A3
   조건: 설계의 `overview.md`에 `##` 절이 7개 이상 있습니다.
   기대 동작: `check`와 `changes list`가 나눌지 검토하라는 경고를 보이고, 종료 코드와 커밋은 막지 않습니다. 에이전트는 덧붙이기 전에 나눌지 사용자에게 묻습니다.
5. 경로: 기본 흐름, A4
   조건: 설계가 잘못된 문법으로 요구사항을 참조하거나 없는 요구사항을 가리킵니다.
   기대 동작: `check`가 문제로 알리고 커밋을 거부합니다.
6. 경로: A5
   조건: 설계 파일을 옮기거나 나누거나 지우고, 기능 폴더 이름이 바뀝니다.
   기대 동작: 같은 D-ID의 파일은 같은 문서로 추적하고, 지운 파일은 이력에 제거로 남습니다.
