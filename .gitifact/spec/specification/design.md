# 기능 명세 관리 설계

## 개요

기능별 현재 요구사항과 구현 설계를 Markdown으로 관리한다. 순수 형식·편집 규칙은 packages/core에, 파일 접근과 잠금·복구는 CLI 어댑터에 둔다. Git 연결은 Git 기록 연결 설계에서 다룬다.

## 구조와 데이터
<!-- gitifact-ref: R-errzmn5edh, R-fypnjx6dju, R-obomewrs7e -->

.gitifact/spec/<기능>/에 requirements.md, 선택적인 design.md, 변경 이유가 생겼을 때 history.jsonl을 둔다. 별도 요구사항 목록이나 docs/specs 복사본은 만들지 않는다.

requirements.md는 첫 줄의 gitifact-spec 주석에 S-ID를, 각 요구사항 제목 아래 gitifact-req 주석에 R-ID를 둔다. 최상위 제목은 문서 이름이고 요구사항은 제목·본문·수용 조건으로 구성한다. 본문은 사용자 역할·목표·이유를 담은 사용자 스토리로 시작한다. 필요한 확정 제약은 별도 범위와 제약 절에 보존한다. 조건과 기대 동작은 기존 일반 텍스트 형식을 유지한다. `gitifact docs spec`이 작성 방식을 안내하며 CLI는 사용자 스토리의 문형이나 의미를 검사하지 않는다. frontmatter는 사용하지 않는다.

ID는 CLI가 발급하는 소문자 base32 10자다. 이름·폴더와 독립적이며 이동·개명에도 유지한다. 이름 변경을 다른 요구사항 생성으로 처리하지 않는다.

## 설계 문서
<!-- gitifact-ref: R-hbz77tj5kc -->

design.md의 gitifact-design 주석은 소유 기능의 S-ID와 일치해야 한다. 최상위 제목과 비어 있지 않은 본문을 저장하며 개요·구조와 데이터·처리 흐름·오류 처리와 검증·주요 결정·미결 사항 중 필요한 절을 쓴다.

관련 절은 gitifact-ref 주석으로 실제 R-ID를 참조한다. 참조는 현재 전체 명세에서 찾아 다른 기능으로 이동한 요구사항에도 연결할 수 있다. 코드 블록의 예시는 참조로 해석하지 않는다. 설계의 현재 문서 전체가 비교 단위이며 별도 문단 ID는 없다. tasks.md는 지원하지 않는다.

## 저장 흐름
<!-- gitifact-ref: R-uvehohexvw -->

1. spec working으로 전체 명세와 stamp, 참조 경고를 읽는다.
2. spec save에 expected stamp와 create·add·update·move·rename-spec·set-design·delete-design 중 필요한 작업을 전달한다.
3. core는 입력과 편집 결과를 검증한다. 파일 어댑터는 잠금 아래 기존 stamp를 대조하고 실제로 바뀐 파일만 반영한다.
4. CLI는 변경 경로·발급 ID·새 stamp와 경고를 반환한다. 저장은 커밋이나 완료 선언을 만들지 않는다.

create·add·set-design을 한 요청에 담을 수 있다. 아직 발급되지 않은 R-ID를 설계에 지어내지 않고 반환 결과로 후속 참조를 보완한다. 전용 요구사항 삭제·폴더 개명 작업은 아직 없다.

## 오류 처리와 검증

중복 ID, 잘못된 주석, 소유 ID 불일치, 요구사항 없는 설계, 오래된 입력, 링크·특수 파일과 한도 초과를 거부한다. 현재 없는 설계 참조는 경고해 삭제 이후 원문 조회를 막지 않는다. 저장 중 실패하면 자신의 변경을 복원하되 외부 편집이 확인되면 보존하고 복구 자료를 남긴다. 다중 파일의 강제 종료 후 자동 복구는 보장하지 않는다.

형식 고정 자료와 독립 저장소로 파싱·편집·이동·충돌·실패 복구를 검사한다. 명세 구조가 유효하다는 결과를 제품 의미나 코드 구현의 검증으로 해석하지 않는다.

## 주요 설계 결정

기능 응집은 사용자의 제품 맥락으로 정하고 코드 모듈 구조를 강제하지 않는다. 설계는 기본 작성 대상으로 안내하되 빈 파일 생성을 강제하지 않는다. 현재 문서만 저장하고 과거 원문은 Git에서 읽어 중복 스냅샷을 줄인다.
