# Gitifact

![GITIFACT](./gitifact-logo.svg)

Gitifact는 에이전트와 제품을 만드는 대화가 요구사항과 결정의 기록으로 이어지게 하는 도구다. 사용자는 평소처럼 에이전트와 무엇을 만들지 고민하고, 구현하고, 고쳐 나간다. 그 과정에서 요구사항과 변경 이유가 Git에 쌓이고, 사람과 에이전트가 같은 기록을 보며 제품의 상태를 이해한다.

## 누구를 위한 것인가

개인이나 팀이 하나의 Git 저장소 안에서 제품을 만드는 환경을 전제로 한다. CLI, 데스크톱 앱, VS Code 어디에서 에이전트와 대화하든 익숙한 방식으로 제품을 만들 수 있어야 한다. 개발자뿐 아니라 로컬 에이전트와 대화하며 제품을 만드는 비개발자와 바이브 코더도 같은 대상이다.

사용자는 별도의 개발 방법론이나 기록 명령을 배우지 않는다. 스펙 주도 개발과 AI-Native SDLC의 기본 원리를 따르되, 그 개념을 먼저 공부하거나 정해진 절차에 익숙해져야 시작할 수 있는 흐름은 만들지 않는다.

## 어떻게 쓰이는가

1. 새 프로젝트는 처음 아이디어를 나누는 대화부터 시작한다. 에이전트가 요구사항과 구현 설계를 함께 정리하고 불명확한 제품 동작만 질문한다.
2. 기존 프로젝트는 도입한 시점부터 기록을 쌓는다. 유지보수하거나 기능을 추가하면서 해당 영역의 요구사항을 정리한다. 과거 전체를 먼저 문서화하지 않아도 된다.
3. 사용자는 작업할 영역을 토론하고 구현하고 테스트한 뒤 커밋을 요청한다. 에이전트는 그동안 현재 명세를 다듬는다.
4. 커밋 시점에 작업 범위와 최종 명세를 대조하고 의미 있는 변경과 이유를 남긴다. 영구 이력의 기준은 Git에 커밋된 명세다.
5. 읽기 전용 브라우저에서 활동, 제품 기능, 지침, 참여자를 살펴본다. 사람에게는 제품을 만드는 흐름이, 에이전트에게는 다음 작업을 이어갈 근거가 남는다.

## 원칙

- 제품에 집중한다. 사용자가 매번 기록할 항목과 명령을 지정하지 않아도 필요한 맥락이 남아야 한다.
- 커밋된 명세가 기준이다. 초안의 모든 수정 과정을 따로 보존하지 않고 Git에 남은 버전에서 과거 내용과 변경 전후를 읽는다.
- 자동 기록은 자동 커밋·푸시 권한이 아니다. 커밋 시점·메시지·브랜치·서명은 사용자 요청과 프로젝트 정책을 따른다.
- 외부 서비스 없이 로컬에서 동작한다. 브라우저는 읽기 전용이며 구현 완료를 자동 판정하지 않는다.
- 같은 커밋에 코드가 있다는 사실, 구현 완료, 테스트 통과는 각각 다른 사실이다. 추정과 사용자 의도, 현재 구현과 계획을 구분한다.
- 기존 프로젝트의 기록·설정·에이전트 지침을 임의로 덮어쓰거나 재해석하지 않는다.

## 범위 밖

- 하나의 제품을 여러 저장소로 나눈 멀티 레포의 통합 요구사항 관리. 저장소 사이의 상태 동기화가 필요해지고 프로젝트 안에서 단순하게 기록을 관리하려는 방향과 멀다.
- PR·이슈 트래커 연동, 승인 절차, note 같은 별도 판단 기록 화면, 브라우저 편집, 전체 훅·감사 체계.
- 특정 docs 폴더를 요구하거나 문서를 그대로 옮기는 기능. Gitifact는 대화와 맥락에서 요구사항을 도출한다.

## 용어

| 용어 | 뜻 |
| :--- | :--- |
| 기능 명세 | 기능 하나의 요구사항(requirements.md)과 구현 설계(design.md) |
| 요구사항 | 유지해야 할 제품 동작과 제약. 제목·본문·수용 조건으로 쓴다 |
| 변경 이유 | 커밋 시점에 요구사항·설계·문서 ID에 연결해 남기는 이유 |
| 활동 | 커밋된 명세와 문서의 추가·변경·이동·제거 이력 |
| 참여자 | Git author 기준의 사람. 요청자나 승인자를 뜻하지 않는다 |
| 제품 개요 | 이 문서. 제품이 무엇이고 누구를 위한 것이며 어떤 원칙을 갖는지 |
| 지침 | 구현 방식을 정하는 아키텍처·코드 규칙 문서 |

## 이름과 표기

제품 이름은 Gitifact, 명령과 패키지는 `gitifact`다. 화면의 워드마크는 대문자 GITIFACT를 쓴다. 이전 이름 Tryce는 과거 기록에만 남는다.
