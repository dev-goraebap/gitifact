공통 문체는 CLI 내장 지침 `gitifact guide show writing`이다. 모든 프로젝트에 해당하는 규칙은 그쪽에 두고 여기에 다시 적지 않는다. 이 지침에는 이 저장소에만 해당하는 것을 둔다.

- 날짜별 작업·검증·배포 기록은 지침과 명세에 두지 않는다. 그것은 [개발 환경](../../../docs/development.md)과 Git 이력의 몫이다. 문서가 바뀐 경위와 결정의 맥락·검토한 대안은 결정기록에 둔다(`pnpm cli guide show records`).
- 긴 문서를 다시 쓸 때는 옛 본문의 사실(경로·명령·수치·규칙·결정)을 목록으로 뽑아 새 본문이나 결정기록에 남았는지 대조한다. 뺀 것이 경위뿐인지 확인하고, 결정기록에 아직 없는 경위는 그 변경의 결정기록에 요지를 적는다.
- 지침은 명세(요구사항·설계·기능 소개)를 링크하지 않는다. 방향은 설계가 `sources`로 지침을 가리키는 쪽 하나이고, `docs check`가 지침의 명세 링크를 `INSTRUCTION_SPEC_LINK`로 막는다. 지침에는 여러 기능에 걸쳐 지키는 규칙을 두고, 한 기능의 사정은 그 기능의 설계에 둔다.
- 제품 이름은 Gitifact, 저장 경로는 `.gitifact`로 쓴다. 과거 이름 Tryce와 `.tryce`는 과거 기록을 설명할 때만 쓴다.
- 에이전트 지침의 원본은 `apps/cli/src/shared/i18n/<lang>/docs/`다. 모든 프로젝트에 적용할 규칙을 프로젝트 지침에 적지 않고 그 파일에 적는다.
- 제품의 목적·원칙·범위는 루트 README(원본은 `packages/intro`)에, 구현 규칙과 결정은 영역별 프로젝트 지침(`.gitifact/instructions/`)에 두고, 언제 무엇을 읽을지는 AGENTS.md에 적는다.

## 설계 문서

기능별 요구사항은 원하는 동작과 수용 조건을, 설계는 구현 구조와 처리 방식을 설명한다. 설계의 축, 프론트매터, 파일 나누기, 결정기록과의 구분, 다이어그램, 개정 방식은 CLI 지침 `pnpm cli guide show design`을 따르고 여기에 다시 적지 않는다. 지침 원본은 `apps/cli/src/shared/i18n/<lang>/docs/design.md`다.

새 기능을 정리할 때 에이전트는 요구사항과 설계를 함께 쓴다. 단계별 승인을 강제하지 않고 중요한 불명확함만 질문한다. CLI는 빈 설계를 만들지 않으며, 사용자가 요구사항만 요청하거나 기존 기능에 설계가 없으면 그대로 둔다. tasks 문서는 다루지 않는다. CLI는 형식과 참조의 존재만 검사하고 설계 내용의 타당성은 판정하지 않는다.

본문이 약 1만 자를 넘고 한 관점이 여러 절인 기능만 축 파일로 나누고, 나머지는 `overview.md` 하나로 둔다. 작은 기능을 나누면 두 문단짜리 파일이 생기고 읽는 사람이 파일 사이를 여러 번 옮겨 다닌다. 어느 기능이 나뉘었는지는 `docs list`로 본다.
