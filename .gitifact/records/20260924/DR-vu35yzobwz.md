## 맥락

요구사항이 파일 하나씩으로 나뉘자 CLI도 목록·검색·역참조·문서 이력을 빠르게 답해야 했다. 합성 자료로 재니 캐시 없이 문서 1,000개 목록 896ms·5,000개 4.0초였고 캐시로 124ms·323ms였다. 역참조와 이력은 Git 프로세스를 띄워야 해 어차피 캐시가 필요했다. 대가는 worktree마다 처음 한 번 다시 읽는 것(이 저장소 2.85초)과, 5,000개 기준 첫 생성 22초·원문의 약 3.5배 크기(본문 trigram 색인, 줄이는 방법 미결)다.

## 결정

CLI와 브라우저 서버가 캐시 `.gitifact/cache/index.db` 하나를 함께 쓴다. `node:sqlite`로 열고 두 프로세스가 동시에 쓸 수 있도록 WAL 모드를 쓴다. 문서·참조·검색 색인·커밋별 변경을 두고, 명령마다 수정 시각·크기가 바뀐 문서와 새 커밋만 다시 읽는다. 옛 색인 `.git/gitifact/index.sqlite`는 CLI가 지우지 않고 전환 절차가 지우라고 안내한다.

## 검토한 대안

- 캐시 없이 매번 파일 읽기(문서 수에 비례해 느려지고 역참조·이력은 Git 호출이 필요함)
- `.git/gitifact/index.sqlite` 색인(브라우저 이력만 담던 옛 결정)
