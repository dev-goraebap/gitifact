상태: Accepted · 2026-09-22 · 결정 0001을 대체

## 맥락

0.7까지는 기능마다 `requirements.md`와 `design.md` 한 파일에 요구사항과 설계를 모두 담고, 요구사항 ID는 `##` 제목 아래 HTML 주석(`gitifact-req`)으로, 설계 절과 요구사항의 짝은 `gitifact-ref` 주석으로 적었다(결정 0001). 구조 정보를 본문 주석에서 뽑아야 해서 파서가 제목·주석의 위치에 묶였고, 저장은 `spec save`가 stamp를 대조해 파일을 대신 써 주는 방식이라 에이전트가 파일을 직접 고칠 수 없었다. 에이전트가 필요한 요구사항 하나를 읽으려 해도 기능 파일 전체를 열어야 했고, 기능이 커지면 설계 한 파일이 4만 자를 넘었다. 이유는 기능 폴더·위키마다 `history.jsonl`에 흩어져, 요구사항을 다른 기능으로 옮기거나 여러 폴더에 걸친 이유를 남길 때 어느 파일에 둘지가 모호했다.

SQLite를 원본으로 두는 안도 시험했다. 바이너리 DB는 커밋마다 통째로 저장되고, 병합에 레코드 단위 병합 도구가 따로 필요하며, diff가 보이지 않아 기각하고 시험 커밋에서 지웠다.

## 결정

- **문서 하나가 파일 하나다.** 기능 폴더 `.gitifact/spec/<기능>/`에 소개 `index.md`(S-), 요구사항 `requirements/<slug>.md`(R-), 설계 `design/<slug>.md`(D-, 관점별 파일, `overview.md` 필수)를 둔다. 위키는 그대로 `.gitifact/wiki/**/*.md`(W-)다.
- **구조 정보는 프론트매터에만 둔다.** `id`·`title`·`description`은 모든 문서에 필수이고, 요구사항·설계는 `order`, 설계는 `requirements`·`sources`를 가진다. 소속은 폴더로 정한다. 본문은 산문이며 CLI가 파싱하지 않고, `#` 제목과 gitifact 주석을 쓰지 않는다.
- **파일은 에이전트가 직접 고친다.** 저장 명령은 없다. ID는 `docs new`만 발급하고, 형식은 `docs check`와 커밋 직전의 같은 검사가 확인한다.
- **이유는 `.gitifact/history.jsonl` 한 파일에 둔다.** 한 줄이 `{id, docs, reason}`이며 `changes commit`만 줄을 더한다. 두 브랜치가 줄을 더해도 둘 다 남도록 `merge=union`을 쓴다. 파일은 10MB(약 25,000줄)를 넘으면 나누기를 다시 검토한다(6,300줄 2.3MB를 13ms에 읽는다).
- **형식 번호는 schemaVersion 3이다.** 0.7(schemaVersion 2) 프로젝트는 CLI가 변환하지 않고 에이전트가 `guide show migrate`의 절차로 옮긴다. 옛 ID와 이유 문장은 그대로 옮겨 적고, 전환 커밋에 `Gitifact-Migration: 0.8.0` 트레일러를 붙인다. 그 이전 이력은 1.0.0까지 남기는 0.7 파서로 읽는다.

## 결과

에이전트는 `docs list`로 제목·설명만 보고 필요한 파일만 연다. 요구사항을 옮기거나 제목을 바꾸면 파일 이동·수정일 뿐이고 ID가 이어 준다. 형식 규칙이 프론트매터와 경로에만 있어 검사가 단순하다. 대가는 파일 수가 늘고(이 저장소는 기능 9개에 요구사항 파일 45개, 설계 파일 19개), 설계 절과 요구사항의 짝이 파일 단위로 굵어진 것, "읽은 뒤 바뀌었으면 저장 거부" 같은 저장 명령의 보호가 없어져 일반 코드 파일과 같은 수준이 된 것, 기존 프로젝트가 한 번 옮겨야 하는 것이다.

이유를 파일에 두는 방식은 커밋 메시지·git notes·별도 ref·고아 브랜치·Change-Id와 비교해 고른 것이다. 파일은 GitHub squash 병합에서 메시지를 고치거나 PR 제목만 쓰는 설정이어도 남고, 일반 clone에 따라온다. 기각: 커밋 메시지 트레일러(squash·편집으로 사라지고 CLI가 막을 수 없음), git notes(기본으로 push·fetch되지 않고 squash에서 사라짐), 별도 ref(기본 clone에 받아지지 않아 전용 동기화가 필요함), 고아 브랜치(코드 커밋과 이어지지 않음), Change-Id(squash에서 끊김). 이유마다 파일을 두는 조각 파일 방식은 병합 규칙과 크기 문제가 없지만 파일 수가 늘고 읽기·쓰기를 다시 만들어야 해 보류했다. 얕은 clone은 어느 방식이든 이력이 없으므로 감지해 알리는 것으로 대응한다(미구현).

그 밖에 기각한 안: 요구사항 여러 개를 한 파일에 두고 프론트매터 목록으로 나누기(제목과 ID의 대응을 따로 유지해야 함), 파일 이름을 ID로 쓰기(사람이 읽는 slug를 택함), 기능 소속을 `part_of` 같은 관계 필드로 적기(폴더와 어긋날 수 있음).
