상태: Accepted · 2026-09-22 · 결정 0009를 대체

## 맥락

결정 0009는 브라우저 이력을 `<git 공용 폴더>/gitifact/index.sqlite`에 색인으로 두었다. 0.8.0에서 요구사항이 파일 하나씩으로 나뉘자(결정 0010) CLI도 목록·검색·역참조·문서 이력을 빠르게 답해야 했다. 이 저장소 문서를 0.8.0 구조로 옮겨 복제한 합성 자료로 재어 보니, 캐시 없이 프론트매터만 읽어도 문서 1,000개에서 목록 896ms, 5,000개에서 4.0초였고, 캐시를 쓰면 124ms와 323ms였다. 역참조와 문서 이력은 Git 프로세스를 띄워야 하므로 어차피 캐시가 필요했다.

## 결정

CLI와 브라우저 서버가 캐시 파일 하나 `.gitifact/cache/index.db`를 함께 쓴다. Node 24 내장 `node:sqlite`로 열고, 두 프로세스가 동시에 쓸 수 있도록 WAL 모드를 쓴다. 캐시에는 문서의 프론트매터·경로·수정 시각과 크기, ID 참조와 역참조, 본문 검색 색인, 커밋별 변경 기록과 변경 전후 본문을 둔다. 명령마다 수정 시각·크기가 바뀐 문서와 새 커밋만 다시 읽는다.

캐시는 파생물이다. 원본은 문서 파일과 Git이며, 캐시를 지우거나 형식 번호가 다르거나 손상되면 다시 만든다. 캐시를 처음 여는 명령이 폴더 안에 내용이 `*`인 `.gitignore`를 만들어 커밋에서 빼고, 사용자 저장소의 루트 `.gitignore`는 건드리지 않는다. 같은 커밋의 소스 파일 목록은 형식 번호를 바꾸지 않도록 캐시에 넣지 않고 서버 메모리에 200커밋까지 둔다. 옛 색인 `.git/gitifact/index.sqlite`는 CLI가 지우지 않고 전환 절차가 지우라고 안내한다.

## 결과

목록·검색이 문서 수백 개를 넘어도 0.1~0.3초 안에 답하고, CLI와 브라우저가 같은 결과를 본다. 대가는 worktree마다 캐시가 따로라 새 worktree에서 이력을 처음 한 번 다시 읽는 것과, 처음 만드는 비용이다. 캐시가 빈 상태의 첫 이력 조회는 이 저장소에서 2.85초다(0.7 트리를 배치로 읽도록 고치기 전 8.6초). 합성 자료 5,000개의 문서 캐시는 처음 만드는 데 22초가 걸렸고 크기가 원문의 약 3.5배였다. 원인은 본문 trigram 색인이며 줄이는 방법은 미결이다.

위치는 0.8.0 초안의 `.gitifact/cache/index.db`를 그대로 따랐다. 기각: 캐시 없이 매번 파일 읽기(문서 수에 비례해 느려지고 역참조·이력은 Git 호출이 필요함).
