## 맥락

브라우저의 활동 화면은 이력을 페이지로 나눠 받고, 받은 범위 안에서만 거르고 셌다. 필터가 아직 불러오지 않은 변경을 찾지 못했고, 건수도 받은 범위의 건수였다. 이력을 읽는 비용이 커밋마다 저장소 전체를 두 번 읽는 것이라 처음부터 전체를 읽을 수도 없었다. 커밋이 바꾼 파일만 읽게 바꾸면서 전체를 읽는 비용이 명세 커밋 수에 비례하는 작은 값이 됐고(명세 커밋 37개에 약 0.5초), 사용자는 git을 쓰더라도 화면은 DB를 쓸 때처럼 전체를 대상으로 검색·필터·페이징해야 한다고 했다.

## 결정

이력은 로컬 SQLite 색인에 두고 서버가 거르고 세고 찾는다. 파일은 `<git 공용 폴더>/gitifact/index.sqlite`이고 Node 24 내장 `node:sqlite`로 연다. 커밋의 변경은 한 번 읽어 영구히 두고, HEAD마다 커밋 순서만 더한다. 색인은 캐시다. 기록 원본은 계속 Git이며, 색인을 지우거나 형식이 바뀌거나 손상되면 다시 만든다. 현재 명세·위키(체크아웃)는 저장 규약의 상한이 있어 색인에 두지 않고 요청 때 읽어 통째로 보내며, 검색을 위해서만 색인에 복사한다.

## 결과

필터·검색어·건수·페이지가 전체 이력 기준이 됐고, 서버를 다시 띄워도 읽은 커밋은 다시 읽지 않는다(이 저장소에서 첫 이력 요청 538ms → 재기동 후 99ms, 질의 9~18ms). 전역 검색이 지난 변경의 제목·이유까지 찾는다. 대가는 서버 코드(스키마·동기화·전문 검색)와 `.git` 안에 쓰는 파일 하나다. `.gitifact/data/`에 두는 안은 에디터 트리에 폴더가 보이고 worktree마다 따로 만들어 기각했다. 서버 메모리에만 두는 안은 서버를 띄울 때마다 전체를 다시 읽고, JSON 파일은 결국 메모리에서 직접 거르고 찾아야 해 기각했다. 서버 프레임워크(express·Fastify)는 느린 원인이 HTTP가 아니었고 CLI가 런타임 의존성 없이 번들되므로 넣지 않았다.
