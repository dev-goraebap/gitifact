# 브라우저

브라우저는 CLI 로컬 서버가 제공하는 읽기 전용 React SPA다. 제품 개요, 요구사항, 프로젝트 위키, 활동, 참여자, Git 상태를 보여주며 요구사항을 편집하거나 승인을 만들지 않는다.

## 화면

브라우저는 제품 개요에서 시작한다. 메뉴 순서는 제품 개요 → 기능별 요구사항 → 프로젝트 위키 → 활동 → 참여자 → Git 상태이며, 아래 GITIFACT 절에 소개가 있다.

| 경로 | 화면 |
| :--- | :--- |
| `/product` | 제품 개요. 프로젝트 이름과 규모, 변경 종류·참여자별 커밋 차트, 최신 활동. 위키로 가는 링크는 없다 |
| `/features`, `/features/$featureId` | 기능별 요구사항. 기능마다 그 요구사항을 행으로 잇는 목록(기능 단위 페이징)과 요구사항·설계 탭 상세 |
| `/wiki`, `/wiki/$documentId` | 프로젝트 위키. 왼쪽 트리와 오른쪽 본문(폴더 내용 또는 페이지)으로 된 탐색기 |
| `/` | 시작 주소. `/product`로 리다이렉트하고, 검색 인자가 있으면 0.5.0 전 활동 주소로 보고 같은 인자로 `/activity`에 보낸다 |
| `/activity` | 활동. 커밋된 요구사항·설계·문서의 추가·변경·이동·제거 타임라인, 필터, 상세 드로어 |
| `/contributors`, `/contributors/$email` | 참여자 카드와 상세 |
| `/git` | Git 상태 |
| `/about` | Gitifact 소개. README와 같은 내용 |

모든 화면 머리에 문서 검색 입구가 있다. `mod+K`와 그 버튼이 같은 검색창을 열며, 별도 주소는 두지 않는다.

목록을 대체하는 상세는 경로 매개변수로 구분한다. 같은 화면 안의 상태(활동 드로어의 `selected`, 기능 상세의 `tab`, 위키의 `folder`, 검색어 `q`)는 검증된 search params에 둔다. 검색 입력은 URL replace, 상세 이동은 뒤로가기로 복원한다. 검색창은 입력값을 URL에 직접 묶지 않는다. 라우터의 비동기 갱신이 한글 조합 중인 값을 되돌려 쓰므로 필드가 입력값을 들고 URL에 따라 반영한다(`pages/product/ui/SearchFilter.tsx`).

## 코드 구성 (FSD)

`app`(라우트·provider) → `pages` → `widgets` → `features` → `entities` → `shared` 방향으로만 의존한다. 단일 화면의 api/model/ui는 해당 page에 둔다. 여러 화면이 공유하는 조회·도메인 표현만 entities, 공통 화면 블록은 widgets에 둔다. 같은 계층의 다른 슬라이스를 참조하지 않고 외부에서는 index.ts 공개 API만 쓴다. 명세·문서 화면은 `pages/product` 슬라이스가 조합하고 세션·명세 Query와 미커밋 여부 훅(`useWorkingChanges`)은 `entities/project`가 소유한다. 화면 문구는 `shared/i18n`의 `t()`·`tNodes()`로 가져오고 소개 본문은 `packages/intro/<lang>/intro.md`를 `shared/i18n`이 가져오고, 맨 앞 로고 블록은 같은 패키지의 로고 파일을 번들한 이미지로 보여 준다. 규칙은 CLI 지침의 문구 절을 따른다.

## 데이터 흐름

| 상태 | 소유 |
| :--- | :--- |
| CLI 응답·조회 오류·재조회 상태 | TanStack Query |
| 상세 대상(기능 ID·참여자 이메일·문서 ID) | Router 경로 매개변수 |
| 검색·필터·탭·드로어 선택·위키 폴더 | Router의 검증된 search params |
| 모바일 메뉴 등 일시 UI | 컴포넌트 또는 app provider |

QueryClient는 앱에서 하나만 만든다. 조회 키에 계약 버전·서버 세션·repository/worktree를 포함하고 다른 세션의 캐시를 이어 보여주지 않는다. 처음 로딩·빈 결과·조회 실패를 구분하고 재조회 실패는 이전 자료와 확인 시각을 유지한다. 세션 변경·계약 불일치는 다시 연결하도록 한다. 실패를 빈 목록이나 clean으로 바꾸지 않는다.

읽기 HTTP는 AbortSignal을 전달하고 서버 상태를 localStorage에 영구 저장하지 않는다. 자동 재시도는 제한하며 상태 갱신 POST를 반복하지 않는다. 파일 변경을 자동 통지받는다고 가정하지 않고 명시적 새로고침으로 갱신한다. 명세 조회는 그래서 만료되지 않는다(staleTime 무한). 모든 명세 화면이 이 조회 하나를 함께 쓰므로 만료되면 화면을 옮길 때마다 불러온 페이지를 전부 다시 읽는다. 이력은 HEAD·조건마다 useInfiniteQuery로 50건씩 이어 읽고 다음 페이지 실패 시 기존 목록을 보존한다. 같은 HEAD의 이력은 바뀌지 않으므로 새로고침은 체크아웃만 다시 읽는다.

미커밋 명세 변경 여부는 두 출처를 함께 본다. 명세 응답의 `working`은 명세 화면이 채운 Query 캐시에서만 읽고 셸이 명세 API를 따로 호출하지 않으므로, gitifact 저장소가 없는 프로젝트에서 Git·소개 화면이 오류를 내지 않는다. 모든 페이지가 헤더의 프로젝트명을 위해 읽는 Git 상태 응답에서는 `.gitifact/`(과거 `.tryce/`) 아래 변경 경로가 있으면 같은 표시를 켠다. 그래서 Git 상태 페이지로 바로 들어와도 인디케이터와 배너가 보인다.

초기 조회는 200ms 뒤 골격을 보여주고 한번 보이면 최소 300ms 유지한 뒤 본문을 페이드인한다(useLoadingHold). 골격은 화면별 실제 배치를 화면의 여백·간격 클래스를 그대로 써서 본뜬다. 검색어 입력은 타자가 멈춘 뒤 500ms에 반영한다(`shared/lib/search`의 값 하나를 화면 검색창과 검색창 팔레트가 함께 쓴다). 재조회 중에는 현재 목록을 유지한다.

## 레이아웃

AppShell은 wash 변형의 inset 배치다. 왼쪽 메뉴(기본 240px, 200~400px 조절, localStorage 유지)의 머리는 폭 128px(8 × `--spacing-4`)의 워드마크이며 글자색으로 그린다. 메뉴와 바닥이 같은 배경이고 본문은 둥근 모퉁이·테두리·낮은 그림자의 카드 안에 있다. 카드가 스크롤 컨테이너다. 64rem 미만에서는 여백·모퉁이·그림자를 없앤다. 미커밋 명세 변경이 있으면 Git 상태 메뉴 항목 오른쪽에 경고색 StatusDot을 두고, 설명 문장은 Git 상태 페이지 상단의 Banner에만 둔다. 활동·요구사항 목록 위에 안내 문장을 두지 않는다.

페이지 헤더는 폴더 아이콘·프로젝트명 뒤에 이동 경로를 잇는 얇은 바다. 중간 계층은 링크, 마지막은 텍스트다. 헤더 오른쪽에는 검색 입구, 조회 시각(`<time>` + "조회")과 새로고침 ghost 버튼을 나란히 둔다. 검색 입구는 열리는 입력칸과 같은 모양이고 단축키를 새겨 두며 48rem 미만에서는 아이콘만 남는다. 48rem 미만에서는 조회 시각을 숨긴다. "로컬 읽기 전용" 같은 안내는 두지 않으며 설명·경로는 본문에 둔다. 제목 옆 개수 배지는 두지 않는다.

제품 개요·요구사항·활동·참여자·Git 상태·소개는 64rem 중앙 컬럼을 쓴다. 제품 개요는 페이지 제목 대신 프로젝트 이름을 큰 제목으로 두고 그 아래 한 줄에 규모(기능·요구사항·위키·참여자)와 미커밋 Token·최근 변경을 둔다. 오른쪽 끝은 일자별 변경 막대다. 그다음이 높이가 같은 좌우 두 장의 차트 카드이고, 마지막이 최신 활동이며 활동 화면의 타임라인을 그대로 쓴다. 커밋 셋, 커밋마다 기록 10개까지 보이고 나머지는 "기록 N건 더"로 활동에 잇는다. 이력 요약이 오기 전에는 건수와 빈 상태 대신 같은 골격을 둔다. 활동으로 가는 링크는 그 제목 옆 하나만 둔다. 위키는 저장소 호스팅의 파일 탐색기 구성을 따라 콘텐츠 카드 전체를 채운다. 왼쪽 17rem에 위키 전체를 접고 펴는 Astryx TreeList, 오른쪽에 현재 위치 Breadcrumbs와 본문이 있다. 본문은 폴더일 때 그 폴더의 내용(폴더 먼저, 파일은 이름·제목·최근 변경)이고 폴더에 README.md가 있으면 목록 아래에 이어 보여 준다. 파일일 때는 제목·경로·ID·최근 변경·활동 링크와 읽기 본문이다. 트리와 본문은 따로 스크롤하고, 위치가 바뀌면 본문은 맨 위에서 시작한다. `/wiki`와 `/wiki/$documentId`는 부모 라우트 하나가 그려 페이지를 옮겨도 트리의 펼침 상태가 유지되고 화면 전체가 다시 나타나지 않는다. 48rem 미만에서는 트리를 숨기고 경로와 폴더 목록으로 이동한다. 활동 상세 드로어는 데스크톱에서 오른쪽 도킹 패널(폭 조절 가능), 1024px 미만에서 전체 화면이다. 드로어의 변경 내용은 변경 후 위에 변경 전을 겹치고 손잡이를 끌어 드러내는 비교 슬라이더이며 변경 전 층은 `--color-background-yellow`다.

활동 타임라인의 한 항목은 커밋 하나다. 세로 선 위의 아바타 옆에 작성자·상대 시각·기록 수, 그 아래 커밋 해시와 커밋 제목 한 줄이 머리이고, 본문은 기록된 이유마다 한 덩어리다. 이유는 한 번만 적고 그 이유로 바뀐 기록을 한 줄씩 아래에 둔다. 이유 문단은 46rem 폭까지만 흐른다. 묶음을 나누는 선은 두지 않고 간격으로만 나눈다. 한 이유와 그 기록 사이는 `--spacing-2`, 이유 묶음 사이는 `--spacing-5`다. 세로 선은 타임라인의 것 하나뿐이다. 기록 줄은 변경 종류 토큰·명세 종류·제목·현재 위치 순서이고 앞의 두 칸이 폭을 지켜 줄끼리 맞춰지며, 48rem 미만에서는 위치가 제목 아래로 내려간다. 날짜가 바뀌는 자리에 날짜를 표시하고 그 자리에서 세로 선을 끊는다.

기능별 요구사항 목록은 기능 행 아래에 그 기능의 요구사항을 낮은 행으로 잇는다. 요구사항 행은 번호·제목과 그 요구사항을 설명하는 설계 절로 가는 링크만 두고, 누르면 상세의 그 절로 가는 프래그먼트 주소로 이동한다. 페이지는 40행을 넘기 전까지 기능을 담되 한 기능을 쪼개지 않으며, 한 기능은 요구사항 12개까지 보인 뒤 나머지를 상세로 잇는다. 페이지 매김은 카드 바닥에 붙는 푸터에 두고, 기능 행에는 빗금 바탕을 깔아 묶음의 머리를 구분한다. sticky만으로는 스크롤이 없는 짧은 화면에서 바닥에 붙지 않으므로 푸터가 든 칸을 카드 높이까지 늘인다. 묶음 사이는 마지막 요구사항 행의 아래 여백으로 벌리며 그 자리에는 빗금을 깔지 않는다. 어느 절을 보러 왔는지는 절 제목 위를 지나는 형광펜 표시(`<mark>`)로 알린다. 절 옆 세로 줄은 두지 않는다. 요구사항과 설계 절 양쪽에 같은 표시를 쓰고, 밖에서 연 주소도 그 절에서 시작한다.

목록 표의 한 행은 한 줄이고 모든 행의 높이가 같다. 행마다 다른 높이는 열을 훑는 눈이 걸리게 하므로 보조 설명은 제목 옆에서 남은 폭만 쓰고 넘치면 자른다. 표에서 대부분의 행이 같은 값을 갖는 항목은 열로 두지 않고 예외인 행에만 표시를 붙인다. 수량 열은 숫자와 함께 가장 큰 값 대비 ProgressBar를 둬 다른 행과 견줄 수 있게 한다. 필터와 정렬은 검증된 search params에 두고 기본값은 주소에 쓰지 않으며, 목록에서 상세로 갈 때와 돌아올 때 그대로 넘긴다. 정렬은 별도 Selector가 아니라 견줄 값이 있는 열의 머리에 둔다. 처음 누른 열은 그 열이 읽히는 방향으로 열고(이름은 오름차순, 개수·날짜는 내림차순) 한 번 더 누르면 뒤집는다. 행이 묶인 표에서는 플러그인에 정렬을 맡기지 않고 화면이 묶음 단위로 정렬한다. 좁혀진 목록은 남은 개수와 전체 개수를 함께 알린다.

목록처럼 같은 요소가 여러 번 그려지는 곳에서는 Astryx Text의 `maxLines`를 쓰지 않고 CSS로 자른다(한 줄 `text-overflow: ellipsis`, 여러 줄 `-webkit-line-clamp`). maxLines는 잘림 여부를 재려고 요소마다 레이아웃을 강제해, 활동 334줄에서 2.7초가 들었다. 한 번만 그려지는 곳(이동 경로 등)은 잘렸을 때의 툴팁이 쓸모 있어 그대로 쓴다. 이어 붙는 목록은 항목을 memo 컴포넌트로 두고 그 자료를 동일성으로 비교해 새 항목만 그린다.

루트 글자 크기는 1920px까지 100%, 그 위로는 뷰포트에 비례해 2560px에서 18px이다. Astryx의 spacing·size-element 토큰은 같은 16px 기준값을 rem으로 다시 선언해 글자와 함께 커진다. 페이지별 zoom이나 root font-size 변경은 두지 않는다.

## 차트

집계 차트에는 차트 라이브러리를 추가하지 않는다(문서 다이어그램의 mermaid는 결정 0008의 예외다). 제품 개요의 부분-전체 막대와 일자별 변경 막대는 인라인 SVG로 그리고, 크기 비교는 Astryx ProgressBar를 쓴다. 계열이 하나면 범례 대신 무엇을 센 범위인지 적는다. 계열 색은 Astryx 데이터 토큰을 파랑 → 주황 → 보라 → 초록 순서로 고정해 쓰고 꼬리는 `--color-data-neutral`이다(인접 쌍의 색각 이상 분리 검증을 통과한 순서). 글자는 텍스트 토큰만 쓰고 계열 색을 입히지 않는다. 계열이 둘 이상이면 항상 범례를 두고 각 항목에 값과 비율을 직접 적는다. 분할 사이에는 표면색 2px 간격을 둔다.

## 서버 계약

`/api/v1/session`, `/api/v1/status`(+`/refresh` POST), `/api/v1/changelog`, `/api/v1/specs`, `/api/v1/history`, `/api/v1/history/summary`, `/api/v1/change`, `/api/v1/search`, `/api/v1/assets/<경로>`를 쓴다. specs는 체크아웃(현재 명세·위키·Git author 집계·미커밋 여부)을 통째로 준다. 체크아웃은 저장 규약의 상한이 있어 화면이 거른다. 이력은 끝이 없으므로 화면이 받은 범위에서 거르거나 세지 않는다. 필터·검색어·건수·페이지는 모두 서버가 전체 이력에 대해 답하고(history), 개요의 집계도 서버 요약(history/summary)을 쓴다. 이력은 `.git` 안의 SQLite 색인이 답하며 git은 색인에 없는 커밋을 읽을 때만 부른다(결정 0009). Windows에서 git 프로세스는 하는 일과 무관하게 약 80ms이므로, 기록 수나 파일 수만큼 git을 띄우는 읽기를 새로 만들지 않는다. 참여자는 최근 10,000개 커밋 기준이며 초과 시 표시한다.

서버 경로는 `server/routes/`의 경로 표에 한 줄씩 둔다(메서드·경로·세션·쿼리 스키마·처리 함수). 쿼리 스키마는 `@gitifact/contracts`에 두어 브라우저와 함께 쓴다. 모든 요청의 공통 검사는 `server/http/guard.ts` 한 곳이다. 서버 프레임워크는 쓰지 않는다.

Markdown은 Astryx의 안전한 렌더링을 쓰고 원시 HTML을 실행하지 않는다. 문서 본문의 ```mermaid 펜스는 다이어그램으로, `> [!NOTE]` 등 GitHub 알림은 종류 상자로 그린다(shared/ui/document). mermaid는 동적 import로만 불러 자기 청크에 두고 CDN에서 받지 않으며, 색은 그 자리의 테마 토큰을 읽어 넘긴다. 테마 토큰은 `light-dark(a, b)` 문자열일 수 있으므로, CSS 변수를 스스로 읽지 못하는 라이브러리에 색을 넘길 때는 토큰의 선언값이 아니라 그 토큰으로 칠한 요소의 계산된 색을 넘긴다. 테스트도 선언값이 아니라 계산된 색을 비교한다.

## 문서 링크

문서 본문의 상대 링크는 원문을 바꾸지 않고 그릴 때 해석한다. `shared/ui/document/resolveDocumentLink.ts`가 문서의 저장소 경로를 기준으로 대상을 계산하고 Astryx `Markdown`의 `components.link`·`components.image`로 렌더링한다. 위키 페이지는 `/wiki/$documentId`, 명세는 `/features/$featureId?tab=requirements|design`, 에셋은 `/api/v1/assets/<경로>`, 외부 URL은 새 탭이다. 저장소의 다른 파일은 이동하지 않는 링크 모양으로 두고 클릭하면 경로를 복사한다. 대상이 없는 페이지·기능은 취소선 텍스트와 툴팁으로 표시한다. 문서 경로는 context로 전달하며 `DocumentIndexProvider`가 첫 명세 응답의 페이지·기능 목록을 제공한다. 앞에 `/`가 붙은 링크는 앱 경로로 본다. 이메일 기반 아바타는 로컬에서 생성하며 외부 서비스에 이메일을 보내지 않는다.
