[English](https://github.com/dev-goraebap/gitifact/blob/main/README.md)

Gitifact는 AI 에이전트와의 대화에서 나온 요구사항과 설계, 변경 이유를 코드와 함께 Git 저장소에 관리하는 도구입니다. 별도의 문서 작업이나 정해진 개발 절차를 앞세우기보다, 평소처럼 에이전트와 대화하며 개발하는 흐름 속에서 요구사항이 정리되고 유지되도록 조용히 돕습니다.

에이전트는 요구사항과 설계, 프로젝트의 결정 이력을 작업 맥락으로 참고하고, 사용자는 CLI에 내장된 브라우저 뷰어에서 이 문서들과 변경 이력을 살펴볼 수 있습니다. 개발 규칙이나 아키텍처 결정처럼 프로젝트 전반의 지식은 작업별 프로젝트 지침으로 두고, 조직이나 개인의 작업 방식에 맞게 구성할 수 있습니다.

## 빠른 시작

아래 프롬프트를 프로젝트에서 사용하는 에이전트에게 전달하세요.

```text
이 프로젝트에서 npx gitifact@latest init을 실행하세요.
init이 AGENTS.md 등에 쓴 GITIFACT 블록을 읽고 이번 세션부터 따르세요.
```

설치가 끝나면 평소처럼 에이전트에게 만들고 싶은 기능이나 바꾸고 싶은 동작을 설명하며 개발을 이어가세요. 정리된 문서와 변경 이력은 "gitifact 브라우저를 열어주세요"라고 요청해 확인할 수 있습니다.

에이전트는 새 세션에서 새 버전을 확인하고 업데이트할지 묻습니다. 직접 명령을 실행하려면 [CLI 안내](https://github.com/dev-goraebap/gitifact/blob/main/apps/cli/README.md)를 참고하세요.

## 도구의 목적: 구현 바깥의 맥락

에이전트와 함께 개발하면서 저는 "무엇을, 왜 그렇게 만들었는가"라는 맥락을 남기는 일이 중요하다고 느꼈습니다.

제가 속한 조직에서는 개발 과정의 산출물을 체계적으로 관리하는 프로젝트를 주로 다뤄왔습니다. 반면 개인 프로젝트에서는 간단한 PRD나 설계 문서처럼 에이전트가 개발하는 데 필요한 정도의 문서만 작성해왔습니다. 두 환경 사이의 간극을 경험하면서 요구사항과 문서를 어떻게 관리하면 좋을지 고민이 많았습니다. 산출물의 기본 틀은 비슷하더라도 조직이나 사람마다 작성하고 관리하는 방식이 달라, 하나의 방식으로 정리하기도 어려웠습니다.

에이전트와 함께하는 개발에서도 기존의 문서 관리 방식을 그대로 적용하는 것이 적절한지 확신하기 어려웠습니다. 그렇다고 새로운 방식을 스스로 정해 답으로 제시하기도 어려웠습니다. 그래서 Gitifact는 널리 알려진 스펙 주도 개발 도구들을 참고해, 기능별로 요구사항과 설계를 함께 관리하는 구조를 택했습니다.

Gitifact를 만들며 추구한 것은 **'조용함'**입니다. 특정한 방법론이나 프로세스를 앞세우기보다, 진행 중인 프로젝트의 흐름에 맞춰 기록을 돕고자 했습니다.

요구사항을 주도적으로 관리하고 싶은 사람이라면 에이전트와 대화하며 명세의 품질을 얼마든지 정교하게 다듬을 수 있습니다. 반대로 문서에 신경 쓸 겨를 없이 오로지 제품의 완성에만 몰두하고 싶은 사람이라도 괜찮습니다. 평소처럼 개발에만 집중하다가, 문득 "이 제품이 지금 정확히 어떤 일들을 하고 있는가?" 확인하려 했을 때 이미 제품의 요구사항들이 차분히 정리되어 있는 도구를 지향합니다.

## Git 요구사항 추적

Git은 뛰어난 버전 관리 도구이지만 파일과 줄(line) 단위로 변경을 추적합니다. 반면 요구사항은 제품의 기능과 규칙을 나타내는 의미 단위입니다.

문서 구조가 바뀌어 제목이 달라지거나 내용이 다른 파일로 옮겨지면, Git diff는 이를 단순한 삭제와 추가로 인식합니다. 그 결과 에이전트는 이전 요구사항이 어디로 이동했는지 대화와 diff 속에서 매번 추론해야 하고, 맥락을 놓치기 쉽습니다. 이런 연속성과 연결만큼은 에이전트의 불확실한 추론에 기대기보다 코드가 명확히 보장해 주는 편이 안전하다고 생각했습니다.

Gitifact는 기능마다 **요구사항**과 **설계**를 짝지어 다룹니다. 요구사항은 하나가 파일 하나이고, 설계는 관점마다 파일을 나눕니다. 모든 문서에는 CLI가 발급한 ID가 붙어 있어 제목이 바뀌거나 파일이 다른 기능으로 옮겨져도 같은 문서로 끝까지 추적을 이어줍니다.

- **요구사항(`requirements/`).** 사람이 직접 보고 검토하며 제품의 동작과 현상을 쉽게 이해할 수 있는 형태로 작성됩니다. 제품이 보장해야 할 규칙과 기능이 여기에 담깁니다.
- **설계(`design/`).** 에이전트가 실제 코드 구현을 원활하게 수행할 수 있도록 돕는 구체적인 기술 맥락입니다. 전역적인 아키텍처 결정 기록(ADR)에는 담기 어려운 해당 기능만의 기술적 특이사항과 세부 구현 흐름이 다루어지며, 프로젝트 지침이나 외부의 어떤 문서를 참고하여 작업했는지 그 출처와 배경도 함께 담깁니다.

## 작업별로 읽는 프로젝트 지침

개별 기능의 명세가 무엇을 만들지 말한다면, **프로젝트 지침(`.gitifact/instructions/`)**은 이 프로젝트에서 어떻게 일하는지를 말합니다. 아키텍처 규칙, 여러 기능에 걸친 결정, 문체, 검증 절차처럼 사람의 머릿속에 있던 지식을 작업별 지침으로 나눠 둡니다.

- **필요한 때에 필요한 지침만.** 지침 하나는 폴더 하나이고, 본문 `index.md`와 긴 내용을 나눈 `references/`로 이뤄집니다. 에이전트가 매 세션 읽는 AGENTS.md에는 어떤 작업 때 어느 지침을 읽을지만 짧게 적습니다. 에이전트는 CLI 코드를 고칠 때는 CLI 지침을, 커밋 전에는 검증 지침을 골라 읽습니다.
- **자유로운 구성.** 어떤 지침을 둘지, 지침 안을 어떻게 나눌지는 프로젝트가 정합니다. Gitifact는 ID와 형식 검사, 변경 이력만 맡고 특정 문서 양식을 강요하지 않습니다.
- **한 방향의 연결.** 지침은 여러 기능에 걸친 지식이라 특정 명세를 가리키지 않습니다. 대신 설계가 어떤 지침을 따랐는지 참고 문서로 적어, 명세가 바뀌어도 지침이 함께 낡지 않습니다.

지침 역시 이름이나 위치가 바뀌어도 같은 ID로 추적되며, 에이전트가 커밋할 때 변경 이유를 함께 기록합니다. 브라우저의 "프로젝트 지침" 메뉴에서 AGENTS.md와 작업별 지침을 모아 볼 수 있습니다.

## 바이브 코딩과 커밋 시점의 기록

에이전트와의 대화에서 사소한 수정 요청이 오갈 때마다 매번 요구사항 문서를 개정하지 않습니다.

저는 화면을 보며 "이걸 이렇게 고쳐줘", "동작이 마음에 안 드니 저렇게 바꿔줘"라며 빠르게 시도하고 수정하는 바이브 코딩(vibe coding) 방식으로 작업하곤 합니다. 그 과정의 중간 시도를 모두 요구사항 변경으로 남기면, 최종적으로 어떤 동작을 원했는지 읽기 어려워진다고 느꼈습니다.

그래서 Gitifact에서는 작업을 지시받으면 요구사항 초안을 준비하고 대화에 맞춰 다듬다가, **커밋할 때 에이전트가 바뀐 요구사항과 그 변경 이유를 코드와 함께 묶어 Git에 기록**하도록 했습니다.

사용자가 변경 이유를 남기기 위해 문서를 따로 작성하거나 복잡한 명령을 외울 필요는 없습니다. 대화 맥락을 이해한 에이전트가 "왜 이 변경이 일어났는가"를 알아서 정리하여 커밋에 담아줍니다. 만약 제품의 동작이나 의도가 모호한 부분이 있다면 에이전트가 먼저 질문을 건네며 구체화해 나갑니다.

## 점진적인 도입

기존 프로젝트라면 도입한 시점부터 기록을 쌓아가면 됩니다. 유지보수하거나 새 기능을 추가하면서 해당 영역의 요구사항부터 조금씩 정리해 나가도 되고, 과거 이력 전체를 먼저 문서화해야 한다는 부담을 가질 필요는 없습니다.

반대로 도입하는 시점에 에이전트에게 기존 소스코드나 정보가 담긴 파일들을 살펴보게 하여, 전체적인 요구사항과 설계 초안을 빠르게 먼저 뽑아내는 방식도 얼마든지 가능합니다. 초안에 부족한 부분이 있으면 이후 실제 변경이 일어날 때마다 대화를 통해 보완해 나갈 수 있습니다.

새 프로젝트라면 처음 아이디어를 나누는 대화부터 가볍게 시작하면 됩니다. 만들고 싶은 제품을 구체화하는 동안 에이전트가 요구사항과 구현 설계를 함께 정리하고 불명확한 제품 동작을 질문합니다.

## 적용 범위와 한계

고민 끝에 이 도구는 **하나의 Git 저장소(단일 레포 또는 모노레포) 안에서 제품을 만드는 환경**만을 전제로 두었습니다. 여러 저장소 사이의 연결까지 관리하면 도구의 구조와 사용법이 복잡해질 것이라고 판단했습니다. 여러 저장소를 함께 관리하는 기능은 Gitifact의 범위에 포함하지 않았습니다.

## 프로젝트 상태

Markdown 요구사항·설계와 커밋 시점의 변경 이유를 Git에 연결하고, 브라우저 뷰어에서 활동·요구사항·참여자를 볼 수 있습니다. 에이전트에게 "gitifact 브라우저를 열어주세요"라고 요청하세요.

최신 공개 버전은 [npm](https://www.npmjs.com/package/gitifact)에서, 버전별 변경 내역은 [패치노트](https://github.com/dev-goraebap/gitifact/blob/main/apps/cli/src/shared/i18n/ko/changelog.md)에서 확인하세요.

제품의 목적·원칙·범위는 이 문서에서, 기능별 요구사항과 설계는 [요구사항](https://github.com/dev-goraebap/gitifact/tree/main/.gitifact/spec)에서 확인할 수 있습니다.
