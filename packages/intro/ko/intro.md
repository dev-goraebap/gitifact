AI 에이전트와 함께 개발하면서 직접 코드를 작성하는 일은 점점 줄어들었습니다. 어떻게 구현할 것인가에 대한 고민은 지금도 여전히 중요하지만, 에이전트에게 올바른 설계 컨텍스트를 쥐어주고 '무엇을 만들고자 하는지 명확히 이해하고 전달하는 일'에 점차 더 많은 에너지를 쏟게 되었습니다.

이런 고민 속에서 기존의 스펙 주도 개발 도구들을 제 방식에 맞게 적용해보려 애써보기도 했지만, 좋은 도구들의 방대한 배경과 복잡도를 제가 온전히 따라가지 못해 다소 과하게 느껴지곤 했습니다. 또한 조직에서 관리하는 프로젝트 산출물과 실제 개발 과정에서 빠르게 변화하는 구현 맥락 사이의 간극도 늘 고민거리였습니다.

그래서 거창한 규칙을 더하기보다는, 기존의 개발 방식을 크게 벗어나지 않으면서 에이전트와의 대화 속에서 도출되는 요구사항 명세와 변경 이유를 Git 저장소 안에서 조용히 관리해 줄 가벼운 장치가 필요했습니다. Gitifact는 바로 그 고민에서 출발한 도구입니다.

## 빠른 시작

아래 프롬프트를 프로젝트에서 사용하는 에이전트에게 전달하세요.

```text
npm install -g gitifact@latest로 gitifact를 설치하세요. 이미 설치돼 있어도 최신 버전으로 올리기 위해 실행합니다. 그다음 이 프로젝트에서 gitifact init을 실행하세요.
init이 AGENTS.md 등에 쓴 GITIFACT 블록을 읽고 이번 세션부터 따르세요.
```

Node.js 24.x와 Git이 필요합니다. `init`은 프로젝트의 AGENTS.md 같은 에이전트 지침 파일에 작업 규칙 블록을 씁니다. 그 뒤로는 평소처럼 제품을 설명하고 개발을 이어가면 됩니다. 브라우저가 새 버전을 알려 주면 에이전트에게 업데이트를 맡기거나 직접 설치하고, `gitifact update`로 블록을 새 버전에 맞추세요. 명령 목록은 [CLI 안내](https://github.com/dev-goraebap/gitifact/blob/main/apps/cli/README.md)에 있습니다.

## 도구의 목적: 구현 바깥의 맥락

에이전트에게 개발을 맡길수록 중요해지는 것은 "무엇을, 왜 그렇게 만들었는가"라는 맥락이었습니다.

요구사항 문서를 어떻게 관리해야 하는지에 대해서는 사람마다 의견이 갈릴 수 있고, 사실 이 부분을 논하기엔 저의 지식이 아직 얕다고 생각합니다. 모두를 만족시킬 수 있는 형식을 직접 정의하기도 어려웠습니다. 더 많은 경험을 쌓기도 전에 에이전트 시대가 먼저 찾아온 상황에서, 이미 많은 분들이 좋아하고 인지도가 높은 오픈소스 레퍼런스들의 구조를 차용하는 것이 저로서는 가장 합리적인 차선책이었습니다.

다만 기존의 스펙 주도 개발 도구들과 Gitifact가 다른 점이 있다면 바로 **'조용함'**입니다. 도구가 앞장서서 특정한 방법론이나 프로세스를 강제하지 않고, 진행 중인 프로젝트의 흐름을 건드리지 않으며 조용히 맞춰가는 것을 추구합니다.

요구사항을 주도적으로 관리하고 싶은 사람이라면 에이전트와 대화하며 명세의 품질을 얼마든지 정교하게 다듬을 수 있습니다. 반대로 문서에 신경 쓸 겨를 없이 오로지 제품의 완성에만 몰두하고 싶은 사람이라도 괜찮습니다. 평소처럼 개발에만 집중하다가, 문득 "이 제품이 지금 정확히 어떤 일들을 하고 있는가?" 확인하려 했을 때 이미 제품의 요구사항들이 차분히 정리되어 있는 도구를 지향합니다.

Gitifact는 Git 위에 최소한의 장치만 더합니다.

- **에이전트에게는 작업 맥락을.** Gitifact로 관리되는 프로젝트에 참여한 에이전트는 소스코드뿐 아니라 요구사항과 프로젝트 전반의 결정 이력을 빠르게 파악해 다음 지시를 더 정확하게 수행할 수 있습니다.
- **사람에게는 시각적 가시성을.** CLI에 내장된 읽기 전용 브라우저 뷰어를 통해 제품의 요구사항, 설계, 그리고 자율적으로 구성한 위키 문서를 한눈에 편안하게 확인하고 탐색할 수 있습니다.

## Git 요구사항 추적

Git은 뛰어난 버전 관리 도구이지만 파일과 줄(line) 단위로 변경을 추적합니다. 반면 요구사항은 제품의 기능과 규칙을 나타내는 의미 단위입니다.

문서 구조가 바뀌어 제목이 달라지거나 내용이 다른 파일로 옮겨지면, Git diff는 이를 단순한 삭제와 추가로 인식합니다. 그 결과 에이전트는 이전 요구사항이 어디로 이동했는지 대화와 diff 속에서 매번 추론해야 하고, 맥락을 놓치기 쉽습니다. 이런 연속성과 연결만큼은 에이전트의 불확실한 추론에 기대기보다 코드가 명확히 보장해 주는 편이 안전하다고 생각했습니다.

Gitifact는 기능마다 **요구사항(`requirements.md`)**과 **설계(`design.md`)**를 짝지어 다루며, 문서 안에서 제목이나 위치가 바뀌더라도 같은 요구사항으로 끝까지 추적을 이어줍니다.

- **요구사항(`requirements.md`).** 사람이 직접 보고 검토하며 제품의 동작과 현상을 쉽게 이해할 수 있는 형태로 작성됩니다. 제품이 보장해야 할 규칙과 기능이 여기에 담깁니다.
- **설계(`design.md`).** 에이전트가 실제 코드 구현을 원활하게 수행할 수 있도록 돕는 구체적인 기술 맥락입니다. 전역적인 아키텍처 결정 기록(ADR)에는 담기 어려운 해당 기능만의 기술적 특이사항과 세부 구현 흐름이 다루어지며, 위키의 아키텍처 지침이나 외부의 어떤 문서를 참고하여 작업했는지 그 출처와 배경도 함께 담깁니다.

## 프로젝트 규칙과 자율성을 위한 위키

개별 기능의 명세가 명확한 규칙과 추적으로 관리된다면, 프로젝트 전반의 지식과 약속을 다루는 **위키(`.gitifact/wiki/`)**는 사용자에게 온전한 자율성을 제공합니다.

프로젝트마다 관리해야 할 지식의 성격과 방식은 다릅니다. Gitifact는 특정 문서 양식을 강요하지 않고 프로젝트에 맞게 자유롭게 구조화할 수 있도록 열어두었습니다.

- **자유로운 구조와 테일러링.** 아키텍처 결정 기록(ADR), 코딩 컨벤션, 개발 환경 규칙 등 프로젝트에 필요한 주제별로 하위 폴더와 문서를 원하는 대로 구성할 수 있습니다.
- **운영 방침의 사용자 정의.** 위키의 진입점인 `.gitifact/wiki/README.md`에 작성한 내용이 곧 에이전트가 따르는 '위키 운영 방침'이 됩니다. 프로젝트나 팀의 일하는 방식에 맞게 이 문서를 고치면, 에이전트는 그 지침을 읽고 사용자가 정한 규칙에 맞춰 작업합니다.

위키 문서 역시 파일 위치나 제목이 바뀌어도 끊김 없이 추적되며, 에이전트가 커밋할 때 변경 이유를 함께 묶어 기록합니다. 사용자는 프로젝트의 맥락을 자율적으로 구성하고, 에이전트는 그 규칙을 바탕으로 일관된 작업을 수행합니다.

## 바이브 코딩과 커밋 시점의 기록

에이전트와의 대화에서 사소한 수정 요청이 오갈 때마다 매번 요구사항 문서를 개정하지 않습니다.

화면을 보며 "이걸 이렇게 고쳐줘", "동작이 마음에 안 드니 저렇게 바꿔줘"라며 빠르게 시도하고 뒤엎는 바이브 코딩(vibe coding) 과정의 시행착오나 생각의 변화는 지극히 자연스러운 일입니다. 그 짧은 시간 동안 일어나는 수많은 잔손질과 중간 시도들을 매번 요구사항 변경으로 남기면 오히려 문서가 소음으로 가득 차게 됩니다.

요구사항이라는 것은 그렇게 찰나의 순간마다 바뀌는 것이 아니라고 보기에, 작업을 지시받으면 요구사항 초안을 준비해두고 최종적으로 **커밋할 때 에이전트가 바뀐 요구사항과 그 변경 이유를 코드와 함께 묶어 Git에 기록**합니다.

사용자가 변경 이유를 남기기 위해 문서를 따로 작성하거나 복잡한 명령을 외울 필요는 없습니다. 대화 맥락을 이해한 에이전트가 "왜 이 변경이 일어났는가"를 알아서 정리하여 커밋에 담아줍니다. 만약 제품의 동작이나 의도가 모호한 부분이 있다면 에이전트가 먼저 질문을 건네며 구체화해 나갑니다. 대화를 통해 불명확한 점을 짚어내고 생각을 정리하는 것은 원래 에이전트가 가장 잘하는 영역이기 때문입니다.

## 점진적인 도입

기존 프로젝트라면 도입한 시점부터 기록을 쌓아가면 됩니다. 유지보수하거나 새 기능을 추가하면서 해당 영역의 요구사항부터 조금씩 정리해 나가도 되고, 과거 이력 전체를 먼저 문서화해야 한다는 부담을 가질 필요는 없습니다.

반대로 도입하는 시점에 에이전트에게 기존 소스코드나 정보가 담긴 파일들을 살펴보게 하여, 전체적인 요구사항과 설계 초안을 빠르게 먼저 뽑아내는 방식도 얼마든지 가능합니다. 처음에는 다소 거칠거나 어설픈 정리가 될 수도 있지만 괜찮습니다. 중요한 것은 완벽한 첫 문서가 아니라, **이후 실제 변경이 일어날 때마다 대화를 통해 서서히 가치 있는 문서로 다듬어져 가는 과정**이기 때문입니다.

새 프로젝트라면 처음 아이디어를 나누는 대화부터 가볍게 시작하면 됩니다. 만들고 싶은 제품을 구체화하는 동안 에이전트가 요구사항과 구현 설계를 함께 정리하고 불명확한 제품 동작을 질문합니다.

## 적용 범위와 한계

고민 끝에 이 도구는 **하나의 Git 저장소(단일 레포 또는 모노레포) 안에서 제품을 만드는 환경**만을 전제로 두었습니다. 여러 저장소를 넘나드는 멀티 레포까지 지원하려다 보면 단순해야 할 도구가 지나치게 복잡해지기 때문입니다. 여러 레포를 다루는 큰 규모의 프로젝트라면 전문 이슈 트래커나 별도의 도구를 활용하는 것이 맞다고 봅니다.

## 프로젝트 상태

Markdown 요구사항·설계와 커밋 시점의 변경 이유를 Git에 연결하고, 읽기 전용 브라우저에서 활동·요구사항·참여자를 볼 수 있습니다. 에이전트에게 "gitifact 브라우저를 열어주세요"라고 요청하세요.

최신 공개 버전은 [npm](https://www.npmjs.com/package/gitifact)에서, 버전별 변경 내역은 [패치노트](https://github.com/dev-goraebap/gitifact/blob/main/apps/cli/src/shared/i18n/ko/changelog.md)에서 확인하세요.

제품의 목적·원칙·범위는 이 문서에서, 기능별 요구사항과 설계는 [요구사항](https://github.com/dev-goraebap/gitifact/tree/main/.gitifact/spec)에서 확인할 수 있습니다.
