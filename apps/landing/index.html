해결하려는 문제

에이전트에게 git log를 읽게 할 수는 있지만,
과거 변경 이력만으로는 답하기 어려운 질문이 있습니다.

  • 지금 이 제품은 무슨 동작을 하나요? 코드는 지금 하는 일을 보여 주지만, 어떤 동작이 지켜야 할 규칙이고 어떤 것이 우연히 그렇게 된 것인지는 알려 주지 않습니다.
  • 이 결정은 왜 내렸고, 어떤 대안을 버렸나요? 커밋 메시지에는 대개 무엇을 했는지만 적힙니다. 이전 대화를 모르는 새 세션의 에이전트는 이미 버린 안을 다시 제안하기도 합니다.
  • 파일을 옮기거나 쪼개면 이력은요? Git은 경로와 줄 단위로 변경을 추적하므로, 리팩터링으로 파일을 쪼개거나 옮기면 과거 맥락을 따라가기 어려워집니다.
  • 기록을 빼먹지 않을까요? 시행착오마다 문서를 고치면 개발 흐름이 끊기고, “문서를 꼭 갱신하자”는 다짐은 바쁜 개발 중에 쉽게 잊힙니다.

두 개의 진입점, 하나의 일관된 규칙

에이전트는 AGENTS.md의 GITIFACT 블록을 읽고 저장소에 있는 실행기로 CLI를 부르며, 사용자는 브라우저 뷰어로 결과를 봅니다. 두 진입점은 Core의 같은 규칙과 버전별 계약을 공유하고, Git 저장소의 Markdown 문서와 커밋 이력을 다룹니다.

전체 구조

실행기 — 진입점(CLI/서버) — 도메인 규칙(Core) — 인프라 경계(Adapters)

에이전트는 저장소의 실행기로 프로젝트 기준 버전의 CLI를 실행합니다. CLI 명령과 로컬 서버는 입력을 검증하고 Core 유스케이스를 호출합니다. Core는 Git·파일 시스템·시스템 시간에 직접 의존하지 않고 Port 인터페이스로 통신하며, 인프라 세부사항은 Adapter 계층이 구현합니다. 블록을 선택하면 세부 역할을 볼 수 있습니다.

    원본은 파일과 Git

    모든 데이터의 원본은 Git 이력과 Markdown 파일입니다. 캐시는 조회를 돕는 파생물이며 지워도 다시 만들어집니다.

    프로젝트마다 지정된 버전

    실행기가 .gitifact/config.json의 cli 버전을 사용자 캐시에 한 번 받아 실행합니다. 전역 설치가 필요 없습니다.

    한 곳의 검증 규칙

    문서와 기록의 형식 검사는 Core 한 곳에 있어, check와 changes commit이 같은 검사를 씁니다.

    기계 가독형 오류 코드

    모든 오류는 언어 설정과 무관하게 표준화된 code를 반환하므로, 에이전트가 문자열 파싱 없이 정확히 분기할 수 있습니다.

    표시 언어와 저장 규약의 분리

    안내 문구는 한국어와 영어를 지원하지만, 저장 규약, ID 체계, JSON 데이터 스키마는 언어 설정에 영향받지 않는 독립 표준을 유지합니다.

    점진적 도입과 범위

    기존 프로젝트에도 부담 없이, 오늘부터 시작할 수 있습니다.

    기존 프로젝트

    과거 이력을 전부 정리할 필요 없이, 유지보수나 신규 기능이 추가되는 영역부터 점진적으로 정리합니다. 필요 시 에이전트에게 기존 코드를 분석하여 요구사항 초안을 도출하도록 요청할 수 있습니다.

    신규 프로젝트

    아이디어를 나누는 첫 대화부터 자연스럽게 시작합니다. 제품을 구체화해 나가는 동안 요구사항과 구현 설계가 함께 정리됩니다.

    적용 범위

    하나의 Git 저장소(단일 프로젝트 또는 모노레포) 안에서 제품 개발과 기록 관리가 완결되는 구조를 전제로 합니다. 여러 저장소 사이의 연계는 범위에 넣지 않습니다.
