---
title: 커밋 시점의 최종 변경
description: 커밋 입력, 변경 이유 기록, 실패 후 복구
---

자동 기록은 커밋 권한이 아니다. 사용자 커밋 요청 또는 명시적 프로젝트 정책이 있을 때 실행한다. 정책이 없다는 이유로 자동 커밋하지 않으며 이미 부여된 권한은 다시 묻지 않는다. 푸시는 별도 권한을 따른다.

## 절차

1. 실제 diff와 관련 테스트를 확인하고 `gitifact changes list`를 실행한다. HEAD 대비 바뀐 문서, 이유가 없는 문서, 문서 검사 결과, 커밋 입력 파일 경로가 나온다.
2. 아래 입력을 그 경로에 UTF-8 JSON으로 쓰고 `gitifact changes commit --file <그 경로>`를 실행한다. 범위나 이유 누락을 먼저 보려면 `--dry-run`을 붙인다. dry-run은 파일을 쓰거나 커밋하지 않는다. 커밋이 성공하면 CLI가 입력 파일을 지운다.
3. 성공 결과와 실제 Git 상태를 확인한다. 결과의 `withoutReason`에 문서가 남아 있으면 이유 누락으로 보고한다.

```json
{
  "reasons": [
    { "docs": ["R-실제값", "D-실제값"], "reason": "대화·결정에서 확인한 변경 이유" }
  ],
  "paths": [".gitifact/spec/posts/requirements/delete.md", ".gitifact/spec/posts/design/overview.md", ".gitifact/history.jsonl", "src/posts.ts", "test/posts.test.ts"],
  "message": "프로젝트 정책에 맞는 메시지",
  "authorization": { "basis": "user-request", "evidence": "실제 커밋 요청과 작업 범위" }
}
```

예시 경로·ID·근거를 그대로 복사하지 않는다. 입력에는 이 네 필드만 둔다(`reasons`는 생략할 수 있다). `basis`는 `user-request` 또는 `project-policy`다. CLI는 자연어 권한의 진위를 판정하지 않는다.

## 입력 규칙

- **`reasons`:** 이유 하나가 `{docs: [문서 ID…], reason}`이다. `docs`에는 그 이유로 바뀐 요구사항(R-)·설계(D-)·기능(S-)·위키(W-)의 ID를 종류 구분 없이 적는다. 한 이유가 여러 문서를 설명하면 한 항목에 모은다. 서로 다른 이유는 항목을 나눈다. 이 커밋에서 지우는 문서의 ID도 적을 수 있다.
- **이유 ID:** CLI가 `H-` ID를 발급해 `.gitifact/history.jsonl` 끝에 한 줄씩 더한다. 이 파일을 직접 고치지 않는다. 이미 커밋된 줄은 바꾸지 않는다.
- **이유 없는 커밋:** `reasons`를 빼면 이유 없이 커밋된다. 문서가 바뀌었는데 이유가 없으면 `withoutReason`으로 표시된다. 모르는 이유를 꾸며내지 않는다.
- **`paths`:** 바뀐 문서 파일과 `.gitifact/history.jsonl`(이유를 쓸 때), 관련 코드·테스트를 담는다. 바뀐 문서 파일은 모두 선택해야 한다. 옮긴 문서는 옛 경로와 새 경로를 함께, 지운 문서는 지운 경로를 담는다. 문서가 참조하는 새 에셋(`.gitifact/assets/…`)도 함께 담는다. 서로 무관한 작업이 섞여 있으면 강제로 포함하지 않고 제한을 알린다.
- **검사:** 커밋 직전에 `docs check`와 같은 검사를 돌린다. 문제가 있거나 `draft: true`가 남아 있으면 커밋하지 않는다. 링크·에셋 경고는 커밋을 막지 않는다.
- **staging:** 실행 전에 staging하지 않는다. 기존 staging이나 intent-to-add가 있으면 CLI가 거부한다. 스스로 만든 staging(`git mv`·`git rm` 등)은 `git restore --staged`로 풀고 파일은 그대로 둔 채 다시 실행한다. 파일을 지우거나 옮길 때는 `git rm`·`git mv` 대신 일반 삭제·이동을 쓴다.
- **실패 후:** 훅 등으로 커밋이 거부되고 HEAD가 그대로면 이번에 쓴 이유 줄과 index는 실행 전으로 돌아간다. 원인을 고친 뒤 같은 입력으로 다시 실행한다. 실패 후 훅·서명을 끄지 않는다. 결과를 확인하지 못했다는 오류(HEAD가 바뀌었을 수 있음)면 재시도하지 않고 안내된 복구 자료와 HEAD를 확인한다. 잠금 폴더나 index 백업을 임의로 지우거나 커밋을 reset하지 않는다.

같은 입력을 두 번 커밋하면 이유 줄이 한 번 더 기록된다. 성공한 뒤에는 같은 파일로 다시 실행하지 않는다.

커밋 참조는 구현 완료 선언이 아니다. 실제 테스트 결과와 남은 제한을 별도로 알린다.

## 무엇을 한 커밋에 담는가

기본은 관련 문서·이유·소스·테스트를 같은 커밋에 담는 것이다. 분리 정책이면 문서와 이유를 먼저 커밋하고, 이어지는 코드·테스트 커밋의 메시지에서 관련 문서를 설명한다. 기존 사용자 변경이나 staging을 지우거나 무관한 변경까지 포함하지 않는다.

## 메시지와 트레일러

프로젝트의 커밋 메시지 규약을 따른다. 규약이 없으면 첫 줄에 무엇을 바꿨는지, 본문에 왜 바꿨는지를 짧게 쓴다. CLI가 바뀐 문서와 이유가 가리킨 문서로 트레일러를 붙인다(요구사항은 `Gitifact-Req`, 설계는 `Gitifact-Design`, 기능·위키는 `Gitifact-Doc`). 메시지에 `Gitifact-`로 시작하는 줄을 직접 쓰면 거부된다.

## 이유 쓰기

이유는 대화와 결정에서 확인한 사실만 적는다. 무엇을 바꿨는지보다 왜 바꿨는지를 쓴다. 기각한 대안이 이후 작업에 영향을 주면 함께 적는다. 과거 원문은 `gitifact docs show <ID> --ref <커밋>`, 이유의 흐름은 `gitifact docs history <ID>`로 Git에서 읽으므로 이유에 원문·작성자·시각을 옮겨 적지 않는다.
