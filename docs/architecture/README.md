# 아키텍처 기준

tryce는 `apps`와 `packages`로 구성하는 TypeScript 모노레포로 개발한다. CLI와 브라우저는 실행 환경과 빌드를 분리하고, 기록 규칙과 외부 데이터 계약을 명시적인 패키지 경계로 나눈다.

이 문서는 2026-09-13 사용자 지침과 공식 자료 조사를 바탕으로 정한 구현 방향이다. React·Astryx 사용은 사용자 지정이며, pnpm·Node.js·Vite·TanStack 조합은 위임받은 기술 선택이다. 현재 실행 골격과 검증한 버전·명령은 [개발 환경](../development.md)에 기록한다. 아래 구조에는 아직 구현하지 않은 목표도 포함한다. 제품의 확정·보류 상태는 [제품 기준](../bref.md)을 따른다.

## 문서 구성

- [CLI와 공통 코드](cli.md): 명령, 기록 규칙, Git·파일 접근, 로컬 서버와 배포
- [브라우저](browser.md): React·Astryx, FSD, 라우팅, 서버 상태와 검증

## 저장소 구조

아래는 목표 구조다. 실제 기능을 넣을 때 디렉터리와 패키지를 만들고, 빈 계층을 미리 생성하지 않는다.

```text
apps/
  cli/                   명령 실행, Git·파일 접근, 로컬 HTTP 서버
  browser/               React 브라우저 앱과 정적 빌드
packages/
  core/                  요구사항·이력 규칙과 유스케이스
  contracts/             버전이 있는 외부 DTO·검증 계약
.agents/
  skills/tryce-*/         이 프로젝트가 관리하는 스킬 원본
docs/
  bref.md                제품 기준과 결정 상태
  architecture/          기술 선택과 코드 경계
```

`apps`는 실행하거나 배포하는 단위다. 새로운 실행 제품이 생기면 이곳에 추가한다. `packages`는 독립된 책임과 공개 API가 있는 코드 단위다. 공통으로 보인다는 이유만으로 모든 코드를 옮기지 않는다.

두 초기 패키지는 재사용 횟수뿐 아니라 경계의 필요성 때문에 분리한다. `core`는 명령과 HTTP에서 같은 제품 규칙을 사용하고 독립적으로 시험하기 위한 단위다. `contracts`는 Node.js 코드가 브라우저에 유입되지 않게 하면서 외부 계약을 공유하기 위한 단위다.

## 기술 선택

| 영역 | 선택 | 이유 |
| :--- | :--- | :--- |
| 언어 | TypeScript, strict, ESM | CLI·브라우저에서 타입과 계약을 공유 |
| 워크스페이스 | pnpm workspaces | 로컬 패키지 경계와 의존 관계를 명시 |
| CLI 개발 런타임 | Node.js 24 LTS 계열 | 현재 개발 환경과 장기 지원 계열을 기준으로 시작 |
| 브라우저 | React 19 + TypeScript + Vite | 로컬 서버가 제공하는 SPA 구성 |
| 디자인 시스템 | Astryx | 사용자 지정, 제공 컴포넌트와 테마를 우선 사용 |
| 경로·URL 상태 | TanStack Router | 타입 기반 경로와 검색 조건 관리 |
| 서버 상태 | TanStack Query | 재조회·중복 요청·캐시 무효화 관리 |

pnpm의 루트 workspace 파일과 `workspace:` 의존성을 사용한다. 루트 `package.json`은 private으로 두고 단일 lockfile을 커밋한다. 정확한 도구 버전은 환경 구축 시 호환성을 확인하고 고정한다. 현재 설치된 Node.js는 v24.17.0이며, 이것이 곧 배포 CLI의 최저 지원 버전이라는 뜻은 아니다. 사용자 런타임 지원 범위는 배포 검증과 함께 선언한다. [pnpm workspaces](https://pnpm.io/workspaces), [Node.js 릴리스](https://nodejs.org/en/about/previous-releases).

초기에는 pnpm의 작업 실행으로 충분하다. 빌드 병목이나 별도 배포 요구가 생기기 전에는 추가 모노레포 실행 도구를 도입하지 않는다.

## 의존 방향

```text
apps/browser ──→ packages/contracts
apps/cli     ──→ packages/contracts
apps/cli     ──→ packages/core
```

`core`는 제품 모델과 규칙을 소유한다. 외부 DTO는 `contracts`가 소유하고 CLI의 출력·HTTP 어댑터가 변환한다. UI의 화면 모델은 브라우저 안에 둔다. 역할이 다른 모델을 하나의 거대한 공통 타입으로 합치지 않는다.

- 패키지는 `apps`를 참조하지 않는다. 앱끼리 소스 코드를 직접 import하지 않는다.
- 브라우저는 `core`의 내부 규칙이나 Git·파일 접근 코드를 가져오지 않는다.
- 패키지 간에는 exports로 공개한 진입점만 사용한다. 다른 패키지의 `src`를 경로로 참조하지 않는다.
- React UI를 사용하는 앱이 하나인 동안 UI 공통 코드는 브라우저의 `shared/ui`에 둔다. `packages/ui`는 별도 소비자가 생길 때 검토한다.
- 브라우저의 FSD `shared`와 저장소의 `packages`는 다른 범위다.

## 브라우저와 CLI의 연결

`tryce browser`가 현재 프로젝트를 대상으로 로컬 서버를 실행한다. 서버는 같은 `core` 유스케이스로 데이터를 만들고 버전이 있는 계약으로 응답한다. 브라우저는 HTTP로 읽으며 CLI 프로세스를 직접 실행하거나 파일 시스템에 접근하지 않는다.

개발 중에는 Vite 개발 서버가 API 요청을 로컬 서버로 프록시한다. 배포 시에는 미리 빌드한 브라우저 정적 파일을 CLI 배포물에 포함하고 같은 origin에서 제공하는 방향으로 시작한다. 소스 의존 대신 빌드 산출물을 패키징 단계에서 연결한다. 설치된 CLI가 UI를 보여주기 위해 Vite 개발 서버나 workspace 원본을 필요로 해서는 안 된다.

이력·현재 상태와 브리핑은 공통 모델에서 파생하되 같은 JSON 전체를 모든 화면에 전달하지 않는다. 응답 계약은 제품의 출력 계약 버전과 연결하고 필요한 조회 범위만 제공한다. 정확한 필드와 endpoint는 첫 기능 명세에서 정의한다.

## 스킬과 자체 적용

스킬 원본을 `.agents/skills/tryce-*`에 둔다는 확정을 유지한다. 모노레포 정리를 이유로 `.tryce/skills`나 `packages/skills`에 두 번째 편집 원본을 만들지 않는다. 향후 CLI 배포에 스킬을 포함할 경우 빌드 과정에서 원본을 배포 자산으로 수집한다.

소스 코드의 앱 경계와 실제 사용 프로젝트의 `.agents`·설정·캐시 배치는 별개다. 예외 에이전트 복사본을 커밋할지에 대한 보류 사항도 이 문서가 대신 결정하지 않는다. 현재 개발은 [AGENTS.md](../../AGENTS.md)의 DEV-01 등 대체 절차를 적용한다.

## 구축 순서와 검증

1. pnpm workspace, TypeScript, 빌드·타입 검사·테스트 실행 방법을 만든다.
2. 첫 조회 계약과 임시 Git 저장소 사례를 정의하고 `core`·CLI의 작은 기능을 연결한다.
3. React·Astryx·Router·Query의 최소 화면을 실제 빌드한다. 호환성과 정적 배포를 확인한다.
4. 같은 계약의 mock 응답과 실제 API 응답으로 브라우저를 검증한다.
5. 패키징한 CLI를 workspace 밖에서 실행해 명령과 UI 자산 경로를 확인한다.

정확한 버전 조합, 빌드·테스트 스크립트, 배포 런타임 범위는 검증된 실행 환경 문서에 추가한다. 조사 결과를 실제 실행 성공으로 표시하지 않는다. 클로드가 별도로 작성하는 와이어프레임은 이 계약과 스택을 기준으로 연결하며 중복 제작하지 않는다.
