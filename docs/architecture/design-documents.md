# 기능 설계 문서

기능별 requirements.md는 원하는 동작과 수용 조건을, design.md는 구현 구조와 처리 방식을 설명한다. 새 기능을 정리할 때 에이전트는 두 문서를 함께 작성한다. 단계별 승인을 강제하지 않고 중요한 불명확함만 질문한다. CLI는 빈 설계를 만들지 않는다. 사용자가 요구사항만 요청하거나 기존 명세에 설계가 없으면 그대로 허용한다. tasks.md는 이번 범위에서 제외한다.

## 파일과 식별자

`.gitifact/spec/<기능>/design.md` 첫 줄은 `<!-- gitifact-design: S-ID -->`이며(2026-09-15 이전 커밋의 `tryce-design`·`tryce-ref`·`.tryce` 경로는 읽기만 지원) 같은 폴더의 requirements.md와 같은 실제 S-ID를 사용한다. 별도 설계 ID나 문단 ID는 발급하지 않는다. 최상위 제목 하나와 비어 있지 않은 Markdown 본문이 필요하다. 기능 폴더가 바뀌어도 S-ID가 같으면 동일 설계다. 요구사항 문서 없는 설계·이유 파일은 거부한다.

본문의 선택 참조는 `<!-- gitifact-ref: R-ID, R-ID -->` 형식이다. 실제 ID를 쓰며 코드 블록의 예시는 참조로 해석하지 않는다. CLI는 문법과 기능 소유 ID를 검사한다. 현재 전체 명세에 없는 참조는 MISSING_DESIGN_REFERENCE 경고로 반환한다. 삭제·이동 이후의 설명과 과거 원문을 보존하기 위해 누락 참조로 조회·커밋을 막지는 않는다. 스킬은 경고를 확인하고 해당 설명이 여전히 유효한지 판단한다. 문서 의미의 타당성을 CLI가 판정하지 않는다.

## 작성과 개정

기본 목차는 개요, 구조와 데이터, 처리 흐름, 오류 처리와 검증, 주요 설계 결정, 미결 사항이다. 필요한 절만 작성하고 빈 양식을 채우기 위한 내용을 만들지 않는다. 여러 요구사항의 공통 구조를 한 번 설명하며 관련 절에 R-ID를 연결한다. 결정 목록만으로 구현 설명을 대신하지 않는다.

개정할 때 기존 본문과 관련 요구사항을 읽고 영향받는 절을 수정한다. 전체 문서를 매번 다시 만들거나 과거 결정을 계속 덧붙이지 않는다. 현재 유효한 설계를 유지하고 과거 원문은 Git에서 읽는다. 관측한 구현, 확정된 방향, 미결 제안을 구분한다.

## CLI

spec save의 기존 operations에 다음을 추가한다.

```json
{"type":"set-design","feature":"posts","title":"게시물 관리 설계","body":"## 개요\n게시물의 저장과 조회 방식을 설명한다."}
```

set-design은 생성과 교체에 공통으로 쓴다. create·add·set-design을 하나의 save 요청에 담을 수 있다. S-ID 주석은 CLI가 작성한다. 신규 R-ID는 save 결과에서 얻으므로 같은 요청의 설계에서 아직 발급되지 않은 ID를 지어내지 않는다. 필요한 참조는 반환된 R-ID를 사용해 다음 save로 보완한다. 삭제는 `{"type":"delete-design","feature":"posts"}`다. expected stamp, 잠금·복구, 파일·크기·링크 검사를 요구사항과 동일하게 적용한다.

working/read는 선택적인 design 객체(title/body/requirements)를, changes/diff는 kind가 requirement 또는 design인 변경을 반환한다. 설계의 변경 ID는 S-ID다. 제목·본문 변경은 modified, 경로 이동은 moved, 생성·삭제는 created/deleted다. 변경 후 원복하면 이력도 이유도 생기지 않는다.

## 이유와 커밋

기존 JSONL `{id, requirements, reason}`을 유지하며 설계 이유에 선택적인 `designs: [S-ID]`를 추가한다. 설계만 바뀌면 requirements는 빈 배열이다. 두 배열이 모두 비어 있으면 거부한다. 같은 이유로 요구사항과 설계를 함께 연결할 수 있고 기능별 history.jsonl에 나눠 저장한다. 커밋된 이유는 수정하지 않는다. 원문·작성자·시간을 JSONL에 복제하지 않는다.

spec commit은 설계를 명세 파일로 검증하고 관련 이유·소스와 함께 커밋한다. 설계만 바뀌면 Gitifact-Req를 만들지 않고 Gitifact-Design: S-ID를 남긴다. 이유 누락은 withoutReason에 변경 ID로 표시한다. 기존 staging 보호·격리 index·줄바꿈 필터 검사·훅·서명·거부 후 이유 복구를 유지한다. deprecated 커밋 경로에는 설계 지원을 확대하지 않는다.

## 브라우저

제품 기능 상세에 요구사항/설계 탭을 둔다. tab과 선택 ID는 URL에 반영한다. 참조는 현재 전체 명세에서 R-ID를 찾아 해당 기능의 요구사항 탭으로 연결하고, 없으면 현재 명세에 없다고 표시한다. 과거 설계의 링크도 현재 항목으로 이동하며 당시 상태를 승인·구현 완료로 해석하지 않는다.

명세 이력은 요구사항·설계를 구분하며 전체/요구사항/설계, 기존 기능·작성자·변경 종류 필터를 제공한다. 같은 커밋 항목은 연속 배치하고 커밋 표시로 묶는다. 설계는 파일 전체의 변경 전후와 이유를 읽는다. 그래프는 같은 R-ID 또는 같은 설계 S-ID의 이력만 연결한다. 두 종류가 같은 커밋에 있다는 이유로 서로 연결하지 않는다.

Git 로그 조회에 design.md 경로를 추가하고 기존 커밋 10개 단위 페이지·일괄 blob 조회·고정 커밋 캐시를 유지한다. 설계마다 별도의 Git 프로세스를 호출하지 않는다. 현재 설계는 작업 폴더, 변경 이력은 커밋된 원문 기준이다. 저장 schemaVersion은 1을 유지하며 기존 설계 없는 명세와 이유를 그대로 읽는다. 새 설계 파일이 있는 저장소에는 이 기능을 지원하는 CLI를 사용해야 한다.
