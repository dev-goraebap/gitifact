# MVP 전환 계획

2026-09-14 확정한 방향을 구현하기 위한 임시 작업 문서다. 제품 원칙은 [제품 기준](bref.md), 실제 실행은 [개발 환경](development.md)을 따른다. docs에 기능별 spec을 다시 만들지 않는다. 새 형식과 CLI가 검증되면 유효한 요구사항을 `.tryce/spec/`에 등록하고 이 문서를 종료한다.

## 현재 상태

개발 CLI에 새 spec 명령과 schemaVersion: 1 초기화·스킬 설치를 연결했고 우리 프로젝트도 6개 명세·19개 요구사항으로 전환했다. 구형 원본을 별도 보관하지 않는다는 사용자 요청에 따라 기존 JSON·note·승인·설정 백업을 작업 폴더에서 제거했다. Git 과거 이력과 도입 기준선은 유지한다. 적용 범위와 실제 파일은 [자체 도입 기록](adoption.md), 지정 빌드는 [개발 환경](development.md)을 따른다.

req·note·mode·init --mode는 deprecated이며 호환 동작은 남아 있다. 정식 명령은 spec이고 spec-preview는 실험용 호환 이름이다. 새 브라우저 세 화면은 실제 Markdown·Git 조회에 연결했다. brief 연결과 범용 마이그레이션, 독립 에이전트 도입 시험은 아직 남아 있다. 이 문서는 남은 구현 작업의 임시 목록이며 기능 요구사항의 원본은 .tryce/spec이다.

## 작업 흐름

토론 → 명세·코드 수정 → 테스트 → 사용자 요청 또는 프로젝트 정책에 따른 커밋 → 요청에 따른 푸시.

작업 중 수정은 초안 편집이다. 시간 간격으로 중요도를 판단하지 않고 커밋된 최종 명세를 이력 기준으로 삼는다. 자동 기록은 자동 커밋 권한이 아니다. 정책 부재만으로 자동 커밋하는 기존 기본값은 새 스킬에서 제거한다.

커밋 직전에 에이전트가 작업 범위와 최종 명세를 대조한다. CLI는 구조·참조·저장 상태를 검사한다. 사용자 합의에 따라 관련 명세·이유·코드·테스트를 한 커밋에 담는 것이 기본이다. 프로젝트 정책이 분리를 요구하면 명세·이유를 먼저 커밋하고 구현 커밋에서 R-ID를 참조한다. 명세만 또는 코드만 바뀌는 작업도 지원한다. 기존 staging과 무관한 변경은 보존한다.

수정했다가 원래 내용으로 돌아오면 불필요한 변경 사건을 만들지 않는다. 원문 전체 스냅샷·매 대화 수정 시각·승인 원문 저장은 새 MVP에 필요하지 않다. 커밋, 구현 완료, 테스트 통과는 별개다.

직접 편집·커밋한 명세도 형식이 유효하면 읽는다. 없는 이유·관계를 추정해 채우지 않는다. 직접 커밋한 코드에서 빠진 명세를 자동으로 보완하는 훅은 MVP에 없다.

## 목표 데이터

```text
.tryce/
  config.json
  spec/
    post-management/
      requirements.md
      history.jsonl
```

| 정보 | 기준 |
| :--- | :--- |
| 현재 명세 | requirements.md의 기능 설명·ID별 요구사항·수용 조건 |
| 과거 원문·변경 전후 | Git의 해당 커밋 파일과 비교 기준 커밋 |
| 생성·수정·삭제 | 파싱한 요구사항 ID와 내용의 차이 |
| 이유·분리·통합 | history.jsonl의 최소 보조 기록 |
| 작성자·시점 | 남아 있는 Git 커밋의 author와 시각 |
| 미커밋 내용 | 현재 작업 상태, 영구 이력과 구분 |
| 조회 색인 | 재생성 가능한 로컬 캐시, Git 제외 |

history.jsonl은 스펙별로 모으고 커밋할 최종 변경을 설명한다. after/before 원문 전체를 중복 저장하지 않는다. 같은 커밋의 관련 요구사항을 묶을 수 있어야 하며 커밋 하나와 화면 행 하나가 반드시 같지는 않다.

2026-09-14 사용자 확정: 명세는 `S-<난수>`, 요구사항은 `R-<난수>`로 식별한다. 요구사항 ID에 기능 이름·경로를 넣지 않는다. 같은 요구사항의 제목·내용·소속 명세가 바뀌어도 ID를 유지한다. 전혀 다른 요구사항에 ID를 재사용하지 않는다. 난수의 길이·문자 집합과 문법은 아래 명세 작성 규칙을 따른다.

수용 조건은 일반 본문에서 다음처럼 표현한다. ID 삽입 위치는 아래 명세 작성 규칙을 따른다.

```text
조건: 게시물 항목이 선택된 상태입니다.
기대 동작: 시스템은 테두리로 선택한 항목과 선택하지 않은 항목을 구분합니다.
```

기존 선택 요구사항에 조건을 보완한다. 테두리만의 요구사항을 따로 만들거나 요청하지 않은 색상·두께를 고정하지 않는다. 항상 적용되는 규칙은 불필요한 사건을 꾸미지 않는다.

### 초기 파일 예시 — 검토안

`.tmp/spec-format-preview/initial/.tryce/spec/post-creation/`에 게시물 생성만 있는 첫 파일을 수동 작성했다. 제품 형식 확정이나 실제 프로젝트 전환이 아니다. 설명을 위해 인터뷰에서 제목·본문 필수와 등록 완료 안내를 정했다고 가정한다. 예시의 요구사항을 Tryce 제품에 등록하지 않는다. 조회·수정·삭제 기능은 아직 없다.

아래는 최초 검토 예시다. 기능의 고정 ID를 첫 주석에, 요구사항 ID를 해당 제목 바로 아래 주석에 둔다. 제목과 경로를 바꿔도 ID를 유지한다. 이후 S-/R- 길이·문자 집합과 HTML 주석 문법을 확정했다. `H-` 보조 기록은 실험 규약으로 검증 중이다.

```markdown
<!-- tryce-spec: S-k7m2xqab3d -->
# 게시물 생성

사용자가 제목과 본문을 작성해 게시물을 등록할 수 있습니다.

## 게시물 등록
<!-- tryce-req: R-v4n6paz2ce -->

사용자는 제목과 본문을 입력하여 새 게시물을 저장할 수 있습니다.

### 수용 조건

1. 조건: 사용자가 제목과 본문을 입력하고 등록을 요청합니다.
   기대 동작: 시스템은 새 게시물을 저장하고 등록 완료를 알립니다.

2. 조건: 사용자가 제목을 비운 채 등록을 요청합니다.
   기대 동작: 시스템은 제목 입력 안내를 표시하고 저장하지 않습니다.

3. 조건: 사용자가 본문을 비운 채 등록을 요청합니다.
   기대 동작: 시스템은 본문 입력 안내를 표시하고 저장하지 않습니다.
```

첫 커밋 직전에 준비할 history.jsonl의 한 줄은 아래와 같다. 사용자 대화마다 추가하지 않으며 원문·작성자·시점·생성 유형을 중복 저장하지 않는다. 이유가 실제로 확인된 경우에만 작성한다.

```jsonl
{"id":"H-b6fq2ry4ns","requirements":["R-v4n6paz2ce"],"reason":"게시물을 작성해 저장할 수 있는 기능을 첫 제품 범위로 정했습니다."}
```

일반 커밋의 연결안: 커밋과 부모에서 요구사항 ID·본문을 비교하고, 같은 커밋에 추가된 보조 기록의 requirements로 이유를 연결한다. 첫 명세라면 이전 ID 집합에 없으므로 생성으로 판단한다. 기록 자체에는 자기 커밋 해시를 넣지 않는다. 같은 이유의 여러 요구사항은 requirements 배열로 묶는다. 과거 JSONL 줄은 이후 새 변경의 이유로 다시 붙이지 않는다.

커밋 전에는 미커밋 명세와 커밋 예정 보조 정보일 뿐이다. 현재 예시는 커밋하지 않았으며 실제 Git 이력 생성·조회 검증은 아직 하지 않았다. Markdown 코드 블록 안의 가짜 주석, 중복 ID·누락 주석, 형식 버전, 의미 비교와 순서 변경, merge·squash에서 여러 보조 기록이 추가되는 경우는 후속 검증 대상이다.

### 기능 확장 예시 — 검토안

2026-09-14 사용자 요청으로 `.tmp/spec-format-preview/expanded/.tryce/spec/post-management/`에 조회·수정·삭제를 추가한 비교 자료를 만들었다. initial과 expanded는 서로 다른 시점의 예시이며 실제 저장소에서 같은 명세 ID를 가진 두 폴더를 동시에 관리하는 방식이 아니다.

| 항목 | 초기 | 확장 |
| :--- | :--- | :--- |
| 폴더 | post-creation | post-management |
| 문서 제목 | 게시물 생성 | 게시물 관리 요구사항 |
| 명세 ID | S-k7m2xqab3d | 유지 |
| 기존 등록 요구사항 | R-v4n6paz2ce | ID·본문·수용 조건 유지 |
| 조회 | 없음 | R-t3dw5hjk7m |
| 수정 | 없음 | R-b6fq2ry4ns |
| 삭제 | 없음 | R-z5cx7mp2ka |

조회는 목록과 상세를 같은 요구사항에 묶었다. 입력 필수·대상 없음 안내·삭제 확인과 취소는 설명을 위한 가정이며 실제 사용자 업무 정책으로 확정한 것이 아니다. 권한·인증·삭제 복구 정책은 예시에 포함하지 않았다. 초기 등록 요구사항은 변경하지 않고 문서 소개의 반복만 덜었다.

초기·확장 예시는 확정한 `R-<난수>` 형태로 함께 갱신했다. 실제 프로젝트의 구형 ID를 문자열 치환한 것이 아니다. 구형 CLI와 실제 .tryce 기록은 마이그레이션 검증 전까지 유지한다.

history.jsonl에는 초기 기록을 보존하고 아래 한 줄을 추가한다.

```jsonl
{"id":"H-j3hn6vb4qt","requirements":["R-t3dw5hjk7m","R-b6fq2ry4ns","R-z5cx7mp2ka"],"reason":"게시물 생성에 조회·수정·삭제를 추가하고 명세 범위를 게시물 관리로 넓혔습니다."}
```

예상 비교 결과는 같은 명세의 제목·경로 변경과 요구사항 세 개 생성이다. 기존 등록 요구사항을 삭제·재생성 또는 수정으로 표시하지 않는다. 기계 검증으로 명세 ID 유지, 기존 요구사항 본문 일치, 요구사항 ID 중복 없음, 보조 기록 두 줄의 JSON 문법·대상 참조를 확인했다. 실제 Git 커밋·rename 탐지·이력 조회는 아직 시험하지 않았다. DEV-01로 작성한 설계 예시이며 형식 확정 항목은 여전히 미완료다.

### 요구사항 이동 규칙 — 사용자 확정

R-ID는 저장소 전체에서 고유하며 같은 버전에서 원문은 한 명세에만 둔다. 다른 명세로 옮길 때 ID를 유지하고 양쪽 문서를 같은 커밋에 반영한다. Git 버전별 소속 S-ID를 비교해 이동을 판별하며 삭제·신규 생성으로 처리하지 않는다. 이동과 함께 내용이 바뀌면 두 사실을 함께 표시한다. 단순 인용은 원문 복사 대신 ID 참조로 표현한다.

요구사항을 여러 개로 분리하거나 통합하는 경우의 새 ID와 관계 규칙은 별도로 설계한다. S-/R- 문법은 아래 작성 규칙으로 확정했다. H- 보조 기록 ID와 연결 규칙은 아직 검토 중이다.

### 오배치 정정 Git 시험

2026-09-14 `.tmp/spec-move-fixture/` 독립 저장소에서 실제 이동 전후 커밋을 만들었다. 가상의 업무 예시이며 회사 프로젝트 코드·정책은 수정하거나 복제하지 않았다. 관리자 사원 관리와 사용자 본인의 내 정보 관리가 이미 나뉘어 있는데 본인 프로필 이미지 변경을 사원 관리에 잘못 넣은 상태를 정정한다. 단어가 같거나 코드 모듈이 같다는 이유로 요구사항 소속을 정하지 않는다.

- 이전: 사원 관리 S-k7m2xqab3d에 가입 승인과 본인 프로필 이미지 변경 R-b6fq2ry4ns가 있고, 내 정보 S-u2gk5wd7ra에는 본인 연락처 변경이 있다.
- 이후: R-b6fq2ry4ns를 내 정보로 옮긴다. 요구사항 ID·제목·본문·권한·수용 조건은 유지한다.
- 고정 예시 전용 판독기로 두 Git tree의 명세를 읽어 생성 0·삭제 0·이동 1·내용 변경 0을 확인했다. 소속 S-ID는 두 버전에서 도출하고 이유의 R-ID 참조도 확인했다.
- 이동 전 커밋은 시험 저장소의 5620177a871f69a33680beb8c4b90668864e3143, 이후는 288f9d881b664c821a38325e1eeffe80be843105다. Tryce 루트 커밋이 아니다.

이유는 도착 명세의 history.jsonl에 한 번 기록하는 안을 시험했다. 출발·도착 명세는 Git에서 확인하므로 보조 정보에 중복하지 않았다. 양쪽 기능 필터에서 이동을 보려면 해당 폴더의 log만 조회하지 않고 저장소 단위 ID·소속 색인을 사용해야 한다. 이 조회 기능은 아직 미구현이다.

시험 스크립트는 `.tmp/spec-move-fixture-test.cjs`, 실제 diff와 판독 결과는 시험 저장소의 comparison.diff와 result.json에 있다. 일반 Markdown 파서, merge·squash, 이동하면서 내용 수정, 손상 입력, 성능은 이번 시험 범위가 아니다. DEV-01의 설계 시험이며 CLI·제품 형식 확정이나 실제 데이터 전환이 아니다. 로컬 자료가 없는 checkout에서도 위 시나리오와 기대값으로 재작성할 수 있다.

### 구현 전 결정할 것

- Markdown 파서·정규화와 순수 서식 변경 처리.
- JSONL의 형식 버전·기록 ID·대상 ID·이유·관계 필드·크기 제한.
- 같은 커밋의 명세 차이와 보조 기록 연결. 파일에 자기 커밋 해시를 미리 넣는 방식은 사용하지 않는다.
- 재시도·실패 시 중복 방지, 동시 추가·병합 충돌, 여러 기능의 이동·통합 기록 위치.
- 루트·일반·merge 커밋 비교 기준과 정렬. 현재 checkout 브랜치 기준 조회안을 우선 검증한다.
- squash 후 누적 보조 기록과 최종 명세 차이 조합. Git에 없는 중간 원문을 복원 가능한 것처럼 표시하지 않는다.
- JSONL 장기 크기 증가·증분 조회. 파일이 적다는 이유만으로 빠르다고 간주하지 않는다.
- 구형 형식 판별·과거 읽기·쓰기 제한·전환 도구·마지막 호환 CLI 안내.

## 에이전트 스킬

tryce-workflow 하나를 진입점으로 유지하고 필요한 참고 지침을 나눈다. 맥락 확인·인터뷰·기존 기능 분석·요청 분류·명세 작성·커밋 시 최종 대조를 안내한다. ID 발급과 저장 정확성은 CLI가 책임진다.

기존 프로젝트 전체 도출은 요청받았을 때 수행한다. 일반 개발은 변경 영역부터 기록한다. 질문·예시·에이전트 제안을 사용자 확정 사항으로 꾸미지 않는다.

내부 함수 이름·단순 스타일·푸시 요청은 보통 요구사항이 아니다. 공개 API 변경·선택 표시·오류 동작·외부 서비스 의존 금지는 제품 약속과 제약이므로 명세를 확인한다. 공통 UI 규칙은 디자인 지침에 둔다.

승인·note 자동 추가·정책 부재 시 자동 커밋 안내를 제거하고 스킬 원본·배포 자산·README 프롬프트를 함께 맞춘다. 기존 사용자 스킬은 업데이트만으로 덮어쓰지 않는다. 설치 직후 현재 세션에서 읽고 기존 지침에는 최소 연결만 남긴다.

## 브라우저 MVP와 프로토타입

### 요구사항 이력

첫 화면은 최신순 생성·수정·삭제 목록이다. 기능 필터, 변경 전후와 이유, 관련 요구사항을 제공한다. 동일 요구사항의 수정과 명시적인 분리·통합을 선으로 연결한다. 같은 기능이라는 이유로 독립 요구사항을 연결하지 않는다.

상세에서 현재 기능 명세와 요구사항으로 이동한다. 과거 원문은 해당 커밋에서 읽는다. 현재 ID가 없으면 안내하고 다른 요구사항을 대신 열지 않는다.

작성자는 Git author, 아바타는 이메일 기반 로컬 생성이다. 외부에 이메일을 보내지 않는다. 그래프는 열 재사용·관계 접기로 너비를 제한하고 페이지·필터 밖 연결은 생략 표시한다. 프로토타입의 142px는 확정 규격이 아니다. 가상 스크롤·페이지 경계 연결은 아직 미구현이다.

### 제품 기능

목록 한 항목은 기능별 명세 파일이다. 선택하면 ID별 목차·본문·수용 조건을 보여준다. 기능과 하위 요구사항을 같은 목록 단위로 섞지 않는다. 제목과 실제 형식의 ID를 구분한다. 조건·기대 동작에는 불필요한 박스를 추가하지 않는다. 검색과 관련 이력 이동을 제공한다.

### 기여자

Git author 기반 인물·참여 기능·관련 활동을 보여주고 이력으로 연결한다. 이름만 같다고 합치지 않는다. 이메일·기존 .mailmap 활용을 검증하고 봇·공동 작성자·여러 이메일 처리·조회 범위를 정한다. 팀 소속·권한을 추정하지 않는다. 사건 수를 커밋 수나 구현 완료 수로 표시하지 않는다. PR·요청자·승인자 계정 관리는 제외한다.

### 참고 프로토타입

`.tmp/history-prototype/`의 index.html/history.js, features.html/features.js, contributors.html/contributors.js와 serve.cjs를 유지한다. `node .tmp/history-prototype/serve.cjs`로 실행하면 `http://127.0.0.1:4328/`에서 볼 수 있다. 단독 HTML·JavaScript와 예시 데이터이며 실제 Git·React/Astryx 통합이 아니다. 새 checkout의 필수 자료가 아니므로 위 합의를 구현 기준으로 삼는다.

기존 requirement-history-browser.md의 화면 합의는 이 절로 통합했다. 당시 제안한 승인 스냅샷·커밋 전 사건 보존은 최신 결정으로 제외한다. 별도 요약 대시보드·판단 note 화면은 추가하지 않는다.

## 작업 순서

### 첫 읽기·비교 구현 (실험용)

`spec-preview read --experimental --ref HEAD`와 `spec-preview diff --experimental --from <커밋> --to <커밋>`을 추가했다. 기본 JSON 출력의 contract는 spec-preview, version은 experimental이다. 명시한 두 커밋을 고정 해시로 해석하고 그 Git tree의 전체 명세를 읽는다. 작업 폴더·index·설정은 쓰지 않으며 형식 전환도 하지 않는다. 기존 JSON이 있으면 기존 req 명령을 안내하고 거부한다.

```sh
node <개발빌드의-절대경로>/main.js spec-preview read --experimental --ref HEAD
node <개발빌드의-절대경로>/main.js spec-preview diff --experimental --from HEAD~1 --to HEAD
```

검토 문법은 S-/R-/H- 뒤 소문자 base32 10자를 사용한다. S-/R-는 아래 작성 규칙으로 확정했고 H-는 실험용이다. 명세 첫 줄의 tryce-spec 주석, 하나의 # 제목, ## 요구사항 제목 바로 아래 tryce-req 주석을 읽는다. 본문·수용 조건은 Markdown 원문으로 제공한다. 코드 펜스 안의 제목·주석은 ID로 해석하지 않는다. 다른 HTML 주석·모호한 제목 문법·중복 ID·손상 JSONL은 거부한다. 일반 Markdown 전체 문법과 조건 쌍의 의미 검증을 지원한다고 보지 않는다.

비교 결과는 명세 수준의 제목·경로·소개 변경과 요구사항 수준의 created/deleted/moved/modified를 구분한다. 같은 요구사항의 이동과 수정은 함께 표시할 수 있다. 요구사항 제목·본문의 줄바꿈을 LF로 통일하고 블록 앞뒤 공백을 제외해 비교한다. 본문 안의 순수 서식 변경은 아직 수정으로 표시될 수 있다. 요구사항 순서만 바뀌면 변경 사건을 만들지 않는다.

새 JSONL 기록만 이번 변경의 이유로 연결하며 대상은 이번에 바뀐 요구사항 ID여야 한다. 과거 이유의 참조는 이후 삭제·이동된 요구사항일 수 있으므로 현재 명세에 없다는 이유로 거부하지 않는다. 과거 기록 ID를 그대로 두고 내용을 바꾸면 비교를 거부한다. 명세 전체 제거에 따른 보조 기록 삭제 정책·분리/통합 문법·여러 커밋을 건너뛴 이유 연결은 후속 설계 대상이다. 무관한 커밋 구간의 보조 기록이 최종 변경과 맞지 않으면 이 실험 명령은 오류로 반환할 수 있다.

조회 상한은 파일당 1 MiB, 전체 객체 본문 16 MiB, 관련 파일 2,000개, Git 호출 출력 32 MiB·15초다. 객체는 최대 16개씩 묶어 읽는다. 이는 안전한 검토용 실행 한도이며 장기 이력 성능 목표가 아니다. 얕은 저장소의 없는 커밋을 자동 fetch하지 않는다. Git의 컨텍스트 덮어쓰기 환경과 명세 영역의 링크·서브모듈은 거부한다.

고정 테스트는 core의 spec-preview.test.mjs와 CLI의 spec-preview.test.mjs에 두었다. 파싱·CRLF·펜스 속 가짜 ID·중복·누락·생성·삭제·제목 변경·원복·이동·이동+수정·이유 연결·구형 거부를 확인한다. SHA-1/SHA-256 임시 저장소에서 커밋 조회·하위 경로 실행·현재 파일과 index 보존을 확인했다. 실제 Git merge·squash·linked worktree·대규모 성능 시험은 아직 미실행이다. 기존 .tryce는 전환하지 않았다.

읽기·비교에 이어 아래 초안 저장과 커밋 이유 준비·원문 검증·실험용 커밋 실행을 연결했다. 프로젝트 사용 지정·마이그레이션·색인·브라우저 연결과 최종 보조 기록 규약은 미완료다.

### 명세 작성 규칙 — 사용자 확정

명세 ID는 `S-<난수>`, 요구사항 ID는 `R-<난수>`다. 난수는 `abcdefghijklmnopqrstuvwxyz234567` 중 10자를 사용한다. 문서 첫 줄에 `<!-- tryce-spec: S-... -->`, 각 `## 요구사항 제목` 바로 다음 줄에 `<!-- tryce-req: R-... -->`를 둔다. frontmatter는 도입하지 않는다. 필요한 메타데이터가 생기면 다시 검토한다.

CLI가 난수를 발급하고 저장소의 현재 명세 전체에서 중복을 검사한다. 제목·내용·소속 변경에는 기존 ID를 유지하고 다른 요구사항에 ID를 재사용하지 않는다. 번호나 제목을 ID로 사용하지 않는다. 다른 브랜치와의 병합 충돌 검사는 커밋·병합 검증 단계에서 보완한다.

### 초안 생성·수정·이동 구현 (실험용)

에이전트는 `spec-preview working --experimental`로 현재 Markdown과 `stamp`를 읽고 `spec-preview save --experimental --file <입력.json>`으로 편집한다. 입력은 읽었던 stamp를 넣은 `expected`와 `operations` 배열이다. expected는 승인 기록이 아니라 다른 편집을 덮어쓰지 않기 위한 상태 검사다. CLI가 ID를 발급하고 저장 결과에 반환한다. 새 프로젝트의 Git 저장소에서 초기 커밋 전에도 실행할 수 있다.

```json
{
  "expected": "working이 반환한 stamp",
  "operations": [
    { "type": "create", "feature": "posts", "title": "게시물 관리 요구사항" },
    {
      "type": "add", "feature": "posts", "title": "게시물 등록",
      "body": "사용자는 게시물을 저장할 수 있습니다.\n\n### 수용 조건\n\n1. 조건: 제목을 비운 채 등록을 요청합니다.\n   기대 동작: 제목 입력을 안내하고 저장하지 않습니다."
    }
  ]
}
```

| type | 필드 | 동작 |
| :--- | :--- | :--- |
| create | feature, title, 선택 description | 명세 생성, S-ID 발급 |
| add | feature, title, body | 요구사항 추가, R-ID 발급 |
| update | id(R-ID), title, body | 기존 요구사항 제목·본문 교체 |
| move | id(R-ID), feature | 대상 명세 끝으로 원문 이동, ID 유지 |
| rename-spec | id(S-ID), title | 문서 제목 변경, ID 유지 |

여러 작업은 입력 순서대로 계산한 뒤 전체 결과를 검증한다. feature는 소문자 영문으로 시작하는 영문·숫자·하이픈 조합(최대 80자, Windows 예약 이름 제외)이다. 저장되는 파일은 requirements.md뿐이며 기존 history.jsonl을 수정하거나 새로 만들지 않는다. 변경한 문서는 LF와 일정한 제목 간격으로 출력하고, 건드리지 않은 문서는 원문 바이트를 보존한다. 요구사항의 조건·기대 동작은 body의 Markdown이며 제품 의미나 수용 조건의 충분함을 CLI가 판정하지 않는다.

작업 폴더 전체의 중복 ID·잘못된 구조·UTF-8·경로와 크기를 검사한다. 본문으로 다른 요구사항 제목이나 식별자를 삽입하는 입력은 거부한다. 현재 설정 파일 또는 구형 specs 디렉터리가 있으면 실험 쓰기를 거부한다. 기존 프로젝트를 몰래 전환하는 진입점이 아니다. Git HEAD와 index, 사용자 설정은 변경하지 않으며 커밋을 만들지 않는다.

저장 중에는 현재 worktree의 Git 디렉터리에 tryce-spec-preview.lock을 만들고 변경 전후 원문을 recovery.json에 보존한다. 임시 파일 준비 후 기존 상태를 다시 확인하고 파일별 rename으로 반영한다. 감지한 오류에서는 원문을 복구한다. 다른 편집이 들어와 복구할 수 없으면 이를 보존하고 잠금·복구 자료를 남긴다. 정상 실행 후 잠금은 제거한다.

여러 파일을 운영체제 차원에서 한 번에 바꾸는 트랜잭션은 아니다. 명령을 강제로 종료하면 잠금과 중간 상태가 남을 수 있다. 복구 자료와 실제 파일을 대조하기 전 잠금을 지우거나 다시 저장하지 않는다. 자동 crash 복구 명령·전원 장애 내구성·외부 에디터와의 모든 경쟁 상태는 아직 지원·검증하지 않았다. 실험 단계에서는 중단 시 수동 복구가 필요하며 실제 .tryce의 쓰기 도구로 지정하지 않는다.

고정 테스트는 core의 edit-spec-preview.test.mjs와 CLI의 spec-preview-write.test.mjs다. 생성·수정·이동, ID 충돌 재발급, 잘못된 본문·중복·오래된 expected 거부, SHA-1/SHA-256, Git staging 보존, 두 번째 파일 저장 실패 시 CRLF 원문 복구, 외부 편집 보존·복구 자료 유지, 구형 형식·디렉터리 링크 거부를 검사한다. 요구사항 삭제·폴더 이름 변경의 전용 편집 명령은 후속 작업이며, 직접 편집한 삭제·이동은 유효한 문법이면 비교한다.

### 커밋 이유 준비와 최종 원문 확인 (실험용)

기존 예시의 `id`, `requirements`, `reason` 세 필드를 사용한다. H-ID는 소문자 base32 10자를 발급하고 기존 기록과 충돌하면 재발급한다. 분리·통합 관계와 최종 형식 버전은 이번 구현에서 고정하지 않았다. 에이전트가 확인한 이유를 전달하며 CLI가 대화의 의미나 커밋 권한을 대신 판단하지 않는다.

1. `spec-preview changes --experimental`: 현재 HEAD와 작업 폴더의 최종 명세 차이와 미커밋 이유(pendingReasons)를 읽는다. 초기 커밋 전에는 이전 명세를 빈 집합으로 본다. `expected`는 HEAD·브랜치·현재 명세/이유 파일 상태에 묶인 값이다.
2. `spec-preview prepare --experimental --file <입력.json>`: expected와 최종 reasons를 받아 필요한 history.jsonl만 준비한다. requirements.md·설정·index·HEAD는 수정하지 않는다.
3. `spec-preview verify --experimental --file <검증.json> --staged`: prepare가 반환한 verification 객체로 원문과 HEAD가 그대로인지, staging의 모든 명세·이유 파일이 같은 바이트인지 검사한다. staged를 생략하면 작업 폴더만 검사한다.

```json
{
  "expected": "changes가 반환한 expected",
  "reasons": [
    { "requirements": ["R-v4n6paz2ce"], "reason": "제목 없이 게시물이 저장되는 것을 방지합니다." }
  ]
}
```

reasons는 이번 커밋에 넣을 최종 이유 전체다. 한 이유에 여러 요구사항을 묶을 수 있으며 기능이 다르면 기능별로 나눠 저장한다. 같은 요구사항을 두 이유에 중복 지정하거나 최종 차이가 없는 ID를 지정하면 거부한다. 모르는 이유는 만들어 넣지 않는다. 이유가 없는 변경은 withoutReason에 표시하며 이유가 없어도 명세 비교는 가능하다.

이미 커밋된 JSONL 바이트를 원문 그대로 보존하고 미커밋 부분만 최종 reasons로 교체한다. 이는 새 자동 기록 정책의 초안 정리이며 커밋된 이력 수정이 아니다. 수동으로 적은 미커밋 이유도 이 범위에 포함하므로 changes로 현재 내용을 확인한 에이전트가 유지할 이유를 함께 전달해야 한다. 같은 내용으로 다시 준비하면 기존 미커밋 H-ID를 재사용하며 같은 줄을 추가하지 않는다. 이전 expected로 그대로 재시도하면 상태 변경을 알리고 거부한다.

수정·원복 후 최종 요구사항 차이가 없으면 새 이유를 만들지 않는다. `reasons: []`로 다시 준비하면 미커밋 이유를 제거하고 커밋된 이유만 남긴다. 새 history 파일에 남길 줄이 없으면 파일 자체를 제거한다. 과거 이유 수정·삭제·다른 명세로 재배치는 거부한다.

이동 이유는 도착 명세에, 삭제 이유는 원래 명세에 저장한다. 같은 커밋의 전후 S-ID와 R-ID로 양쪽 기능을 찾으며 이유에 출발·도착 원문을 중복하지 않는다. 삭제 이유나 과거 이유가 있는 기능은 빈 requirements.md를 남겨 보존한다. 기능 전체와 그 이력을 제거하는 정책은 아직 지원하지 않는다.

prepare 결과의 paths는 이번에 실제로 쓴 이유 파일이며 커밋할 모든 파일 목록이 아니다. 직접 Git으로 커밋할 때는 명세 양쪽과 이유를 함께 staging한 뒤 verify --staged로 확인할 수 있다. 아래 commit-plan/apply를 사용할 때는 미리 staging하지 않는다. 실행기가 별도 index에서 staging하고 검사한다. Git 필터나 줄바꿈 변환 때문에 index 원문이 다르면 명세 검증이 실패한다. 무관한 staging은 변경하지 않으며 포함 여부와 커밋 분리는 프로젝트 정책에 따라 별도로 결정한다.

changes·prepare·verify는 커밋을 실행하지 않는다. verify 성공은 그 시점의 원문 일치이며 사용자 승인·구현 완료·실제 커밋 성공을 뜻하지 않는다. 실제 실행은 아래 commit-plan/apply로 연결한다. 진행 중인 merge·rebase·cherry-pick·revert는 거부하고, merge 비교·squash 이후 누적 이유 연결은 아직 별도 범위다. 저장 실패 시 복구는 기존 실험용 초안 저장과 같은 잠금·원문 보존 절차를 사용한다.

추적된 spec-preview-prepare.test.mjs에서 초기 커밋, 여러 번 수정 후 최종 한 건, 재준비 중복 방지, 원복과 미커밋 이유 제거, 커밋된 CRLF 원문 보존, 이유 누락 표시, 이동·삭제, 두 파일 중 두 번째 저장 실패 복구, HEAD 변경·통합 작업 거부, SHA-1/SHA-256 staging과 실제 커밋 후 diff 연결을 시험한다.

### 관련 파일의 커밋 실행 (실험용)

`spec-preview commit-plan --experimental --file <입력.json>`으로 정확한 파일 범위를 정하고, 반환된 plan 객체를 `spec-preview commit-apply --experimental --file <계획.json>`에 전달한다. 두 명령은 에이전트 내부의 준비·실행 절차이며 사용자에게 별도의 단계별 승인을 요구하는 기능이 아니다.

```json
{
  "verification": { "base": { "head": null, "branch": "refs/heads/main" }, "stamp": "prepare의 실제 반환값" },
  "paths": [".tryce/spec/posts/requirements.md", ".tryce/spec/posts/history.jsonl", "src/posts.ts", "test/posts.test.ts"],
  "message": "게시물 제목을 필수로 처리",
  "authorization": { "basis": "user-request", "evidence": "현재 작업에 대한 사용자 커밋 요청" }
}
```

verification은 예시를 조립하지 않고 prepare의 반환 객체를 그대로 사용한다. authorization.basis는 user-request 또는 project-policy이며 evidence에는 실제 근거를 적는다. 정책이 없다는 이유만으로 커밋하지 않는다. CLI는 그 근거의 자연어 의미나 현재 사용자 권한을 인증하지 않으며 에이전트가 판단한다.

paths는 에이전트가 확인한 관련 파일만 명시한다. 이 첫 구현은 미커밋 명세·이유 파일 전체가 선택됐는지 검사하고 빠진 파일을 자동 추가하지 않는다. 여러 작업의 미커밋 명세 중 일부만 커밋하는 범위 선택은 아직 지원하지 않는다. 기존 staging 또는 intent-to-add가 있으면 내용을 보존하고 보류한다. 기존 staging을 지우거나 강제로 전체 파일을 묶지 않는다.

분리 정책이면 명세·이유 경로만 선택해 먼저 커밋한다. 이후 현재 상태에서 prepare를 다시 하고 코드·테스트만 선택하며 requirements 배열에 관련 R-ID를 전달한다. 명세 변경이 있는 커밋에는 변경된 R-ID를 자동 참조하고 추가 requirements는 실제 존재하는 ID인지 검사한다. 메시지의 Tryce-Req 트레일러는 연결 정보이며 구현 완료 선언이 아니다. 구형 workflow-1을 새 형식으로 가장하는 트레일러는 생성하지 않는다.

계획은 HEAD·명세 상태·선택 파일·기존 index·루트와 하위 AGENTS.md/CLAUDE.md·스킬·ignore/attributes 내용을 묶는다. 추가 정책 파일은 policyFiles로 지정한다. 실행 시 다시 계획을 대조하고 잠금 아래 원문과 명세 집합을 재검사한다. 별도 index에 선택 파일만 staging하며 Git 필터가 명세·이유 바이트를 바꾸면 실행하지 않는다. 소스코드의 Git 필터와 저장소 훅·서명 설정은 따른다.

Git 커밋 후 실제 tree·부모·브랜치·R-ID 참조·임시 index를 확인하고 원래 index에 반영한다. 무관한 작업 파일은 건드리지 않는다. 기존 staging이 없는 상태에서 시작하며 관계없는 index 플래그는 복사본을 통해 보존한다. 파일은 최대 128개, 파일당 16 MiB로 제한한다. 링크·서브모듈·중첩 저장소의 파일은 자동 커밋 대상에서 제외한다.

커밋이 거부되고 HEAD가 그대로면 소유한 임시 index와 잠금을 정리하고 원래 index를 유지한다. 파일·명세·정책이 그대로라면 같은 계획으로 재시도할 수 있다. 성공한 계획의 재실행은 HEAD 변경으로 거부하므로 중복 커밋을 만들지 않는다. 실행 후 HEAD가 바뀌었는데 결과 검증에 실패하면 Git 디렉터리의 tryce-spec-commit.lock/recovery.json과 index·명세 잠금을 남기고 재시도를 막는다. 실제 HEAD·원래 index 백업·임시 index를 대조한 뒤 복구하며 이미 생성된 커밋을 자동 reset하지 않는다. 강제 종료·전원 장애 후 자동 복구는 아직 미지원이다.

### 단일 커밋 명령 spec commit

2026-09-15 `spec commit --file <입력.json> [--dry-run]`을 추가했다. `prepare`·`verify`·`commit-plan`·`commit-apply`는 deprecated로 표시하고 0.6.0에서 제거한다. 위 두 절의 저장·검사 규칙은 새 명령에서도 유지한다.

실제 tryce 커밋 두 건(0.4.0 릴리스, 브라우저 MVP)은 네 명령을 스크립트로 연속 호출했다. 이유와 파일 범위는 changes 전에 이미 정해져 있었고 명령 사이에 에이전트 판단이 없었다. 명령을 프로세스별로 나눈 구조 때문에 expected·verification·plan을 넘기며 매번 상태 전체를 다시 읽었다. Windows에서는 한 커밋에 Git 프로세스가 237~265회 실행돼 14~23초가 걸렸다. 측정 방법과 결과는 [개발 환경](development.md#2026-09-15-커밋-성능과-단일-커밋-명령)에 둔다.

```json
{
  "reasons": [{ "requirements": ["R-v4n6paz2ce"], "reason": "제목 없이 게시물이 저장되는 것을 방지합니다." }],
  "paths": [".tryce/spec/posts/requirements.md", ".tryce/spec/posts/history.jsonl", "src/posts.ts"],
  "message": "게시물 제목을 필수로 처리",
  "authorization": { "basis": "user-request", "evidence": "현재 작업에 대한 사용자 커밋 요청" }
}
```

선택 필드는 requirements·policyFiles·expected다. reasons는 prepare와 같이 남길 미커밋 이유 전체이며, 생략하면 이미 준비된 미커밋 이유를 유지한다. expected를 넘기면 changes 이후의 명세 변경을 거부한다. 기록할 이유가 없는 history.jsonl 선택은 staging에서 건너뛴다. dry-run은 이유 검증·선택 범위·기존 staging 검사까지 수행하고 파일을 쓰거나 커밋하지 않는다.

- **이유 누락은 경고한다.** 요구사항 변경에 이유가 없어도 커밋하고 withoutReason으로 표시한다. 대부분의 커밋에 이유가 있을 것으로 보고, 자료가 없다는 이유로 오류를 만들지 않는다. 불편이 확인되면 다시 검토한다. 거부와 입력 옵션으로 허용하는 방식은 기각했다.
- **거부된 커밋은 이유 파일을 되돌린다.** HEAD가 그대로면 이번에 쓴 history.jsonl을 실행 전으로 돌려, 명령이 커밋되거나 아무것도 바뀌지 않는 단위가 되게 한다. 그사이 다른 프로세스가 파일을 고쳤으면 되돌리지 않고 명세 잠금과 복구 자료를 남긴다. HEAD가 바뀐 불확실한 결과는 파일·잠금·복구 자료를 모두 보존한다. 이유 파일을 남겨 두는 기존 방식과, 커밋 성공 후에만 작업 폴더에 쓰는 방식은 기각했다. 후자는 작업 폴더를 읽는 훅이 이유 파일을 보지 못하고, 커밋 후 쓰기에 실패하면 작업 폴더가 HEAD와 어긋난다.
- **줄바꿈은 Git 기준으로 판단한다.** 명세·이유 파일의 변경 여부는 바이트가 아니라 Git이 저장할 blob ID로 비교한다(`git hash-object --stdin-paths` 한 번). core.autocrlf=true 등으로 LF blob이 CRLF로 checkout돼도 변경으로 보지 않고, 같은 내용으로 저장될 이유 파일은 다시 쓰지 않는다. staging 후 필터 검사는 CRLF→LF 줄바꿈 변환만 허용하고 그 밖의 내용 변경은 계속 거부한다. 비교 직전 tryce가 줄바꿈을 직접 무시하는 방식은 .gitattributes·필터 규칙과 어긋날 수 있어 기각했다. `.gitattributes`의 eol=lf로 checkout을 LF로 고정하는 예방책은 init이 사용자 저장소에 파일을 추가하는 결정이라 보류했다. deprecated commit-plan에는 적용하지 않았다.
- **유지한 검사:** 기존 staging·intent-to-add 보류, 미선택 명세 거부, 명세 잠금 아래 원문·명세 집합·index·HEAD 재대조, 격리 index와 Git 필터 검사, 훅·서명, 커밋 tree·부모·트레일러 검증, 원래 index 보존.
- **줄인 조회:** 한 명령 안에서 바뀌지 않는 저장소 위치는 명령 단위로 한 번 읽는다. HEAD 확인은 기존 시점을 유지하되 한 번에 Git 프로세스 2개를 동시에 쓴다. spec 명령의 사전 검사는 전체 status 대신 위치·진행 중인 작업·충돌·기준선만 확인한다. 실행 전 계획 전체를 다시 만들지 않는다.

## 기존 데이터 전환

## 2026-09-14 설정과 과거 호환성 결정

config.json의 kind와 format: spec-1을 제거하고 schemaVersion: 1로 정리했다. baseline은 유지한다. 사용자 요청에 따라 1.0.0 전 과거 규약을 계속 유지하는 설계를 우선하지 않는다. 1.0.0 이후 충돌하는 변경은 마이그레이션 지원 범위를 정한다. 이번 브라우저는 현재 Markdown 규약을 읽으며 구형 JSON 이전 원문은 Git 이력에서만 확인한다.
