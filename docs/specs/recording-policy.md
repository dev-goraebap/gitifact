# 자동모드와 승인모드

사용자는 자신의 작업 방식에 따라 요구사항을 자동으로 정리하며 진행하거나, 구현 전에 확인받도록 선택한다. 제품의 개발 단계와 기록·확인 정책을 분리한다.

상태: 2026-09-13 사용자 응답을 반영한 동작 명세. 명칭과 아래 기본 동작을 채택한다. CLI 0.1.0에는 아직 구현되지 않았으며, 현재 init-1·prototype-1 설정의 의미를 바꾸지 않는다.

## 두 모드

| 항목 | 자동모드 (`auto`) | 승인모드 (`approval`) |
| :--- | :--- | :--- |
| 신규 도입 기본값 | 기본값이며 도입 시 짧게 알림 | 사용자 선택 시 적용 |
| 초안 수집 | 의미 있는 대화를 묶어 기록 | 동일 |
| 구현 기준 확정 | 사용자 의도와 범위가 명확하면 에이전트가 정리해 진행 | 관련 초안을 묶어 보여주고 사용자 확인 후 진행 |
| 불명확한 제품 동작 | 질문하고 해당 부분은 초안으로 유지 | 동일 |
| note | 발견·제약·기각 이유를 필요한 때 기록 | 동일, note마다 승인받지 않음 |
| 사용자 승인 표시 | 실제로 받은 승인이 있을 때만 표시 | 확인한 정확한 내용에 연결 |
| Git 커밋 | 프로젝트 커밋 정책에 따라 별도로 판단 | 동일 |

`approval`은 계획만 세우고 구현하지 않는 상태가 아니다. 요구사항을 확인받은 뒤 구현·기록까지 이어가는 정책이므로 `plan`이라는 이름을 사용하지 않는다. auto도 사용자 의도와 무관한 기능을 임의로 추가할 권한은 아니다.

자동모드에서는 초안을 구현 기준으로 확정하는 사건과 사용자 승인 사건을 구분한다. 이후 요구사항 조회에서 누가 어떤 근거로 정리했고, 별도 사용자 승인이 있었는지 알 수 있어야 한다. 요구사항이 활성 상태라는 이유로 승인·구현·검증 완료를 표시하지 않는다.

## 질문이 필요한 때

모호함이 제품 동작이나 작업 범위를 바꾸면 에이전트가 질문한다. 사소하고 되돌릴 수 있는 구현 선택까지 사용자에게 넘기는 정책은 아니다. 답이 필요한 부분만 보류하고 독립적으로 진행할 수 있는 작업은 계속한다.

승인모드는 [요구사항 수집](requirement-capture.md)의 묶음 확인을 따른다. 사용자가 실제로 본 대상과 현재 내용이 다르면 이전 답변을 변경본의 승인으로 쓰지 않는다. 배포·삭제·원격 푸시 등의 실행 권한은 기록 모드와 별개이며, 기존 프로젝트 지침이나 사용자 요청이 요구하는 확인을 auto로 생략하지 않는다.

## 모드 변경과 과거 기록

모드 변경은 사용자가 요청한 선택으로 기록하고 변경 이후 작업부터 적용한다. 에이전트가 승인 대기를 피하려고 임의로 auto로 바꾸지 않는다. 팀의 명시적 승인 의무와 프로젝트 지침도 유지한다.

auto에서 approval로 바꾸어도 기존 요구사항을 일괄 승인 대기로 돌리거나 승인됨으로 표시하지 않는다. 이후 기존 요구사항을 수정하면 수정 내용을 묶어서 확인받는다. approval에서 auto로 바꾸어도 미승인 초안이 자동 승인되는 것은 아니다. 에이전트가 현재 의도와 남은 질문을 검토한 뒤 auto 규칙으로 확정할 수 있으며, 실제 사용자 승인은 별도로 남는다.

과거 사건은 당시 정책과 근거로 해석한다. 현재 모드를 이용해 과거 승인을 만들거나 기존 기록의 의미를 다시 쓰지 않는다.

## note와 요구사항

note는 프로젝트 단계에 상관없이 필요한 발견·제약·기각 이유다. 요구사항은 사용자가 원하는 제품 동작과 유지할 조건이다. 둘 다 남길 이유가 있을 때는 서로 연결하되 동일한 대화를 기계적으로 이중 기록하지 않는다. note를 요구사항 초안의 근거로 삼아도 원래 기록은 보존한다.

스킬은 두 모드에서 모두 note를 사용하고, 요구사항의 확정·확인에 모드 정책을 적용한다. CLI의 구조 검증과 파일 보존은 두 모드에서 동일하게 유지한다. 향후 진단의 표시 강도는 별도 설정으로 설계하며, auto를 검사 생략 모드로 취급하지 않는다.

## Git 커밋 정책

사용자의 명시적인 커밋 시점·메시지 형식·브랜치·서명·리뷰 규칙을 우선한다. 이번 작업에서 받은 커밋 지시도 함께 적용한다. 규칙을 확인했으나 커밋 정책이 없는 경우에는 관련 작업 단위가 정리됐을 때 에이전트가 자동 커밋하는 것을 기본으로 한다. 정책을 읽지 못한 상태를 정책 없음으로 취급하지 않는다. 모순된 지침의 우선순위를 판단할 수 없다면 해당 커밋만 보류한다.

초안 한 줄을 고칠 때마다 커밋하지 않는다. 요구사항·결정 묶음이 정리되거나 관련 구현과 필요한 검증을 마친 때 커밋한다. 구현이 중단돼도 독립적으로 확정된 기록을 남길 이유가 있으면 기록만 커밋할 수 있다. 승인모드에서 초안 자체를 보존하는 커밋은 승인이나 구현 허용을 뜻하지 않는다. 사용자 정책이 승인을 받은 뒤의 커밋만 허용하면 그 정책을 따른다.

관련 기록과 코드는 같은 변경으로 커밋할 수 있다. 기록 전용 커밋과 코드 전용 커밋을 항상 강제하지 않는다. 다만 다음 조건은 유지한다.

- 커밋 후보의 정확한 파일·내용과 해당 작업과의 관계를 확인한다. 관련 없는 변경은 포함하지 않는다.
- 사용자가 미리 stage한 파일을 임의로 커밋·unstage·재stage하지 않는다. 첫 자동 커밋 구현은 기존 index 변경이 있거나 변경 주체가 불명확하면 자동 구성을 중단하고 준비한 범위와 이유를 알린다.
- 같은 파일에 사용자 변경과 작업 변경이 섞여 있거나 부분 staging이 있으면 파일 전체를 추가하는 방식으로 우회하지 않는다.
- 승인 대상·요구사항·참조가 빠졌거나 서로 불일치하면 완전한 기록으로 커밋됐다고 표시하지 않는다. 기록과 코드가 따로 있어도 필요한 관계를 검증해야 한다.
- 커밋 직전 HEAD·index·대상 파일의 변경을 확인한다. 경쟁 변경·훅·서명 실패 시 검사를 끄거나 사용자 파일을 되돌려 재시도하지 않는다.
- 커밋 결과의 실제 객체와 포함 내용을 확인하고 파일 저장·미커밋·커밋됨을 구분한다. 자동 원격 푸시는 포함하지 않는다.

명시적 사용자 정책과 위 보존 조건을 함께 만족할 수 없으면 충돌 이유와 준비된 기록을 보여준다. 사용자가 직접 만든 커밋까지 로컬 훅으로 항상 통제할 수 있다고 약속하지 않는다. tryce 경로는 사전 검증하고 직접 Git을 사용한 기록은 향후 사후 검사로 진단한다. 팀의 필수 CI 검사는 별도 선택이다.

## 기존 형식에서의 전환

기존 `prototype / normal`을 각각 auto/approval로 자동 치환하지 않는다. 이전 값은 다른 의미의 정책이었으므로 새 기본값과 기존 사용자의 선택을 혼동하지 않는다. 기존 설정을 읽는 기능은 유지하고, 새 정책 도입은 선택할 모드를 명시하는 전환으로 구현한다.

전환 시 설정 원문과 기준선·note를 보존하고 새 형식 식별자를 사용한다. 설치·업데이트나 단순 조회로 전환하지 않는다. 새 도입에는 auto를 기본으로 제공하되 프로젝트 정책을 먼저 확인한다. 과거 기록의 형식은 재작성하지 않는다. 현재 Tryce 저장소와 .tmp/demo는 이 문서 작성으로 전환되지 않는다.

## 구현과 검증 순서

1. 새 정책의 설정·조회·명시적 전환과 기존 형식 읽기, 양쪽 모드의 note 지원을 구현한다.
2. 요구사항 초안·확정·묶음 승인과 현재 세션의 스킬 적용을 연결한다.
3. 프로젝트 정책을 반영한 커밋 후보 검증·실행·결과 확인을 연결한다.
4. 실제 저장소 사례에서 사용자의 기존 변경 보존과 세션 간 맥락 전달을 검증한다.

검증에는 신규 auto 기본값, 모호한 의도의 미확정, 두 모드의 note, 전환 원문 보존·중단 복구, 과거 승인 비소급, 오래된 묶음에 대한 승인 거부, 커밋 금지 정책, 정책 없음의 자동 커밋, 기존 staging·부분 staging·동시 수정·훅 실패를 포함한다. 이는 구현할 검사이며 현재 테스트 통과를 뜻하지 않는다.

CLI와 스킬을 통해 수집·조회·승인·Git 연결이 모두 동작하면 GUI 없이 사용하는 범위를 검증한다. GUI는 동일한 기록을 사람이 살펴보는 후속 화면이다. README 도입 프롬프트의 별도 새 세션 시험은 사용자가 요청한 순서에 따라 이 정책·기록 기능 이후에 진행한다.
