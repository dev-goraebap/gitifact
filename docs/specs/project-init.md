# 프로젝트 초기화

`tryce init`은 현재 checkout에 프로젝트 설정과 도입 기준선을 만든다. 기존 코드를 요구사항으로 변환하지 않으며, 이후 기록을 시작할 경계를 남긴다.

상태: 첫 개발용 구현 명세. 2026-09-13 사용자가 네 가지 초기화 방향을 승인했다. 설정 위치·기준선·초기 모드·설정만 생성하는 범위를 채택했고, 정확한 저장·출력 형식은 [init-1](project-format.md)에 정의한다. 전체 요구사항 기록 형식과 스킬·훅 연동은 아직 지원하지 않는다.

## 기존 기준과 첫 구현 범위

| 항목 | 기존 기준 | 이번 범위 |
| :--- | :--- | :--- |
| 도입 기준선 | 이전 커밋을 추적 누락으로 집계하지 않고 재실행 시 보존 | 기준선 기록과 유효성 확인 |
| 프로젝트 설정 | `.tryce/`에 설정과 재생성 캐시를 구분 | 설정만 생성, 캐시는 필요한 기능에서 생성 |
| 요구사항 | `specs/<spec>/`에 문서와 spec 메타 배치 | 초기화에서 빈 spec이나 요구사항 ID를 만들지 않음 |
| 스킬 | `.agents/skills/tryce-*`가 원본, 관리 관계를 명시 | 배포 매니페스트와 sync 명세 이후 구현 |
| 사용자 파일 | 지침·스킬·기존 변경을 보존 | 기존 파일을 자동 수정하거나 덮어쓰지 않음 |
| 호환성 | CLI·영속 형식·출력 계약 버전을 구분 | 미지원 형식의 쓰기 거부 |

첫 구현은 프로젝트 기록을 시작하기 위한 초기화다. 스킬 설치, 에이전트 지침 연결, 훅 설치까지 끝났다는 의미로 사용하지 않는다. 성공 출력에도 각 연동이 미설치임을 구분한다. Git stage·commit과 전역 설정 변경은 수행하지 않는다.

## 파일 구성

첫 초기화는 checkout 루트에 `.tryce/config.json` 한 파일을 만든다. `.tryce/` 전체를 gitignore하지 않으며 설정은 Git에 커밋할 프로젝트 기록으로 취급한다. 생성 성공과 커밋 완료는 별개다.

```text
.tryce/
  config.json       프로젝트 설정과 도입 기준선, Git 추적 대상
```

캐시는 필요해질 때 `.tryce/cache/`에 추가하고 해당 경로만 무시한다. 첫 init은 빈 캐시·spec·스킬 폴더나 루트 `.gitignore` 수정분을 만들지 않는다. 재생성할 수 없는 설정과 기준선을 캐시에 보관하지 않는다.

설정 경로가 기존 ignore 규칙으로 제외되면 변경 전에 해당 규칙을 안내하고 중단한다. 사용자 ignore 규칙을 자동으로 고치거나 강제 stage하지 않는다. 기존 `specs/`, `docs/`, `.agents/`, `AGENTS.md`가 있더라도 읽어 들여 변환하거나 소유권을 주장하지 않는다.

설정에는 다음 정보만 기록한다. 첫 개발 형식 init-1은 설정만 지원하며 전체 기록 형식으로의 전환은 별도 명령으로 제공한다.

| 정보 | 의미 |
| :--- | :--- |
| 문서 종류 | tryce 프로젝트 설정임을 식별 |
| 영속 형식 | 설정·요구사항·메타·트레일러·생성 규약의 호환 조합 참조 |
| 프로젝트 모드 | `normal` 또는 `prototype` |
| 기준선 종류 | 특정 커밋까지 제외하거나, 기존 커밋이 없는 시작 |
| 기준선 커밋 | 커밋 기준선일 때만 전체 object ID와 Git object format |

CLI 버전, 로컬 절대 경로, 원격 URL, 브랜치 이름을 프로젝트의 영속 식별자로 쓰지 않는다. 현재 status의 `repo:`·`worktree:` 키와 브라우저 sessionId는 로컬 관측용이므로 설정으로 복사하지 않는다. 별도의 프로젝트 UUID는 실제 소비 기능과 clone·fork 의미를 정한 뒤 검토한다.

영속 형식은 출력 계약 `repository-status` 버전과 독립적이다. 최소 init을 먼저 시험하더라도 설정만 정한 상태를 전체 영속 형식의 완성이나 공개로 표시하지 않는다. 첫 형식의 지원 범위와 후속 기록 형식의 추가·전환 방식을 명세한 뒤 쓰기 구현에 연결한다.

## 도입 기준선

커밋이 있는 저장소에서는 초기화 계획을 만들 때의 HEAD를 기준선으로 기록한다. 기준선 커밋 **자신과 그 조상**은 추적 누락 검사에서 제외한다. 시간이나 브랜치 이름으로 경계를 계산하지 않는다. 적용 직전에 HEAD가 달라졌다면 쓰지 않고 새 계획이 필요하다고 알린다.

예를 들어 `A → B → C`에서 초기화했다면 C를 기록한다. 이후 D에 설정과 작업을 커밋하더라도 기준선을 D로 옮기지 않는다. 초기화 재실행, CLI 업데이트, 설정 파일의 새 커밋으로도 기준선을 자동 변경하지 않는다.

기준선은 기존 이력을 소급해 추적 누락으로 집계하지 않기 위한 경계다. 기존 코드의 승인·테스트 통과·구현 완료를 뜻하지 않는다. 기준선 이전에 명시적으로 존재하는 tryce 기록을 삭제하거나 형식 오류까지 숨기는 근거도 아니다.

| 상황 | 동작 |
| :--- | :--- |
| HEAD가 커밋을 가리킴 | 해당 커밋까지 기존 이력으로 기록. detached HEAD도 동일 |
| 첫 커밋이 없는 저장소 | `시작 이전 커밋 없음`을 별도 값으로 기록. 가짜 해시나 미래 첫 커밋을 기준선으로 만들지 않음 |
| 작업 폴더·index에 일반 변경이 있음 | 설정 경로와 충돌하지 않으면 허용. 미커밋 변경은 기준선에 포함되지 않음을 출력 |
| 병합 충돌 또는 merge·rebase 등 Git 작업이 진행 중 | 첫 구현에서는 쓰기를 거부하고 해당 작업을 정리한 뒤 재실행하도록 안내 |
| 기준선 객체가 없거나 현재 HEAD의 조상으로 확인되지 않음 | 기준선 불일치로 보고, 새 기준선으로 대체하거나 전체 이력 검사로 전환하지 않음 |

첫 커밋이 없는 경우 미래의 첫 커밋부터 검사 후보가 될 수 있다. 커밋이 있는 경우에도 기준선의 조상이 아닌 별도 브랜치의 커밋을 나중에 병합할 수 있다. 그 커밋을 날짜만 보고 도입 이전으로 제외하지 않는다. 병합의 부모 비교, 초기 설정만 추가한 커밋의 분류, 소스 분류·억제는 후속 check 명세에서 정한다. 이 문서는 검사 후보를 곧 위반으로 판정하지 않는다.

shallow 이력 등으로 조상 관계를 확인할 수 없다면 확인 불가로 남기고 자동 fetch하지 않는다. 기준선 삭제·재설정은 init 옵션으로 제공하지 않으며, 명시적 프로젝트 전환 절차에서 다룬다.

## 명령과 결과

```sh
tryce init --mode normal
tryce init --mode prototype
tryce init --mode normal --dry-run
```

첫 초기화에서는 모드를 명시하게 한다. 모드는 이후 진단 적용 범위에 영향을 주므로 생략을 임의의 사용자 선택으로 기록하지 않는다. 기존 설정이 있으면 `tryce init`만으로 상태를 확인할 수 있고, 다른 `--mode`를 주면 변경하지 않고 별도 모드 전환이 필요하다고 알린다. 자동 승인 옵션이나 기준선을 덮어쓰는 `--force`는 첫 범위에 두지 않는다.

입력은 현재 checkout이다. 하위 폴더에서 호출하면 그 Git 저장소의 checkout 루트를 대상으로 한다. linked worktree는 호출된 checkout만 대상으로 하며, submodule 내부에서는 해당 submodule을 별도 저장소로 취급한다. 부모 프로젝트의 설정을 상속하거나 탐색 중 발견한 다른 저장소를 초기화하지 않는다.

bare 저장소, Git 관리 디렉터리, 저장소 선택을 바꾸는 환경변수는 [status의 범위](repository-status.md)와 같이 거부한다. 읽기 기능의 현재 `status`·`browser`는 초기화 없이도 계속 사용할 수 있다.

`--dry-run`은 생성 예정 경로, 선택한 모드, 기준선, 충돌·미지원 상태를 보여주고 파일·디렉터리·잠금을 만들지 않는다. dry-run 결과가 다음 실행의 쓰기를 보장하지 않으며 실제 실행은 입력을 다시 확인한다.

출력은 기본 JSON과 선택 가능한 text다. 결과는 `생성됨`, `이미 초기화됨`, `계획만 확인함`을 구분하고 루트·기준선·모드·생성 경로·미설치 연동을 포함한다. 정상 결과는 stdout·종료 코드 0, 충돌·호환 불가·쓰기 실패는 stderr·종료 코드 1이다. DTO와 오류 코드는 [project-init / 1](project-format.md)에 정의한다.

## 기존 파일과 재실행

재실행은 최초 생성과 별도 경로로 처리한다. HEAD가 이동했다는 이유로 정상 설정을 다시 생성하지 않는다.

| 관측 상태 | 처리 원칙 |
| :--- | :--- |
| `.tryce/`와 설정이 없음 | 사전 검사 후 새 설정 생성 |
| `.tryce/`는 일반 디렉터리이고 설정은 없음 | 다른 파일을 보존. 과거 설정 삭제·불완전 생성인지 확인한 뒤 판단 |
| 지원하는 정상 설정이 있음 | 바이트와 기준선을 보존하고 이미 초기화됨을 표시 |
| 알 수 없는 버전 또는 손상된 설정 | 원문 보존, 정상 초기화로 표시하지 않으며 쓰기 거부 |
| HEAD 또는 index에는 설정이 있는데 작업 폴더에서 삭제됨 | 사용자 삭제를 복구하거나 재초기화하지 않고 충돌로 보고 |
| 설정의 HEAD·index·작업 폴더 버전이 다름 | 사용자 변경을 보존. 이미 초기화됨 결과와 별도로 변경 상태를 알림 |
| `.tryce`가 파일·symlink·junction이거나 설정 경로가 링크·디렉터리임 | 다른 위치를 따라 쓰지 않고 경로 충돌로 거부 |
| 두 init이 동시에 실행됨 | 한 실행만 새 설정을 확정. 나머지는 최종 설정을 재검증하고 덮어쓰지 않음 |

설정 파일의 존재만으로 모든 연동 파일의 소유권을 증명하지 않는다. 첫 init의 쓰기 대상은 정확히 설정 한 파일이다. 향후 스킬·훅에는 원본·대상·생성 규약·배포 당시 내용 지문을 갖춘 관리 관계가 별도로 필요하다. eject에서 지울 수 있는 범위도 그 명세에서 정한다.

## 쓰기와 복구의 구현 조건

쓰기 전 저장소 위치·HEAD·설정 경로·기존 바이트·index 상태를 확인하고, 적용 직전에 다시 확인한다. 현재 status의 관측 결과는 쓰기 잠금이 아니므로 그 결과만으로 파일을 덮어쓰지 않는다. Git index나 refs는 수정하지 않는다.

완성한 설정을 임시 파일에 기록하고 검증한 뒤, 기존 대상이 있으면 실패하는 방식으로 최종 경로에 확정한다. 중간 바이트를 정상 설정으로 노출하지 않는다. 현재 구현은 완성된 임시 파일을 hard link로 확정한다. 지원하지 않는 파일시스템에서는 실패하며 덮어쓰기 방식으로 우회하지 않는다. 여러 파일과 Git 상태 전체가 한 번에 원자적으로 바뀐다고 보장하지 않는다.

실패 시 이번 실행이 만든 임시 파일만 정리한다. 기존 디렉터리와 내용은 보존한다. 생성했던 디렉터리에 다른 내용이 들어오면 디렉터리 전체를 지우지 않는다. 설정 확정 직후 출력 실패가 발생해도 정상 설정을 삭제하지 않는다. 다음 실행에서 바이트를 검증해 이미 초기화된 상태로 복구한다.

강제 종료로 남은 파일은 이름의 접두어만으로 삭제하지 않는다. 소유권을 확인할 근거가 없으면 경로와 수동 정리 방법을 안내한다. 다른 프로세스가 바꾼 HEAD나 파일을 rollback 명목으로 되돌리지 않는다. 사전·사후 검증으로 확인할 수 없는 외부 동시 변경의 한계도 검증 결과에 남긴다.

## worktree와 clone

설정은 각 checkout의 Git 추적 파일이다. 다른 worktree의 설정을 직접 복사하거나 공용 Git 디렉터리에 프로젝트 설정을 따로 쓰지 않는다. 설정을 포함한 커밋을 checkout한 환경은 동일한 기준선을 읽는다. 경로가 바뀌거나 clone했다는 이유로 다시 초기화할 필요가 없어야 한다.

설정이 없는 다른 브랜치에서 별도로 init하면 서로 다른 도입 기록이 생길 수 있다. 이후 합칠 때 한쪽 기준선을 자동 선택하지 않는다. 기준선 변경·독립 도입의 병합 정책은 프로젝트 전환 명세에 남긴다. 첫 구현은 공유 설정이나 훅을 설치하지 않으므로 다른 worktree의 개발 환경도 수정하지 않는다.

## 채택한 결정과 후속 범위

다음 네 방향은 2026-09-13 사용자가 채택했다. 세부 개발 형식과 전환 범위는 init-1 명세로 구체화했다.

| 항목 | 채택한 방향 | 영향 |
| :--- | :--- | :--- |
| 첫 init의 범위 | 설정·기준선만 생성, 연동은 후속 단계 | 초기화 성공과 에이전트 연동 완료를 구분 |
| 파일과 영속 형식 | `.tryce/config.json`, 개발 형식 init-1 | 요구사항·메타·트레일러는 미지원이며 전체 기록 형식 전환을 별도 명세 |
| 기준선 | 현재 HEAD와 조상 제외, unborn은 별도 표현 | 첫 커밋·병합·미커밋 변경의 검사 범위에 영향 |
| 초기 모드 | 최초 실행에 명시, init으로 기존 모드 변경 금지 | 진단 범위를 암묵적으로 선택하지 않음 |

스킬 생성물 커밋, 에이전트별 경로, 훅 설치·제거, 승인 단위, brief 분량은 이 문서로 확정하지 않는다. 최초 요구사항 작성·상태 전이와 spec 메타 스키마는 다음 영속 형식 명세에서 연결한다.

## 검증과 자체 적용

구현 검증은 임시 Git 저장소에서 수행한다. 다음 사례의 예상 생성물·기준선·실패 후 바이트를 고정한다.

- 일반·unborn·detached HEAD, SHA-1·SHA-256, 하위 폴더, linked worktree와 submodule.
- 같은 설정 재실행, HEAD 이동 후 재실행, 다른 모드 요청, 독립 초기화한 브랜치의 설정 충돌.
- staged·unstaged·untracked 변경 보존, 설정 삭제·부분 staging·병합 충돌·Git 작업 진행 중.
- 설정 경로 충돌·ignore·지원하지 않는 버전·손상된 JSON·링크 경로·쓰기 권한 실패.
- 두 실행의 경합, HEAD·index·대상 파일 변경, 확정 전후 강제 종료와 재실행.
- dry-run 무변경, 전체 사용자 파일·index·refs·Git 설정 보존, 다른 worktree 무변경.
- pack한 CLI의 저장소 밖 초기화와 재실행, 기존 status·browser 회귀 검사.

실제 파일시스템 실패·경합 시험과 제어한 입력 시험을 구분하고, 실행하지 않은 OS를 지원 검증 완료로 표시하지 않는다.

검증 후 이 프로젝트에서 사용할 CLI 빌드와 지원 형식을 [개발 환경](../development.md)에 지정한다. 그다음 실제 저장소 초기화로 진행한다. 기존 docs와 개발 예외 기록은 보존하며 요구사항·승인 이력을 소급해 꾸미지 않는다. DEV-01·02는 기록·check가 지원하는 범위에 맞춰 별도로 축소하고, 스킬·훅이 없는 동안 DEV-04도 유지한다.
