# 대화에서 요구사항으로

사용자는 평소처럼 제품을 이야기하고, 에이전트는 의미 있는 논의를 요구사항 초안으로 정리한다. 관련 초안을 묶어 구현 전에 확인받고, 승인된 내용과 이후 변경을 구분해 보존한다.

상태: 첫 기능의 동작 설계. 2026-09-13 사용자가 ‘조용히 초안으로 기록하고 구현 전에 확인’하는 기본 흐름과 ‘관련 초안을 묶어서 확인’하는 방식을 선택했다. 아래의 확정된 행동을 구현 기준으로 삼는다. 저장 스키마·명령 이름·형식 전환은 설계안이며 아직 CLI에 구현하지 않았다.

## 수집의 기준

사용자가 만들고 싶은 동작, 유지할 조건, 바꾸기로 한 방향을 이야기하면 에이전트가 기존 요구사항과 관련 기록을 먼저 확인한다. 이미 있는 항목을 대화마다 새로 만들지 않고 관련 논의를 묶어 초안으로 정리한다. 설명을 위한 예시, 단순 질문, 에이전트 자신의 제안은 사용자 확정 사항으로 기록하지 않는다.

사용자의 “구글 로그인도 있으면 좋겠네요”는 구현을 승인한 것으로 해석하지 않는다. 요구사항 초안으로 남길 수 있지만 구체적인 범위와 확인할 질문을 함께 적는다. 작은 말마다 확인 질문을 끼워 넣지 않는다. 초안을 저장했다는 사실은 자연스러운 작업 요약에서 알릴 수 있다.

사용자가 특정 내용을 기록하지 말라고 하면 그 범위를 따른다. 대화 전체를 복사하지 않고 요구사항을 이해하는 데 필요한 의도와 근거만 정리한다. CLI가 다른 앱의 대화를 감시하거나 직접 의미를 추출하는 기능은 만들지 않는다. 해석은 에이전트, 형식 검증과 저장은 CLI가 맡는다.

## 한 번의 확인으로 다룰 범위

같이 구현할 관련 초안들을 한 묶음으로 보여준다. 각 항목은 원하는 동작과 확인 가능한 조건을 담고, 포함하지 않은 범위와 남은 질문이 있으면 함께 보여준다. 사용자가 ID나 파일 경로를 외워서 답하도록 요구하지 않는다.

예를 들어 다음은 가상의 로그인 작업이다. 이 예시는 실제 사용자 요구사항이나 승인 기록이 아니다.

> 이번에는 구글 계정으로 로그인하고 로그아웃할 수 있게 하겠습니다. 로그인 취소·실패 시 다시 시도할 수 있도록 안내합니다. 기존 계정과의 연결은 이번 범위에 포함하지 않았습니다. 이 범위로 진행할까요?

에이전트가 추정한 조건은 추정임을 드러내고 확인받는다. 사용자가 일부만 수락하거나 조건을 바꾸면 변경된 묶음을 다시 정리한다. 다음 행동에 영향을 주는 질문이 남아 있으면 해당 부분을 승인된 것처럼 처리하지 않는다. 독립적인 작업까지 멈출 필요는 없다.

사용자가 방금 제시한 구체적인 묶음에 “네, 진행해주세요”라고 답하면 그 내용의 확인으로 기록할 수 있다. 다른 질문에 대한 답이나 오래전의 포괄적인 진행 요청을 새 묶음의 승인으로 재사용하지 않는다. 이미 동일한 내용에 대해 받은 명확한 승인을 형식 때문에 반복해서 묻지도 않는다.

## 승인된 내용의 보존

승인은 사용자가 본 정확한 내용에 연결한다. [제품 기준](../bref.md)의 문서 Git blob 해시 원칙을 유지하며, 묶음에 포함된 각 문서의 식별자·해시와 승인자를 기록한다. 에이전트가 기록을 작성했다는 사실과 사용자가 승인했다는 사실을 구분한다.

묶음을 보여준 뒤 내용이 바뀌면 이전 화면에 대한 응답을 변경된 내용의 승인으로 저장하지 않는다. 승인 직전에 대상 내용이 그대로인지 CLI가 확인하고, 다르면 갱신된 내용을 보여주도록 돌려보낸다. 승인 이후 수정본도 확인 대상으로 다루되 이전 승인과 원문은 남긴다.

기록됨, 승인됨, 구현됨, 검증됨은 별개다. 첫 기능에서는 초안과 확인된 내용을 다루며 구현·검증 완료를 자동으로 만들지 않는다. 단순히 “확인했습니다”라는 문자열이 파일에 있다고 해서 사용자 인증이나 승인의 진위를 증명한다고 표시하지 않는다.

## 구현할 최소 기능

아래 명령 이름은 구현 설계안이다. 사용자에게 직접 호출하도록 요구하는 절차가 아니라 에이전트가 사용할 인터페이스다.

| 단계 | CLI가 맡을 일 | 에이전트가 맡을 일 |
| :--- | :--- | :--- |
| 초안 저장·수정 | 형식 검증, ID 발급, 기존 내용·변경 이유 보존 | 관련 대화를 묶고 기존 초안과 중복 여부 판단 |
| 확인할 묶음 준비 | 대상 ID와 정확한 내용의 해시를 고정해 반환 | 사용자가 읽을 수 있게 내용을 제시 |
| 확인 기록 | 준비한 묶음과 현재 내용의 일치 확인, 승인 대상 보존 | 실제 사용자 답변과 승인 범위를 전달 |
| 조회·다음 세션 | 초안·확인된 내용·확인 후 변경과 원문 위치 제공 | 필요한 기록을 읽고 작업을 이어감 |

첫 구현은 `req draft`, `req revise`, `req review`, `req approve`, `req list/show`처럼 작은 명령군으로 구성하는 안을 제안한다. 일반 사용자는 채팅으로 의사를 전달한다. CLI가 내용을 이해한 척하거나 승인자를 추측하지 않도록 한다.

요구사항 ID는 확정된 `R-<spec>-<base32 10자>`를 따른다. 요구사항 원문과 spec 메타는 합의된 `specs/<spec>/` 아래에 두며, 기존 note의 discovery·constraint·rejected에 요구사항이나 승인을 억지로 넣지 않는다. 필드·파일 배치·수정본 보존·묶음 ID·상태 전이의 구체적인 저장 형식은 별도 구현 명세에서 확정한다.

공개된 init-1·prototype-1의 의미를 몰래 확장하지 않는다. 새 형식 도입은 원본 설정과 기준선을 보존하는 명시적 전환으로 제공한다. 구형 CLI는 새 형식을 지원하는 것처럼 처리하지 않아야 한다. 현재 Tryce 저장소와 .tmp/demo는 이 설계 문서만으로 전환하지 않는다.

## Git에 남기는 시점 — 결정 필요

파일 저장만으로 Git 이력에 보존됐다고 표시할 수는 없다. 사용자의 작업을 방해하지 않으면서 초안과 승인 기록을 언제 커밋할지는 다음 제품 결정이다.

제안은 초안의 작은 수정마다 커밋하지 않고, 관련 요구사항을 확인한 시점에 기록을 묶어 커밋하는 방식이다. 이후 구현 커밋에서 해당 요구사항을 참조한다. 승인 이후 코드 작성이 실패해도 만들기로 한 범위는 남는다. 다만 사용자가 커밋을 직접 관리하는 프로젝트에 적용할 방식과 원격 푸시 권한은 분리해서 정해야 한다.

이 결정 전에는 자동 stage·commit 기능을 만들거나 켜지 않는다. 기존 Git index의 사용자 변경을 함께 커밋하지 않으며, 자동 원격 푸시를 기본으로 두지 않는다. 부분 staging·동시 수정·잠금에 대한 구체적인 동작도 이 결정 뒤 명세한다.

## 검증 시나리오

아래는 앞으로 실행할 검증이며 현재 통과한 테스트가 아니다.

1. 아이디어 대화가 초안으로 남되 승인·구현으로 표시되지 않는다.
2. 관련 초안 여러 개를 보여주고 한 번의 답변으로 해당 묶음만 확인한다.
3. 일부 항목만 수락하거나 조건을 바꾸면 나머지까지 승인되지 않는다.
4. 확인 요청 이후 다른 세션이 내용을 수정하면 오래된 내용에 대한 승인을 거부한다.
5. 승인 이후 수정해도 승인 당시의 원문과 근거가 남는다.
6. 세션이 바뀌어도 현재 초안과 확인된 내용, 다시 확인할 변경을 구분한다.
7. 파일·Git 충돌, 부분 staging, linked worktree, 형식 전환 중단에서 기존 파일과 index를 보존한다.
8. .tmp/demo의 작은 기능을 실제 에이전트에 맡겨 기록 명령을 사용자가 일일이 지시하지 않아도 흐름이 이어지는지 확인한다.

전체 요구사항 GUI, 자동 완료 판정, 모든 승인 강도 옵션, 기존 기능 일괄 도출, 이슈 트래커 연계는 이 첫 흐름 뒤에 다룬다. 이 문서가 해당 기능을 취소하거나 구현 완료로 바꾸지는 않는다.
