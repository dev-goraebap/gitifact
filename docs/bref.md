# tryce

tryce는 에이전트와 함께 개발하는 프로젝트에서 요구사항, 변경 이유, 구현 이력을 관리하는 CLI다. 사용자는 기존 에이전트로 작업하고, tryce는 그 과정의 기록을 Git에 남긴다. 브라우저는 같은 정보를 사람이 살펴보는 읽기 전용 화면이다.

이 문서는 구현을 시작하기 위한 제품·설계 기준이다. 사용자 확정 사항을 반영하고, 에이전트 간 합의와 아직 결정하지 않은 사항을 구분한다. 명령 이름과 데이터 예시는 구현 명세를 작성하면서 구체화한다.

코드 구조와 기술 선택은 [아키텍처 기준](architecture/README.md), [CLI 설계](architecture/cli.md), [브라우저 설계](architecture/browser.md)에서 다룬다.

현재 실행 방법과 검증 범위는 [개발 환경](development.md)에 기록한다.

공개 npm 패키지의 준비·게시·설치 확인은 [배포 절차](releases.md)를 따른다.

첫 조회 기능의 명세와 지원 범위는 [저장소 상태 조회](specs/repository-status.md)다. 현재 `status`가 Git 상태를 관측하며 brief·요구사항 검사를 구현한 것으로 취급하지 않는다.

같은 조회를 화면에서 제공하는 `browser`의 HTTP·세션·새로고침 계약은 [로컬 브라우저 서버](specs/browser-server.md)에 기록한다.

첫 쓰기 기능은 [프로젝트 초기화](specs/project-init.md)다. 사용자가 채택한 설정·기준선·초기 모드와 파일 보존 규칙을 [개발 형식 init-1](specs/project-format.md)로 구현한다. init-1은 설정만 지원하며 전체 요구사항 기록 형식과 구분한다.

프로토타입의 발견·제약·기각 이유는 [프로토타입 기록](specs/prototype-notes.md)에서 다룬다. `note enable`의 명시적 형식 전환, 기록 추가·참조·조회와 원문 보존을 정의한다.

현재 자료를 새 세션에 전달하는 첫 [세션 브리핑](specs/session-brief.md)은 설정·Git 상태·note·문서 위치와 출처·생략·미실행 범위를 제공한다.

에이전트의 brief·note 사용과 개발용 복사본 생성 절차는 [에이전트 스킬 연결](specs/agent-skills.md)에 기록한다.

다른 프로젝트의 CLI 설치·동기화·로컬 복사본 제거는 [프로젝트 스킬 배포](specs/skill-distribution.md)를 따른다.

자동모드와 승인모드, note와 Git 연결의 기준은 [기록 정책](specs/recording-policy.md)을 따른다. 대화에서 초안을 수집하고 모드에 따라 확정·확인하는 흐름은 [요구사항 수집 설계](specs/requirement-capture.md)에 정리한다. 개발 버전의 저장 구조·명령·보존 범위와 제한은 [workflow-1 실행 형식](specs/workflow-format.md)을 따른다.

## 1. 제품 목적

사용자가 개발 방법론을 익히는 데 부담을 들이지 않고 자신의 제품에 집중하도록 한다. 스펙 주도 개발과 Anthropic의 AI-Native SDLC Playbook에서 영감을 받았으며, 요구사항을 정리하고 변경을 추적하는 원리를 기존 에이전트와의 작업 흐름에 연결한다. 사용자가 평소처럼 대화하고 구현하는 동안 필요한 요구사항과 결정이 기록으로 남는 것이 핵심 목표다. 이 절의 방향은 2026-09-13 사용자가 보완한 제품 철학이며, 구현 완료를 뜻하지 않는다.

코드에는 현재 동작이 남지만, 요구사항을 바꾼 이유나 구현하지 않기로 한 판단은 남지 않을 수 있다. 에이전트 세션이 바뀌면 이러한 맥락을 다시 설명해야 한다.

tryce는 다음 정보를 이어주는 것을 목표로 한다.

- 무엇을 만들고 있으며 어떤 요구사항을 따르는가.
- 무엇이 바뀌었고, 왜 바뀌었는가.
- 무엇을 제외했으며 어떤 제약이 있었는가.
- 다음 작업을 시작할 때 어떤 문서와 미결 질문을 확인해야 하는가.

주 사용자는 개인과 소규모 팀이며, 개발자뿐 아니라 로컬 에이전트로 제품을 만드는 비개발자·바이브 코더를 포함한다. CLI·데스크탑·VS Code 등 특정 대화 환경이나 에이전트에 종속되지 않고, 브랜치와 Git worktree를 포함한 사용자의 작업 방식을 존중한다. 작업 폴더가 달라졌다는 이유로 사용자가 설정과 동기화를 반복해야 하는 문제는 도구가 처리한다.

제품의 관리 단위는 하나의 Git 저장소다. 여러 저장소에 걸친 제품의 요구사항 소유 위치와 진행 상태를 통합하는 멀티 레포 관리는 지원 범위에서 제외한다. 저장소 간 조율 체계를 추가하기보다 프로젝트 안에서 단순하게 기록을 유지한다. 이슈 트래커 연계는 검토 대상이나 개발 여부·일정은 미정이다.

첫 범위에는 요구사항·결정 기록, 이력 검사, 세션 브리핑, 스킬 현황, 읽기 전용 브라우저를 포함한다. 조직 단위 승인 체계, 요구사항 커버리지 점수, 브라우저 편집, 외부 스킬의 설치·갱신은 포함하지 않는다.

## 2. 역할과 데이터의 기준

CLI는 사실 수집, 구조 검증, 파일 기록을 담당한다. 에이전트는 맥락을 해석하고, 질문하며, 요구사항과 변경 내용을 작성한다. 의미 변경이나 작업의 완료 여부를 CLI가 문장과 코드만으로 추측하지 않는다.

tryce가 관리하는 요구사항과 메타데이터는 CLI를 통해 기록한다. 스킬은 이 절차를 에이전트에 연결한다. CLI가 제공하는 절차 안내와 에이전트 판단의 구체적인 경계는 후속 명세에서 정한다.

사용자가 매번 기록 명령을 지시하는 것을 기본 흐름으로 요구하지 않는다. 에이전트가 대화 맥락에서 요구사항과 결정을 식별하고 CLI를 통해 저장·Git 기록으로 연결한다. CLI가 다른 앱의 채팅을 상시 수집하는 구조를 뜻하지 않는다.

사용자에게 보이는 모드는 자동모드(auto)와 승인모드(approval)로 정한다. 신규 도입은 auto가 기본이며 의도가 명확하면 별도의 기록 승인을 기다리지 않는다. approval은 관련 요구사항을 묶어 확인받은 뒤 구현한다. 두 모드 모두 불명확한 제품 동작은 질문하고, note로 발견·제약·기각 이유를 기록한다. 실제 사용자 승인을 받은 대상과 기록을 연결하고, 확정·승인·구현·검증을 구분한다. 기존 normal/prototype과 자동으로 대응시키지 않고 명시적 전환을 제공한다. 세부 저장·전환 계약은 구현 전에 명세한다.

모드 변경은 이후 작업에 적용하고 과거 기록의 승인 여부를 바꾸지 않는다. Git 커밋은 프로젝트 정책을 우선하며 정책이 없으면 관련 작업 단위에서 자동 커밋한다. 관련 기록과 코드는 함께 담을 수 있으나 무관한 변경과 사용자 staging을 임의로 포함하거나 바꾸지 않는다. 자동 푸시와 작업 실행 권한은 모드에 포함하지 않는다.

데이터의 출처는 다음과 같이 나눈다.

| 종류 | 기준 | 보관 방식 |
| :--- | :--- | :--- |
| 프로젝트 기록 | 커밋된 요구사항·설정·메타데이터와 Git 이력 | Git에 보관 |
| 현재 편집 상태 | 현재 작업 폴더 또는 index | 조회 시 출처를 표시 |
| 이력 인덱스·검사 캐시 | 프로젝트 기록에서 계산한 결과 | 재생성 가능, gitignore |
| 외부 스킬·플러그인 현황 | 현재 환경의 파일과 확인 가능한 설정 | 로컬 관측 결과, 확인 시각 표시 |

외부 스킬의 설치 상태는 프로젝트 Git만으로 복원할 수 없다. 이를 프로젝트의 영속 기록과 혼합하지 않는다. 캐시를 지워도 프로젝트 기록은 유지되어야 한다.

## 3. 프로젝트 도입과 개발 흐름

### 기존 프로젝트 도입

`tryce init`은 도입 기준선을 기록한다. 기준선 이전의 커밋은 추적 누락으로 집계하지 않는다. 기존 코드 전체를 요구사항으로 자동 변환하는 작업도 기본 동작에 포함하지 않는다.

새 기능부터 spec을 작성하고, 기존 영역은 변경이 필요할 때 점진적으로 편입한다. 변경하지 않는 영역에 spec이 없다는 사실만으로 문제를 표시하지 않는다.

처음부터 과거 전체를 엄격하게 정리할 필요는 없다. 유지보수 과정에서 필요한 영역의 기록을 쌓는 것을 기본 도입 흐름으로 삼는다. 사용자가 원하면 에이전트가 기존 기능을 살펴 요구사항 초안을 한 번에 도출하는 흐름도 제공한다. 코드에서 추정한 초안을 실제 사용자 의도나 승인된 요구사항으로 단정하지 않는다. 특정 문서나 폴더를 필수 입력으로 삼지 않는다. 에이전트는 코드·테스트·문서·Git 이력·대화 중 이용 가능한 맥락으로 요구사항을 도출한다. 문서는 그중 하나의 근거이며 원본 파일의 이동을 뜻하지 않는다. 상세 도출 절차는 후속 명세로 정하며 init의 자동 동작에 넣지 않는다.

`init`은 재실행해도 기준선을 덮어쓰지 않아야 한다. 기존 지침과 사용자 스킬을 보존하고, tryce가 만든 항목을 식별할 수 있어야 한다. `eject`는 그 항목을 기준으로 연동을 제거하며, 공유 연동이 있다면 다른 worktree에 미치는 영향을 고려한다. 정확한 설치·제거 범위는 후속 명세로 남긴다.

### 일반 개발

새 프로젝트에서는 아이디어를 고민하는 첫 대화부터 같은 흐름을 적용한다. 사용자는 익숙한 방식으로 제품을 구체화하고, 에이전트는 선택한 기록·승인 정책에 따라 요구사항을 정리하고 필요한 확인을 받는다. 기록을 위해 정해진 문서 작성 절차를 사용자가 매번 직접 수행하게 하지 않는다.

요구사항, 설계, 작업을 작성하고 필요한 승인을 기록한 뒤 구현한다. 구현 커밋은 관련 요구사항을 참조한다. 구현 중 요구사항이 바뀌면 변경된 문서와 관련 소스를 같은 커밋에 담고, 실제 사건에 맞는 변경 유형을 기록한다.

### 발견 기록과 기존 프로토타입 설계

발견, 제약, 기각 이유는 두 모드 모두에서 짧게 기록한다. 이전에는 이를 prototype 모드로 한정했으나 새 정책에서는 제품 단계와 분리한다. 현재 0.1.0의 note 쓰기 제약은 새 형식으로 전환하기 전까지 유지한다.

```text
[discovery] 발견한 동작이나 가능성 — 근거
[constraint] 유지해야 할 제약 — 이유
[rejected] 제외한 접근 — 이유
```

`promote`는 기록과 코드 변경을 바탕으로 에이전트가 질문하고, 사용자가 초안을 확인한 뒤 spec으로 정리하는 절차다. 유지할 동작, 가져갈 코드, 버릴 코드, 제외한 범위를 구분한다. 발견 기록은 보존하고 생성한 spec은 draft로 시작한다. 브랜치를 자동 병합하지 않는다.

새 정책에서는 프로젝트 단계와 관계없이 필요한 요구사항 초안을 수집한다. 기존 `promote` 구상은 새 모드 전환과 같은 작업으로 보지 않으며, note에서 요구사항을 도출하는 후속 흐름으로 재검토한다. 아직 ID가 없는 기각 아이디어와 기존 요구사항을 제외하는 `scope-cut`은 자동으로 동일시하지 않는다.

## 4. 요구사항과 변경 기록

### 요구사항 ID — 확정

```text
R-<spec>-<base32 10자>
예: R-auth-k7m2p9x3qd
```

접미사는 무작위로 발급한다. 발급 시 확인 가능한 활성·폐기 ID와 겹치면 다시 발급한다. spec 이름을 변경해도 기존 ID는 유지하고 별칭으로 연결한다.

ID는 재사용하지 않는다. 의미가 유지되는 수정에는 기존 ID를 쓰고, 동작·조건·범위가 실질적으로 달라지면 새 ID를 발급한다. 대체되거나 제외된 ID도 재사용 금지 기록에 남긴다.

이력에서 독립 발급으로 의심되는 같은 ID를 찾으면 충돌 후보로 보고한다. 본문이나 패치가 같다는 사실만으로 같은 발급임을 확정하지 않는다. 판정 전에는 후보들의 이력을 하나의 확정된 요구사항 이력으로 합치지 않는다. 충돌 이후 과거 참조를 정리하는 절차는 미정이다.

### 커밋 트레일러 — 확정

tryce 트레일러는 `Tryce-` 접두어를 사용한다. `Tryce-Format`은 CLI 배포 버전이 아니라 기록의 해석 규약을 나타낸다. 아래의 `1`은 최초 형식의 예시다.

```text
feat(auth): 토큰 갱신 구현

Tryce-Format: 1
Tryce-Spec: auth
Tryce-Req: R-auth-k7m2p9x3qd
Tryce-Change: implement
```

| 변경 유형 | 의미 | ID 처리 | 이유 |
| :--- | :--- | :--- | :--- |
| `implement` | 요구사항에 따른 구현을 기록 | 유지 | 선택 |
| `amend` | 의미를 유지하는 수정 | 유지 | 필수 |
| `supersede` | 실질 변경으로 대체 | 새 ID 발급, 이전 ID는 superseded | 필수 |
| `scope-cut` | 대체 없이 범위에서 제외 | 기존 ID는 cut | 필수 |
| `approve` | 승인 대상과 승인 기록 | 대상 참조 | 선택 |
| `discover` | 발견 사항 기록 | 대상에 따라 결정 | 선택 |
| `adopt` | 기존 영역을 spec으로 편입 | 편입 대상에 따라 결정 | 선택 |

이유는 `Tryce-Why`로 남긴다. `supersede`는 이전 ID와 새 ID를 모두 참조하고, 메타데이터의 `supersededBy`로 대체 방향을 명시한다. 참조 순서로 방향을 추측하지 않는다.

검사 억제는 `Tryce-Ack`에 기록해 해당 커밋에 한정한다. 억제 코드와 필수 이유 등 상세 규칙은 후속 명세에서 정의한다.

요구사항의 기본 상태는 draft, active, superseded, cut이다. 상태별 허용 전이, 최초 작성의 변경 유형, 여러 사건이 섞인 커밋, 분할·통합, 병합 커밋의 비교 기준은 구현 전에 명세한다.

### 승인과 완료

승인은 대상 문서의 Git blob 해시와 승인자를 기록하고 커밋한다. 승인 후 문서가 바뀌면 승인된 내용과 현재 내용의 차이를 표시한다. 구체적인 승인 단위와 stage 범위는 별도 명세로 정한다.

구현 선언 커밋, 작업 완료 표시, 연결된 테스트는 각각 별개의 사실이다. `Tryce-Req`나 `implement`만으로 구현·테스트 완료를 선언하지 않는다. 테스트 연결은 명시된 근거가 없으면 비워 둔다.

## 5. 검사와 조회 기준

### 차단과 진단

구조적으로 판정 가능한 위반은 차단한다. 예를 들어 지원 형식에 없는 변경 유형, 필수 이유 누락, 존재하지 않는 ID 참조, 폐기 ID 재사용, 선언한 사건과 상태 전이의 불일치다.

검사는 텍스트 diff의 줄 수가 아니라 파싱한 ID 집합·상태·대체 관계를 비교한다. 제목 위치 이동을 ID 삭제·추가로 취급하지 않는다. 파싱 실패와 상태 전이 위반도 구분한다. 문장의 의미가 바뀌었는지는 에이전트가 판단한다.

진단은 확인한 사실과 근거를 제공한다. 승인 이후 변경, 완료 표시와 참조 기록의 차이, 오래된 미참조 요구사항, 추적 없는 변경, 문서 변경 없는 코드 변경, 미결 질문 방치 등을 다룬다. 임계값과 세부 적용 조건은 검사별 명세로 둔다.

### 기존 모드별 검사 — 과거 설계

아래 표는 normal/prototype을 기준으로 한 이전 합의다. 새 auto/approval의 검사표로 치환하지 않는다. 두 새 모드 모두 구조·기록 보존 검사를 유지하고 실제 승인 대상의 변경을 구분한다. 나머지 진단의 표시·차단 정책은 개별 검사 명세로 정하며, 자동모드를 검사 생략으로 취급하지 않는다.

| 검사 | 프로토타입 | 일반 |
| :--- | :--- | :--- |
| 형식·구조 검증 | 실행 | 실행 |
| 승인 후 변경 | 실행 | 실행 |
| 작업 완료 표시와 커밋 기록의 차이 | 비활성 | 실행 |
| 오래된 미참조 요구사항 | 비활성 | 실행 |
| 추적 없는 변경, 문서 변경 없는 코드 변경 | 비활성 | 실행 |
| 미결 질문 방치 | 실행 | 실행 |

과거 커밋의 검사는 당시 모드로 판단한다. 현재 상태의 검사는 선택한 스냅샷의 모드를 따른다. 일반 모드로 전환했다고 프로토타입 기간의 커밋을 추적 누락으로 소급 집계하지 않는다.

### 스냅샷과 캐시 — 합의

| 명령·상황 | 기준 |
| :--- | :--- |
| `brief`, `check` | HEAD 이력과 현재 작업 폴더의 상태를 출처별로 구분 |
| `check --staged` | index의 후보 스냅샷, 일반 커밋은 HEAD와 비교 |
| 커밋 전 검사 | 후보 index와 실제 커밋 메시지 |
| `reindex`, 과거 조회 | 대상 커밋에서 도달 가능한 이력과 커밋된 문서 |

스냅샷을 섞어 검사하지 않는다. 작업 폴더에만 존재하고 stage하지 않은 ID는 후보 커밋의 유효한 참조 대상이 아니다. 현재 문서를 읽지 못해도 HEAD의 문서로 조용히 대체하지 않는다.

필요한 입력이 없는 검사는 미실행으로 표시한다. 모드상 비활성, 검사 실패, 검사 완료를 구분한다. 미커밋 소스에 메시지가 없다는 이유만으로 추적 누락을 표시하지 않는다. `clean`은 해당 범위의 검사가 완료됐고 문제가 없을 때만 사용한다.

첫 구현에서는 이력 캐시를 사용하고 현재 문서·설정·상태는 매번 읽는다. 관리 경로의 새 파일과 삭제도 포함한다. 기존 캐시 HEAD가 새 HEAD의 조상이고 형식·설정이 호환될 때 증분 갱신한다. 그 전제가 깨지면 재생성한다. 실제 전체 실행에서 병목이 확인되면 최적화한다.

## 6. 세션 브리핑과 브라우저

`brief`는 새 세션이 작업을 이어가기 위해 읽는 지도다. spec 전체를 복제하기보다 활성 spec, 진행 중 작업, 미결 질문, 진단, 최근 결정, 지침, 다음에 읽을 문서와 위치를 제공한다. JSON을 기본 계약으로 하고 사람이 읽는 출력도 제공한다.

분량 정책은 보류 상태다. 전체 출력 크기를 제한하고 개수·생략·추가 조회를 제공하는 안이 제안되어 있다. findings 전량 포함과 고정 길이 상한을 동시에 확정된 요구로 취급하지 않는다.

첫 구현은 사용자가 승인한 핵심 정보·원문 참조·생략 표시 방향을 따른다. 구체적인 기본 개수와 `--all`의 범위는 [brief 출력 버전 1](specs/session-brief.md)에 한정한다. 전체 제품의 findings·이력·미결 질문과 전역 분량 정책을 이 기본값으로 대신 확정하지 않는다.

브라우저와 brief는 공통 프로젝트 모델을 사용한다. 브라우저에서 요구사항·작업·승인·스킬을 편집하지 않는다. 다시 검사하는 동작은 허용하되 프로젝트 원본을 수정하는 기능과 구분한다.

화면이 다루는 정보는 다음과 같다. 구체적인 배치와 탐색 흐름은 별도 와이어프레임에서 정한다.

- 프로젝트 브리핑과 미결 질문
- 요구사항 목록, 상세 내용, 과거 시점과 변경 이력
- 요구사항·작업·참조 커밋·테스트의 연결
- 범위 변경과 기각 이유를 포함한 결정 기록
- 진단 결과와 검사 실행 상태
- 프로젝트 지침과 에이전트별 스킬 현황

과거 문서는 해당 시점의 경로와 커밋을 통해 조회한다. 파일 이동과 spec 이름 변경을 고려해야 한다. 공유용 정적 export는 후속 범위다.

## 7. 스킬 관리

### tryce 제공 스킬 — 확정

프로젝트 원본은 `.agents/skills/tryce-*`에 둔다. `.tryce/skills/`를 별도 원본으로 사용하지 않는다. `.agents`를 직접 읽지 않는 지원 에이전트에는 tryce가 필요한 복사본을 만든다.

첫 구현은 외부 설치 CLI에 위임하지 않고 관리 대상만 직접 복사한다. 프로젝트가 선택한 지원 에이전트의 경로만 관리하며, 접두어만으로 파일의 소유권을 판단하지 않는다. 정확한 경로와 배포 관계를 매니페스트로 관리하고, 복사 전에 소유권과 사용자 수정 여부를 확인한다.

원본에서 파생본을 맞추는 `sync`와 원본 스킬을 새 템플릿으로 업그레이드하는 작업은 구분한다. 일상적인 sync가 사용자의 맞춤 원본을 덮어쓰지 않아야 한다. 스킬과 생성 규약의 버전은 CLI 호환성 정책에 연결한다.

2026-09-13 사용자가 원본만 커밋하고 에이전트용 복사본은 로컬 생성하기로 정했다. 새 checkout에서는 복사본 생성 절차를 실행한다. 복사본의 소유권·갱신 지문도 로컬에서 관리한다. 파일이 존재한다는 것과 실행 중인 에이전트가 지침을 갱신했다는 것은 구분한다. 제품의 설치·제거와 호환성 규약은 후속 명세로 정한다.

### 사용자 설치 스킬과 플러그인 — 표시 모델 합의

사용자가 설치한 스킬은 원래 위치에 두고 읽기만 한다. 외부 설치 기록과 플러그인 캐시를 임의로 수정하거나 이동하지 않는다. 설치 기록은 출처를 보완하는 근거이며, 실제 파일과 확인 가능한 활성 설정도 함께 살핀다.

GUI는 폴더별 중복 행을 줄이되 다음 정보를 보존한다.

| 정보 | 설명 |
| :--- | :--- |
| 설치 항목 | 발견 경로, 실제 대상, 범위, 설치 방식, 출처 근거 |
| 내용 버전 | SKILL.md와 지원 파일의 내용 지문 |
| 목록 묶음 | 같은 대상 또는 확인된 배포 관계를 묶은 표시 단위 |
| 에이전트별 상태 | 탐색 대상, 비활성, 가려짐, 중복 선택지, 확인 불가 등 |

범위와 설치 방식은 구분한다. 플러그인은 프로젝트 범위일 수도 사용자 범위일 수도 있다. 내용 해시가 같다는 사실만으로 출처나 소유권을 합치지 않는다. 반대로 에이전트별 변환본은 내용이 달라도 같은 배포 관계일 수 있다.

기본 표시는 현재 프로젝트·작업 폴더에서의 탐색 상태다. 실제 관측 근거 없이 현재 세션이 스킬을 읽거나 실행했다고 표시하지 않는다. 깨진 링크, 확인 불가능한 설정, 비활성 플러그인을 정상 상태와 구분한다. 에이전트별 탐색 규칙에는 공식 근거와 확인 시점을 연결한다.

## 8. 버전과 업데이트 — 확정

### 호환성의 기준

CLI 업데이트와 프로젝트 형식 전환은 별개다. 지원 중인 옛 형식은 새 CLI에서도 계속 읽고 쓸 수 있어야 한다. CLI 설치나 업데이트만으로 프로젝트 원본을 변경하지 않는다.

버전은 CLI 배포, 영속 형식, 출력 계약으로 구분한다. 영속 형식은 요구사항·설정·메타·트레일러의 호환 조합을 정의하고 생성 규약을 연결한다. 캐시 버전은 내부 재생성 정책으로 관리한다.

각 릴리스는 읽기·쓰기·출력 계약의 지원 범위를 명시한다. 공개한 과거 이력의 읽기는 유지한다. 기존 쓰기·출력 계약의 지원을 축소할 때는 앞선 릴리스에서 예고하고 전환 도구와 마지막 호환 CLI를 안내한다. 모든 옛 형식에 대한 쓰기를 영구 지원하는 것은 아니다.

### 이력의 해석

- tryce 기록에는 형식 버전 트레일러를 남긴다. 현재 프로젝트 설정으로 과거에 명시된 버전을 덮어 해석하지 않는다.
- tryce 기록이 없는 커밋은 당시 설정과 모드로 검사 적용 여부를 판단한다.
- tryce 기록이 있는데 형식 버전이 없으면 조용히 보충하지 않는다. 후보 커밋은 형식 오류로, 과거 커밋은 불완전한 기록으로 보고한다.
- 명확하게 식별 가능한 정식 구형 형식은 전용 해석기로 읽는다. 판별할 수 없는 기록은 원문을 보존하고 형식 미확인으로 표시한다.
- 새 기록에서 기능이나 변경 유형을 제거해도 과거 사건의 의미를 바꾸지 않는다.

### 프로젝트 전환

형식 전환은 명시적인 작업으로 진행한다. 사전 검사, 변경 계획, 전환 전 상태 보존, 적용, 검증, 복구 또는 재개 절차를 제공한다. 계획 이후 입력이 바뀌었으면 다시 확인한다.

전환은 현재 체크아웃에 한정한다. 다른 worktree나 진행 중인 사용자 변경을 덮어쓰지 않는다. 관련 문서·메타·스킬의 전환은 하나의 검토 가능한 변경으로 묶는다. 복구의 기본 약속은 전환 전 상태의 보존이며, 모든 새 형식을 역변환할 수 있다는 뜻은 아니다.

첫 공개 버전부터 알 수 없는 형식의 쓰기를 거부한다. 읽기만 지원하면 읽기 전용으로 동작한다. 읽기 범위도 벗어나면 확인 가능한 원문과 호환성 정보를 제공하고 정상 해석 결과처럼 꾸미지 않는다.

### 훅의 호환성

| 상태 | 기본 동작 |
| :--- | :--- |
| 호환 가능한 CLI가 있음 | 검사 실행, 형식 위반이면 차단 |
| CLI가 없거나 훅 검증 계약에 호환되지 않음 | 검증 미실행을 경고하고 커밋 허용 |
| 검사가 실행되어 후보 기록의 오류를 확인함 | 차단 |
| 실행 중 예기치 않은 오류·출력 파싱 실패 | 검증 실패를 명시하고 중단 |

엄격 모드에서는 CLI 부재·호환 불가도 차단할 수 있다. 훅과 CLI의 배포 번호가 정확히 같은지를 요구하지 않고 검증 계약과 프로젝트 형식의 호환성을 확인한다. 훅은 후보 index와 메시지를 검증하며 index를 자동 수정하지 않는다.

경고 후 허용된 커밋은 사후 검사에서 누락과 구조 오류를 진단한다. 로컬 훅만으로 모든 이력의 형식을 보장하지 않으며, 저장소 단위의 필수 CI 검증은 선택 사항이다.

### 릴리스 검증

공개 형식별로 고정 예제 저장소를 유지한다. 시계·설정·출력 계약·대상 커밋을 고정하고 ID, 상태, 대체 관계, 이유, 진단 결과의 의미를 비교한다. brief 전체의 바이트 일치나 옛 파서 버그의 보존을 요구하지 않는다.

검증에는 정상 기록, 형식 누락·미지원 형식, 트레일러 없는 프로토타입 커밋, 부분 staging, 새 CLI의 옛 형식 쓰기, 옛 CLI의 새 형식 쓰기 거부, 전환 실패 복구, 다른 worktree 보존을 포함한다.

## 9. 구현 범위와 남은 결정

### 첫 구현 방향

기존 초안의 우선순위는 추적 없는 변경 검사와 brief다. 이를 구현하기 위한 영속 형식·호환성 경계, 기준선, 커밋 파싱을 먼저 정의한다. 이후 프로토타입 전환, 스킬 연동, 브라우저 기능을 확장한다. 브라우저 와이어프레임은 병행하되 데이터 계약은 공통 모델을 따른다.

명령군은 다음을 기준으로 세부 명세를 작성한다. 아직 구현 완료를 뜻하지 않는다.

| 영역 | 명령 후보 |
| :--- | :--- |
| 도입·환경 | `init`, `mode`, `sync`, `eject` |
| 조회·검사 | `brief`, `check`, `reindex`, `scan` |
| 기록 | `req`, `adopt`, `note`, `approve`, `commit`, `task sync` |
| 전환·표시 | `promote`, `browser`, 프로젝트 형식 전환 명령 |

후속 구현 명세에서는 상태 전이와 draft 처리, 혼합·병합 커밋, ID 충돌 복구, 승인 단위, 소스 분류와 검사 억제, 생성 규약, 훅 설치·제거와 스킬 로딩 시점, 버전별 지원 범위, 마이그레이션 명령을 정한다. 요구사항은 `.tryce/spec/<spec>/tryce.json`에, 설정과 note도 `.tryce/` 아래에 둔다. 재생성 캐시는 Git 기록과 구분한다. 프로젝트 자체 문서의 위치는 강제하지 않는다. 현재 요구사항 저장·확인 규약은 [workflow-1](specs/workflow-format.md)에 정의했다.

요구사항 초안은 프로젝트 단계에 관계없이 수집하며 상세 저장 형식은 미정이다. 공개 패키지는 @tryce/cli로 게시됐다. 남은 보류 항목은 구현을 편하게 하기 위해 확정된 것으로 간주하지 않는다.
