# tryce 제품 기준

tryce는 에이전트와 제품을 만드는 과정에서 요구사항을 정리하고, 커밋된 명세의 변화를 Git으로 추적하는 도구다. 사용자가 별도의 개발 방법론이나 기록 명령을 배우지 않고 제품에 집중하도록 한다. 개인과 팀 모두 기존 에이전트·에디터·Git 작업 흐름을 유지한다.

2026-09-14 사용자 논의를 반영한 목표다. 배포된 CLI 0.3.0은 기존 JSON·승인·note 형식으로 동작한다. 개발 빌드는 새 Markdown의 실험용 조회·편집·비교·커밋 준비와 실행을 지원하며 데이터 전환은 아직 하지 않았다. 전환 작업은 [MVP 전환 계획](mvp-transition.md) 한 문서에서 관리한다.

## 작업 흐름

사용자는 작업할 영역을 토론하고, 구현하고, 테스트한 뒤 커밋을 요청한다. 에이전트는 그동안 현재 명세를 정리한다. 짧은 대화 중 수정은 초안을 다듬는 과정이며 매번 독립적인 이력으로 쌓지 않는다.

커밋 시점에는 작업 범위와 최종 명세를 대조하고 의미 있는 변경과 이유를 정리한다. 영구 이력의 기준은 Git에 커밋된 명세다. 자동 기록은 자동 커밋·푸시 권한이 아니다. 커밋 시점·메시지·브랜치·서명은 사용자 요청과 프로젝트 정책을 따른다.

기본은 관련 명세·변경 이유·소스코드·테스트를 한 커밋에 담는다. 프로젝트 정책에 따라 분리할 때는 명세와 이유를 함께 커밋하고 구현 커밋에서 관련 R-ID를 참조한다. 명세만 또는 구현만 바뀐 작업에 불필요한 파일 변경을 만들지 않는다. 무관한 변경과 기존 staging을 임의로 포함하지 않는다. 같은 커밋에 코드가 있다는 사실, 구현 완료, 테스트 통과는 각각 다른 사실이다.

MVP는 자동 기록에 집중한다. 승인모드는 사용 중 필요가 확인되면 다시 설계한다. note와 별도의 판단 기록 화면도 MVP에서 제외한다.

## 기록할 요구사항

앞으로 유지해야 할 제품 동작과 제약을 기록한다. 모든 채팅 지시를 요구사항으로 등록하지 않는다.

| 요청 | 처리 |
| :--- | :--- |
| 사용자가 게시물을 삭제할 수 있게 해주세요 | 제품 요구사항 |
| 내부 함수 이름을 바꿔주세요 | 보통 코드 수정과 일반 Git 이력으로 충분 |
| 지금 푸시해주세요 | 작업 지시 |
| 외부 서비스 없이 동작해야 합니다 | 제품 제약사항 |
| 카드 테두리를 연하게 해주세요 | 보통 스타일 수정 |
| 선택한 항목을 테두리로 구분해주세요 | 기존 선택 요구사항의 수용 조건에 반영 |
| 모든 카드에 테두리를 쓰지 마세요 | 공통 디자인 지침에 반영 |

공개 API 이름처럼 사용 방식과 호환성이 달라지면 명세를 확인한다. 기존 명세에 적힌 조건을 바꾸면 명세도 수정한다. 사용자가 정하지 않은 색상·두께 등 세부 구현을 제품 규칙으로 고정하지 않는다.

## 명세와 이력

관련 요구사항을 기능별로 모으고 각 요구사항에 고유 ID와 제목·본문·수용 조건을 둔다. 명세는 `S-<난수>`, 요구사항은 `R-<난수>`로 식별하며 ID에 기능 이름을 넣지 않는다. 같은 요구사항은 이름이나 소속이 바뀌어도 ID를 유지한다. 수용 조건은 일반 본문에서 `조건:`과 `기대 동작:`으로 표현한다. 별도의 요구사항 목록에 같은 내용을 중복 관리하지 않는다.

목표 위치는 `.tryce/spec/<기능>/requirements.md`와 같은 폴더의 `history.jsonl`이다. 현재 원문은 Markdown, 과거 원문·변경 전후·작성자·시점은 Git, 변경 이유와 분리·통합 관계는 보조 기록이 담당한다. 매 수정의 after/before 전체 스냅샷은 저장하지 않는다. 정확한 저장 문법은 전환 계획에서 확정한다.

커밋에 남지 않은 초안은 복원하지 않는다. squash 이후에는 남은 Git 버전을 기준으로 조회한다. 미커밋 내용은 현재 작업 상태로 구분한다. 파일 이동을 요구사항 삭제로, 파싱 실패를 기록 없음으로 해석하지 않는다.

## 도입과 역할

새 프로젝트는 에이전트 인터뷰로 아이디어를 구체화한다. 기존 프로젝트는 변경하는 영역부터 점진적으로 기록하고, 요청받으면 코드·테스트·문서·대화 등 맥락에서 기존 기능을 도출한다. 특정 docs 폴더를 요구하거나 문서를 그대로 옮기는 기능이 아니다. 추정과 사용자 의도, 현재 구현과 계획을 구분한다.

- 에이전트 스킬: 인터뷰, 요청 분류, 명세 작성과 커밋 시 최종 대조.
- CLI: ID 발급, 파일 기록, 구조·참조 검사와 Git 연결. 코드와 명세의 의미 일치를 자동 판정하지 않는다.
- 브라우저: 같은 데이터를 읽어 사람에게 표시.

스킬 진입점은 tryce-workflow 하나다. 설치 직후 현재 세션에서도 직접 읽고 이후 세션은 프로젝트 지침에서 연결한다. AGENTS.md·CLAUDE.md의 기존 정책을 보존하고 최소 안내만 연결한다. 스킬 원본만 커밋하고 지원 에이전트용 복사본은 로컬 생성한다. 외부 스킬·전역 설정은 임의로 변경하지 않는다.

## 브라우저 MVP

| 화면 | 제공할 내용 |
| :--- | :--- |
| 요구사항 이력 | 최신순 생성·변경·삭제, 변경 전후와 이유, 기능 필터, 관계 그래프, 작성자 |
| 제품 기능 | 명세 파일 단위 기능 목록과 현재 요구사항·수용 조건 |
| 기여자 | Git author 기반 인물과 기능별 참여·관련 활동 |

세 화면을 서로 연결한다. 첫 화면 전에 요약 대시보드를 강제하지 않는다. 그래프는 실제 요구사항의 수정·분리·통합 관계를 표현한다. 작성자는 Git author를 기준으로 하고 아바타는 이메일을 이용해 로컬에서 생성한다.

브라우저는 읽기 전용이다. 이력과 상세를 나눠 조회하고 재생성 가능한 로컬 색인으로 반복 분석을 줄인다. 색인은 Git에서 제외하며 원본으로 취급하지 않는다. 프로토타입 속도를 실제 Git 조회 성능으로 주장하지 않는다.

## 범위와 보존

관리 단위는 하나의 Git 저장소다. 멀티 레포 통합, PR·이슈 트래커 연동, 설계·작업 파일, 승인 절차, note, 브라우저 편집, 전체 훅·감사 체계는 현재 MVP에서 제외한다. 구현·검증 연결은 실제 근거를 남기는 범위로 시작한다.

CLI 업데이트와 형식 전환은 별개다. 기존 기준선·요구사항·승인·note를 문서 개정만으로 삭제하거나 재해석하지 않는다. 전환은 임시 저장소에서 검증하고 사용자와 정한 보존·제거 범위로 적용한다. 우리 프로젝트는 별도 원본 백업 없이 유효한 요구사항만 재정리했으며 과거 Git 이력은 유지한다.

## 문서 위치

제품 요구사항의 최종 관리 위치는 `.tryce/spec/`다. docs/specs를 병행 운영하지 않는다. 전환 중 작업과 형식 결정은 [MVP 전환 계획](mvp-transition.md)에 모은다. 전환 뒤 유효한 요구사항을 `.tryce`에 등록하고 임시 계획을 종료한다.

- [아키텍처 기준](architecture/README.md): 코드 구조와 기술 경계
- [프론트엔드 지침](architecture/frontend/README.md): UI 구현 규칙
- [개발 환경](development.md): 실제 실행과 검증 기록
- [자체 도입 기록](adoption.md): 기존 데이터의 도입 근거
- [배포 절차](releases.md): 패키지 게시와 릴리스 기록

스펙 주도 개발과 Kiro의 기능별 명세, Anthropic의 AI-Native SDLC Playbook에서 영감을 받았다. 사용자가 이 방법론을 먼저 학습해야 한다는 의미는 아니다.
