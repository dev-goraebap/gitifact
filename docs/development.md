# 개발 환경

## 2026-09-21 전역 설치 없는 도입

기본 도입을 `npx --yes gitifact@latest init`으로 바꾸고, 생성되는 GITIFACT 블록은 실행한 CLI 버전의 npx 명령을 안내한다. 한국어·영어 소개와 시작하기, workflow를 함께 갱신했다. 프로젝트가 지정한 로컬·전역 실행 방법은 우선하며, 프로젝트 의존성 추가와 전역 설치는 선택 사항이다. 전역 설치 권한이 없다는 이유로 기록을 건너뛰지 않고, 실행·다운로드가 차단되면 필요한 승인과 원인을 알리도록 했다.

`pnpm check`를 통과했다(브라우저 81, CLI 134, core 29, 계약 7, 소개 문서 2건과 패키지 설치 검사). 패키지 검사는 새 임시 프로젝트와 빈 npm 캐시에서 같은 버전의 프로젝트 설치본을 npx로 오프라인 실행해 init·spec working, 블록의 버전 고정, package.json·잠금 파일 보존을 확인했다. 자연어 지침을 받은 에이전트의 실제 승인 요청 행동과 별도 제한 환경의 네트워크 접근은 검증하지 않았다. 사용자 프로젝트·전역 설치는 변경하지 않았고 커밋·배포는 하지 않았다.

## 2026-09-20 기능별 요구사항 화면

사용자가 이 화면이 무난하고 내용이 없다고 했다. 세어 보니 기능 8개 중 7개가 설명이 비어 있어 목록 행에 제목·개수·아바타·시각만 남았고, 정작 내용인 요구사항 39개는 목록에 한 줄도 없었다. 네 가지를 함께 고쳤다.

**목록.** 표를 그대로 두고 기능 행 아래에 그 기능의 요구사항을 낮은 행(38px)으로 이었다. 사용자가 기능 행을 그룹 머리로 남기는 안을 골랐고, 요구사항만 평평하게 늘어놓는 안(기능 이름이 39번 반복된다)과 접었다 펴는 안(기본 상태가 지금과 같다)은 기각했다. 요구사항 행을 누르면 `?selected=R-…#R-…`로 상세의 그 절로 간다. 페이징은 `model/feature-rows.ts`가 맡아 40행을 넘기 전까지 기능을 담되 한 기능을 쪼개지 않는다. 행으로 나누면 한 기능이 페이지에 걸쳐 끊기고, 기능 수로 나누면 요구사항 200개짜리 도입 커밋 하나가 페이지를 덮는다. 한 기능은 요구사항 12개까지 보인 뒤 "요구사항 N개 더"로 상세에 잇는다. `page`는 숫자 인자라 주소가 `?page=2`로 읽힌다. 처음엔 문자열이라 `?page="2"`가 됐다.

**포커스 표시.** 절 옆 세로 줄을 빼고 절 제목 위로 형광펜이 지나가는 표시(`<mark>` + linear-gradient)로 바꿨다. 사용자 지적대로 줄은 긴 절에서 "여기 무언가 있다"만 말하고 어느 줄을 읽으라는 말은 하지 못한다. 요구사항과 설계 절이 같은 표시를 쓴다.

**설계 절 지목.** Astryx Markdown이 제목에 붙이는 id를 그대로 쓰고, `model/design-sections.ts`가 ref 주석 위의 제목을 문서 순서로 outline과 맞춰 요구사항 → 절 id를 만든다. 글이 어긋나는 짝은 버린다. 엉뚱한 절로 보내는 것이 링크가 없는 것보다 나쁘다. `components.heading`을 우리 렌더러로 바꿔 id를 지키면서 현재 절만 표시한다.

**요구사항 → 설계.** 설계는 절마다 관련 R-ID를 보여 주는데 반대 방향이 없었다. 요구사항 39개 중 38개가 어떤 절에 연결되므로 거의 모든 요구사항에 "이 요구사항의 설계 →"가 붙는다.

사용자 요청으로 두 가지를 더 넣었다. 기능 행에 빗금 바탕을 깔아 묶음의 머리를 구분했다. 배경 이미지로 깔아서 hover 바탕이 아래로 비친다. 페이지 매김은 카드 바닥에 붙는 푸터로 옮겼다. 한 페이지가 40행이라 화면보다 길어 끝까지 내려가야 다음 페이지를 찾을 수 있었다. 처음에는 `position:sticky`만 줬는데 사용자가 고정이 안 된다고 했다. sticky는 스크롤할 것이 있을 때만 붙으므로, 내용이 짧은 마지막 페이지에서는 표 바로 아래 화면 중간에 머물렀다. 푸터가 든 칸을 카드 높이까지 늘이고(`min-height:100%` + `flex:1`) `margin-block-start:auto`로 바닥에 붙였다. 늘이는 규칙은 `:has(.featurePager)`로 걸어 다른 화면은 건드리지 않는다. 사용자가 다음 기능과의 분리감을 더 달라고 해서 묶음 사이를 마지막 요구사항 행의 아래 여백 24px로 벌렸다(`:has(+ tr[data-row=feature])`). 선만으로는 행 구분선과 구별되지 않아 묶음이 끝난 것으로 읽히지 않았고, 빈 자리에는 빗금이 없으므로 빗금이 다시 시작하는 것이 곧 다음 묶음이다.

사용자 요청으로 정렬을 필터 줄의 Selector에서 열 머리로 옮겼다. 견줄 값이 있는 세 열만 `sortable`이고 참여자는 아바타뿐이라 빠진다. `useTableSortable`은 머리의 표시와 조작만 맡고 실제 정렬은 화면이 한다. 행이 묶여 있어 플러그인이 평평한 배열을 다시 늘어놓으면 묶음이 흩어지기 때문이다. 상태는 `sort`와 `dir`이고 기본인 최근 변경 내림차순은 주소에 쓰지 않는다. 플러그인의 기본 주기가 항상 오름차순부터라 최근 변경을 누르면 가장 오래된 것이 먼저 왔는데, 그건 그 열을 보려는 이유가 아니라 `onSortChange`에서 열마다 여는 방향을 정했다. 쓰이지 않게 된 정렬 문구 네 개를 지웠다.

작업 중 결함을 하나 발견해 함께 고쳤다. 밖에서 붙여 넣은 주소의 프래그먼트는 절이 그려지기 전에 읽혀 브라우저가 스크롤하지 못했다(대상이 652·2208·2301px에 있는데 scrollTop 0). 앱 안에서 누를 때는 라우터가 처리해 문제가 없어 보이던 것이다. 이제 대상이 바뀔 때 그 절을 직접 화면에 올리고, 세 주소 모두 상단 바 아래 69px에서 시작한다.

검증: `pnpm check` 통과(브라우저 72, CLI 128). 브라우저 테스트 5건을 더했다 — 요구사항이 기능 아래 행으로 나오고 눌러서 그 절이 표시되는지, 밖에서 연 프래그먼트가 그 절에 서는지, 설계 절과 요구사항이 서로를 가리키고 표시는 하나뿐인지, 40행 기준 페이징이 기능을 쪼개지 않고 주소에 남는지, 검색어가 기능이 아니라 요구사항을 찾으면 그 요구사항만 남는지. 기존 4건은 표의 행이 두 종류가 되어 기능 행만 세도록 고쳤다. 라이트·다크·760px을 실제 CLI 서버로 확인했고 가로 스크롤·콘솔 오류는 없다.

## 2026-09-20 활동 화면을 이유 단위로

사용자가 타임라인 느낌은 두고 정보 배치를 고쳐 달라고 하면서, 같이 커밋한 기록마다 변경 이유가 똑같이 찍혀 전달력이 떨어진다고 지적했다. 세어 보니 이 저장소의 이력 209건에서 서로 다른 (커밋, 이유) 묶음은 81개뿐이었다. 같은 문단이 209번 찍히고 그중 128번이 바로 위와 같은 글이며, 한 이유가 최대 26건을 덮는다. 실제 화면 첫 아홉 줄 중 네 줄이 글자 하나까지 같았고, 그 이유는 한 줄로 잘려 문장 중간에서 끊겨 있었다.

사용자가 이유를 제목으로 묶는 안을 골랐다. 커밋으로만 묶고 이유를 모아 보이는 안과, 줄 구조는 두고 중복만 생략하는 안은 기각했다. 커밋 34개 중 24개가 이유를 둘 이상 기록하고 여덟 개까지 있어서, 커밋으로만 묶으면 어느 이유가 어느 기록의 것인지 잃는다.

타임라인의 한 항목이 커밋 하나가 됐다. 세로 선 위 아바타 옆에 작성자·상대 시각·기록 수, 그 아래 커밋 해시와 커밋 제목이 오고, 본문은 이유마다 한 덩어리다. 이유는 한 번만 적고 46rem 폭까지만 흐른다. 처음에는 이유 묶음에 왼쪽 세로 규칙을 뒀는데, 사용자가 안쪽 줄은 필요 없다고 해서 뺐다. 대신 간격으로 나눈다 — 이유와 그 기록 사이 `--spacing-2`, 이유 묶음 사이 `--spacing-5`. 세로 선은 타임라인의 것 하나만 남는다. 그 아래 기록은 변경 종류 토큰·명세 종류·제목·현재 위치 순서로 한 줄씩이고, 앞의 두 칸이 폭을 지켜 줄끼리 맞춰진다. 현재 위치를 오른쪽 끝에 붙이는 배치도 만들어 봤는데 제목과 600px 떨어져 연결이 끊겼고, 위키 규칙의 "대부분의 행이 같은 값인 항목은 열로 두지 않는다"에도 걸려 제목 옆으로 붙였다. 48rem 미만에서는 제목 아래로 내려가며 제목 위치에 맞춰 들여쓴다. 두 칸의 폭은 사용자가 여백이 넓다고 해서 실제 글자 폭에 맞춰 줄였다 — 변경 토큰 72→48px, 명세 종류 80→60px(가장 긴 "위키 페이지"가 58px)이라 제목이 40px 왼쪽으로 왔다. 명세 종류는 제목 옆의 이름표이지 제목과 대등한 칸이 아니므로 글자도 12px에서 11px로 낮췄다(제목 16px, 라이트 대비 6.45:1). 날짜가 바뀌는 자리에 날짜를 표시하고 그 자리에서 세로 선을 끊는다.

기록 수는 그 항목에 지금 보이는 수다. 서버가 커밋별 전체 건수를 주지 않고 페이지가 커밋 중간에서도 끊기므로, 걸친 커밋은 다음 페이지를 불러오면 한 항목으로 합쳐지며 수도 올라간다(50a421b가 6 → 25). 이유 본문은 자르지 않았다. 이유 81개의 중앙값은 143자, 최대 318자로 길어야 다섯 줄이고, 잘린 이유가 애초의 불만이었다.

`memo`는 줄에서 커밋 항목으로 옮겼다. 묶음 배열은 페이지를 더 읽을 때마다 새로 만들어지므로 이벤트·기능 객체의 동일성을 직접 비교하는 비교 함수를 붙였고, 선택 여부는 자기 항목에 든 키만 받아 다른 항목이 다시 그려지지 않게 했다. 잰 값: 더보기 80~114ms로 기록 243건까지 일정했고(전에는 104~171ms), 다른 화면에 다녀와 그리는 데 260~375ms다. 활동 골격도 새 배치로 다시 그렸고, 골격이 자기 여백을 한 번 더 주고 있어 실제 목록과 가로로 16px 어긋나던 것을 함께 고쳤다.

사용자 요청으로 제품 개요의 "최근 변경 이력"을 "최신 활동"으로 바꾸고, 같은 타임라인 컴포넌트를 그대로 불러 쓰게 했다. 개요만의 행 컴포넌트(`CommitGroup`)와 그 전용 CSS 일곱 덩어리를 지웠다. 그중 `.record`는 이 파일에 두 번 선언돼 뒤의 규칙이 타임라인 줄에 `max-width`를 얹고 있었다 — 프론트엔드 코드 스타일이 금지하는 중복이며 이번에 사라졌다. 개요 골격도 같은 `TimelineSkeleton`을 쓰되 자기 status 영역 안에 들어가므로 `isPlain`으로 role을 뺀다.

커밋 하나가 기록 수백 개를 만드는 경우(도입 커밋 등)를 사용자가 지적해 커밋마다 10개까지만 그린다. 서버는 이미 12개까지만 보내지만 전체 수(`count`)를 함께 주므로, 머리의 "기록 N건"은 가려진 것을 포함한 실제 수이고 목록 끝의 "기록 N건 더 →"가 차액을 활동으로 잇는다. 잘라내기는 `ActivityTimeline`의 선택 prop `hidden`으로 넣어 활동 화면은 기본값 0으로 동작이 그대로다.

작업 중 결함을 하나 발견해 함께 고쳤다. 이력 요약은 체크아웃과 다른 조회인데 오는 동안 개요가 "전체 활동 0건", "아직 자료가 없습니다", "커밋된 명세 활동이 아직 없습니다"를 보이고 있었다. 사실과 반대를 말하는 데다 브라우저 규칙의 "처음 로딩·빈 결과·조회 실패를 구분한다"에도 어긋난다. 이제 답이 오기 전에는 같은 타임라인 골격과 막대 자리를 둔다.

검증: 브라우저 테스트 67건 통과(2건 추가 — 기록 25건짜리 커밋이 10줄과 "기록 15건 더 →"로 그려지고 그 링크가 여는 활동 화면에는 25줄이 모두 있는지, 요약이 오는 중에 개요가 0건·빈 상태를 말하지 않는지). 라이트·다크·760px과 불러오는 중 화면을 실제 CLI 서버로 확인했고 가로 스크롤·콘솔 오류는 없다.

검증: `pnpm check` 통과(브라우저 65, CLI 128). 브라우저 테스트에 한 이유가 기록 셋 위에 한 번만 적히는지, 커밋 하나가 항목 하나인지, 날짜가 바뀔 때만 날짜가 붙는지 검사하는 건을 더했고, 목록 줄 수를 세던 기존 세 건은 기록 목록을 세도록 고쳤다. 실제 CLI 서버에서 라이트·다크·760px과 필터·선택·더보기·골격을 확인했고 가로 스크롤과 콘솔 오류는 없다. 확인용 캡처는 남기지 않았다.

## 2026-09-19 검색창의 깜빡임

사용자가 검색창을 열었을 때 보이는 "최근 변경" 목록이 입력할 때마다 빨리 깜빡인다고 했다. 프레임마다 목록을 기록해 보니, 입력하는 순간 목록이 "검색할 문서가 없습니다" 빈 상태 그림으로 바뀌었다가 약 0.5~0.7초 뒤 결과로 바뀌었다. 문서가 하나도 없을 때의 안내라 틀린 문구이기도 했다. Astryx CommandPalette는 결과를 기다리는 동안 이미 보이는 목록을 제목으로 좁히고, 남는 게 없으면 빈 상태를 보인다. 이 동작을 끄는 속성은 없다. 그래서 입력칸의 change 이벤트로 "기다리는 중"을 세우고, 그동안 빈 상태 자리에 결과 줄 모양의 골격을 두었다. 처음에는 검색 함수 안에서 상태를 세웠는데, 팔레트가 그 함수를 transition 안에서 불러 결과가 온 뒤에야 반영됐다. 고친 뒤에는 입력 전 목록 → 골격 → 결과 순서로만 바뀌고, "일치하는 문서가 없습니다"는 결과가 온 뒤에만 나온다. 좁힌 부분 목록은 틀린 내용이 아니어서 그대로 두었다.

검증: 브라우저 테스트 64건 통과. 검색 응답을 붙잡아 두고, 그동안 골격이 보이며 두 빈 상태 문구가 나오지 않는지 검사하는 테스트를 더했다. safety-solution-webapp에서 프레임별 기록으로 바뀐 순서를 확인했다.

## 2026-09-19 긴 목록 그리기

사용자가 활동에서 더보기를 누른 뒤 다른 화면에 다녀오면 느리다고 했다. 재 보니 서버 요청이 아니라 그리기가 원인이었다. 334줄에서 돌아오는 데 2,899ms(멈춤 2,748ms)가 걸렸고, CPU 프로파일에서 그중 2.7초가 Astryx Text의 maxLines가 잘림 툴팁을 위해 요소마다 크기를 재는 코드였다. 활동 한 줄에 두 번 쓰였다. 이 한 줄 자르기를 CSS로 바꿔 401~490ms(멈춤 316~395ms)가 됐다. 사용자가 남은 개선도 바로 하라고 해서 같은 방식을 참여자 카드·참여자 상세의 기능 카드·기능 목록 설명·개요 이유(두 줄)·검색창 결과 줄에도 적용했고, 활동 줄을 memo 컴포넌트로 바꿔 더보기가 새 줄만 그리게 했다. 더보기 한 번은 누를수록 147ms에서 361ms로 늘던 것이 104~171ms로 일정해졌다. 이동 경로의 maxLines는 한 번만 그려지고 툴팁이 쓸모 있어 남겼다. 처음부터 다시 더보기를 시키는 안은 돌아올 때 약 230ms로 차이가 작고 읽던 범위를 잃어 쓰지 않았다.

검증: 브라우저 테스트 63건 통과. safety-solution-webapp에서 잘림이 실제로 적용되는지(`text-overflow: ellipsis`, `white-space: nowrap`)와 화면을 확인했다. 잘린 글에 마우스를 올렸을 때의 툴팁은 없어졌고, 전문은 서랍과 상세에서 본다.

## 2026-09-19 이력 색인과 서버 구조

사용자가 활동 화면이 불러온 범위만 거르는 것을 지적했다. git을 쓰더라도 화면은 DB를 쓸 때처럼 전체를 대상으로 검색·필터·페이징해야 한다는 것이다. 이에 따라 이력을 로컬 SQLite 색인에 두고 서버가 거르고 세고 찾게 했다. 색인 위치는 `.gitifact/data/`와 `.git/gitifact/`를 비교한 뒤, 사용자에게 새 폴더가 보이지 않는 `.git/gitifact/index.sqlite`로 정했다. 범위도 비교했다. 끝이 없는 이력과 작성자 집계, 전역 검색은 색인으로 옮기고, 상한이 있는 체크아웃은 지금처럼 통째로 보낸다. 서버 프레임워크는 넣지 않고 서버 구조를 경로 표로 정리했다. 결정과 기각한 안은 위키 결정 0009와 브라우저 설계의 이력 색인·서버 구조 절에 있다.

바뀐 것: browser-specs v4는 체크아웃만 담는다. 이력은 browser-history v1(필터·검색어·offset·limit, 전체 건수), 개요는 browser-history-summary v1, 서랍은 browser-change v1(키로 목록 정보와 전후 본문), 검색은 browser-search v1이다. 쿼리 스키마도 계약에 둔다. 서버는 `http/`(guard·router·respond·static-files), `routes/`(project·record·asset), `checkout/`, `history/`(commit-changes·index-database·history-index·search-text)로 나눴다. 화면에서는 활동이 필터를 서버에 보내고 "전체 N건 중 M건"을 보이며, 개요가 서버 요약을, 참여자 상세가 작성자 필터 10건을, 검색창이 서버 검색("변경 이력" 묶음 포함)을 쓴다. 서랍은 목록에 없는 변경도 키로 연다. 개요 카드 제목은 전체 이력을 세게 되어 "변경 종류"로 바꿨다.

잰 값(safety-solution-webapp 332건, 이 저장소 202건): 색인이 없을 때 첫 이력 요청 292ms·538ms, 재기동 후 60ms·99ms, 페이지·필터·요약·단건 9~18ms, 검색 14~35ms. 실제 브라우저에서 활동 목록 1.0초, 설계 필터(전체 58건) 0.9초, 개요 0.9초였고 콘솔 오류는 없었다.

검증: `pnpm check` 통과(브라우저 63, CLI 128, 패키지 설치 검사). CLI 테스트는 작업 폴더가 그대로인지(색인 파일만 `.git` 안에 생김), 경로별 쿼리·세션·메서드 거부, 50건 페이징, 첫 페이지에 없는 변경을 필터가 찾는지와 전체 건수, 색인 재사용과 새 커밋 추가, 손상 파일·다른 형식 번호에서의 재생성, 검색(두 글자·세 글자·순위·패턴 문자·지난 변경), 레거시 경계, 예전 방식과의 동등성, 작성자 집계를 검사한다. 브라우저 테스트는 가짜 API가 한 자료에서 체크아웃·이력·요약·단건·검색을 서버처럼 답하게 바꿨다. 불러오지 않은 변경을 필터가 찾는 경우, 목록에 없는 변경의 서랍, 개요의 전체 건수와 참여자 최근 활동, 검색창의 변경 이력을 더했다. 전체 검증 중 브라우저 테스트 한 건이 한 번 실패했는데 단독 실행과 3회 반복(189건)에서는 재현되지 않았다. CLI 테스트와 동시에 돌 때의 부하로 보이며 어느 테스트였는지는 잡지 못했다.

## 2026-09-19 활동 이력 읽기: 바뀐 파일만, 변경 50건씩, 본문은 열 때

사용자가 다른 프로젝트(safety-solution-webapp)에서 활동 화면이 느리다고 했다. 그 프로젝트에서 먼저 쟀다. 커밋 1,662개 중 `.gitifact` 커밋은 10개(파일 131개·1.1MB, 기능 22·위키 63)라 v3의 "커밋 10개씩" 페이징으로는 첫 페이지에 이력 325건·1.9MB가 한 번에 왔다. 화면까지 2.8~3.9초였고 서버가 1.4~2.5초(git 119회), 브라우저가 약 1.3초 동안 멈췄다. git 호출은 종류와 무관하게 한 번에 약 80ms였다.

사용자가 세 가지를 모두 고치기로 했다. 서버는 커밋마다 바뀐 파일만 읽고(`log --raw` 한 번, `cat-file --batch` 한 번), 첫 페이지의 기능·페이지별 log를 `--name-only` 순회 한 번으로 합쳤다. 페이지는 변경 50건 단위이고 한 커밋 안에서도 끊는다(커서 `<커밋>:<n>`). 목록 이벤트에서 본문을 빼고 서랍을 열 때 `/api/v1/change`로 받는다. 계약은 browser-specs v4와 browser-change v1이다. 재 보니 남은 시간의 대부분은 작업 폴더를 두 번씩 읽는 readWorkingPreviewState(한 번 약 310ms)를 요청마다 두 번 부르는 데 있었다. 이어지는 페이지에서는 부르지 않고, 첫 페이지에서는 한 번만 다른 읽기와 나란히 부른다.

결과(같은 프로젝트): 첫 페이지 서버 350~586ms·git 8~9회, 이어지는 페이지 약 100ms·git 3회·약 35KB, 목록 표시 0.9~1.0초(멈춤 71~118ms), 서랍 본문 284ms, 더 보기 493ms.

바뀐 파일만 읽어도 결과가 같은지는 예전 방식(저장소 전체 비교)을 기준값으로 확인했다. 실제 CLI로 기능 생성·수정·다른 기능으로 이동·설계 삭제·위키 생성·이동과 이유를 섞은 이력을 만들어 모든 변경의 종류·이유·전후 본문을 대조하는 테스트를 더했고, 예비 경로를 막은 채로도 통과함을 확인했다. safety-solution-webapp(변경 331건)과 이 저장소(202건)의 전체 이력도 같은 방식으로 대조해 순서까지 같았다.

작업 중 두 가지를 고쳤다. 첫 페이지의 병렬 읽기 중 하나가 먼저 실패하면 요청이 끝난 뒤에도 git 프로세스가 돌아, Windows에서 테스트 임시 폴더를 지울 때 EPERM이 났다. 이제 모든 읽기가 끝난 뒤 실패를 알린다. 또 명세 파일을 직접 쓰는 테스트 도중 Python heredoc이 `\n` 이스케이프를 줄바꿈으로 바꿔 테스트 파일이 깨진 일이 있어, 그 부분은 편집 도구로 다시 썼다.

검증: `pnpm check` 통과(브라우저 59, CLI 125). 브라우저 테스트에 서랍이 본문을 한 번만 읽는지와 읽기 실패 표시를, CLI 테스트에 50건 페이징·커밋 중간 커서·change API의 400/404·기준값 대조·작성자/최근 커밋 대조를 더했다.

## 2026-09-19 활동 화면이 갈수록 느려지던 원인

사용자가 활동 페이지에 들어갈 때마다 느려지고 더보기 뒤 다른 화면을 다녀오면 더 느리다고 알려 왔다. 측정으로 재현됐다. 페이징 자체는 커밋 10개씩 정상 동작했고, 원인은 두 가지였다.

첫째, 명세 조회의 staleTime이 5초였다. 제품 개요·요구사항·위키·활동·참여자가 이 조회 하나를 함께 쓰므로 화면을 옮길 때마다 불러온 페이지가 전부 다시 요청됐다. 더보기를 두 번 누른 뒤 활동으로 돌아오면 3회·약 2초였고 더 불러올수록 늘었다. staleTime을 무한으로 두고 갱신을 새로고침 버튼으로만 하게 했다. 이미 "명시적 새로고침으로 갱신한다"고 문서화된 동작이라 규칙과도 맞는다. 복귀 요청은 0회, 목록 표시까지 약 0.8초로 고정됐다(3회 반복 774·821·781ms).

둘째, 페이지마다 현재 명세 전체가 반복해서 실렸다. 기능 8개 118KB와 위키 18페이지 51KB가 매 응답에 들어갔고, 서버도 페이지마다 기능별 로그 8회·문서별 로그 18회·author 10,000건 집계·git status를 다시 돌았다. browser-specs 계약을 v3로 올려 체크아웃(기능·위키·참여자·미커밋 여부)을 첫 페이지에만 싣는다. 이어지는 페이지는 470KB→301KB, 317KB→148KB로 줄었다. 브라우저는 첫 페이지를 체크아웃이 반드시 있는 형식(browserSpecsFirstV3)으로 검증하고 나머지는 이력 형식으로 읽는다. v2 파일은 지웠다. 이 계약은 CLI가 자기 번들 브라우저에 주는 것이라 구버전 호환 대상이 아니다.

변경 전후 본문을 목록에서 빼는 안(응답의 60~70%)은 이번에 하지 않았다. 사용자가 나중에 Ctrl+K 검색 팝업을 붙일 계획이라 물어 왔는데, 검색은 현재 본문(첫 페이지의 features·documents)을 쓰고 이력 스냅샷은 비교 화면에서만 쓰므로 서로 충돌하지 않는다. 검색 범위를 이력까지 넓히면 클라이언트로 다 보내는 방식이 아니라 서버 검색이 필요하다. 그래서 본문 분리는 검색을 붙일 때 함께 하기로 미뤘다.

검증: `pnpm check` 통과. 테스트를 둘 더했다 — CLI 쪽은 이어지는 페이지에 체크아웃 필드가 없고 커밋 본문은 있는지, 브라우저 쪽은 더보기 뒤 화면을 오가도 요청이 늘지 않고 새로고침에서만 모든 페이지를 다시 읽는지 확인한다. 커밋·푸시는 하지 않았다.

## 2026-09-19 제품 개요를 변경 이유 중심으로

사용자가 개요 페이지가 밋밋하고 정작 궁금한 내용이 없다고 알려 왔다. 첫 화면을 무엇이 이끌지 물어 "무엇이 왜 바뀌었나"를 택했고, 기능 지도가 이끄는 안과 수치 대시보드를 다듬는 안은 기각했다.

바꾼 내용은 브라우저 설계의 제품 개요 절에 있다. 요약 타일 다섯 개와 페이지 제목을 걷어내고, 프로젝트 이름과 한 줄 규모 아래에 최근 커밋의 변경 이유를 본문으로 두었다. 이유는 기록마다 저장되지만 커밋 하나에 붙는 값이라 커밋으로 묶어 그린다. 묶기 전에는 한 커밋이 건드린 기록마다 같은 문단이 되풀이돼 화면이 같은 글로 찼다. 이유가 길어 커밋당 한 문장(두 줄)으로 자르고 나머지는 "이유 N건 더"로 세었다.

첫 구현에는 살펴볼 곳(미커밋·설계 없음·이유 미기록)과 최근 손댄 기능 카드를 넣고 차트 두 장을 뺐는데, 사용자가 두 카드를 빼고 기존 차트 두 장(변경 종류, 참여자별 커밋)을 변경 이유 위에 좌우로 되돌려 달라고 해 그대로 했다. 같은 요청으로 활동 링크를 둘에서 하나로 줄이고 절 이름을 "무엇이 왜 바뀌었나"에서 명사형 "변경 이유"로 바꿨다. 기능 전체 표는 기능별 요구사항 화면이 그리므로 개요에서 되풀이하지 않는다.

검증: 1440·720 폭과 라이트·다크를 실제 CLI 서버로 캡처해 확인했고 가로 스크롤이 없다. 본문 글자 대비는 두 모드 모두 4.5:1 이상이다(Token 15건이 걸렸으나 반투명 배경을 불투명으로 읽은 측정 오류였다). 브라우저 테스트 41건 통과. 개요 테스트는 새 구성으로 고쳐 두 차트의 범례, 변경 이유와 기록 링크, 활동 링크가 하나인 것을 확인하고, 스모크 테스트의 제목 검사는 프로젝트 이름으로 바꿨다. 캡처는 `.tmp/overview/`에 있다. 커밋·푸시는 하지 않았다.

## 2026-09-19 문서의 다이어그램과 알림 렌더링

브라우저가 ```mermaid 펜스를 코드로, `> [!NOTE]` 알림을 `[!NOTE]` 글자가 그대로 남은 인용문으로 보여 주던 것을 고쳤다. 저장소의 `.md`에는 아직 둘 다 쓰인 곳이 없으니 앞으로 쓰기 위한 준비다. 범위는 사용자가 골랐다. mermaid를 지연 로딩으로 담고 알림까지 함께 고치는 안을 택했고, 알림 등 경량 항목만 고치는 안과 mermaid만 넣는 안은 기각했다.

구현은 `shared/ui/document`에 모았다. Astryx Markdown의 `components.code`·`components.blockquote`를 우리 렌더러로 바꾸되, mermaid가 아닌 펜스는 CodeBlock, 표지가 없는 인용은 Blockquote 그대로다. Astryx는 이 슬롯을 바꾸면 감싸개 클래스까지 내주므로 블록 간격은 CSS 모듈이 대신 준다. mermaid는 `import('mermaid')`로만 불러 자기 청크에 두고, 색은 그리기 직전에 그 자리의 테마 토큰 계산값을 읽어 넘기며 화면 모드·색 조합이 바뀌면 다시 그린다. `securityLevel: 'strict'`·`htmlLabels: false`이고 문법 오류는 그 자리에만 원문과 이유를 보여 준다. 설계는 브라우저 design.md의 문서 읽기 절, 결정과 대가는 위키 ADR 0008에 있다.

mermaid는 12.0.0으로 시작했다가 11.17.2로 내렸다. 12.0.0은 라벨 폭을 글자와 무관하게 늘 120px로 계산해 모든 노드 상자가 같은 크기가 되고 긴 라벨이 잘린다. 한글·영문 모두, 앱 밖의 mermaid 단독 페이지에서도 같게 나와 상류 문제로 확인했다. 11.17.2는 같은 입력을 제대로 잰다. 회귀를 막는 테스트(라벨보다 좁은 상자를 잡고, 길이가 다른 두 라벨의 상자가 같으면 실패)를 브라우저 테스트에 넣었다. fastdom·strictdom이 라이선스 파일 없이 README에 MIT 전문을 두어 notices 생성기가 멈췄으므로, 그 절을 `apps/cli/licenses/`에 보관하고 대응을 등록했다.

크기: `apps/browser/dist` 1.5MB → 4.9MB, `apps/cli/dist` 2.8MB → 6.2MB. 늘어난 쪽은 대부분 mermaid가 다이어그램 종류별로 나눠 둔 청크(elk 1.4MB, cytoscape 0.4MB, katex 0.3MB)이고, 쓰지 않는 종류는 내려받지 않지만 패키지에는 실린다. 종류를 골라 담아 줄이는 것은 하지 않았다. THIRD_PARTY_NOTICES는 mermaid의 전이 의존성까지 자동으로 담겼다(186KB).

사용자가 다이어그램 페이지에서 화면이 좌우로 흔들린다고 알려 와 원인을 찾았다. mermaid는 그림을 문서에 넣어 크기를 재는데, 기본값인 `<body>`에 재면 문서가 잠깐 뷰포트보다 150px 커져 세로 스크롤바가 생겼다 사라지고 그만큼 본문이 옆으로 밀린다. 재는 자리를 화면 밖 고정 위치의 요소 하나로 지정해 없앴다. 그 요소를 `visibility:hidden`으로 숨기면 폭이 0으로 측정되므로 숨기지 않는다. 재현 테스트를 먼저 실패시켜 확인했다(문서가 스크롤되면 실패). 이때 테스트가 `vite preview`로 빌드 산출물을 띄운다는 점을 놓쳐 한동안 수정 전후가 같게 나왔다.

검증: `pnpm check` 통과(core 29·contracts 7·intro 3·CLI 136·브라우저 41). 브라우저에 `test/markdown.spec.ts` 7건을 더했다 — mermaid 렌더링과 다른 펜스 유지, 문법 오류 대체, 원문의 click·HTML 라벨이 실행되지 않음, 알림 다섯 종류와 일반 인용 구분, 알림 안의 링크·강조 유지, 라벨보다 넓은 노드 상자, 그리는 동안 문서가 스크롤되지 않음. 실제 CLI 서버로 띄운 위키 페이지에서 라이트·다크와 라벨 잘림을 확인했다(`.tmp/markdown-rendering/`). 표기 안내 페이지 `rules/markdown-notation.md`를 위키에 더했다. 커밋·푸시는 하지 않았다.

## 준비와 실행

개발 기준은 Node.js 24.17.0과 pnpm 10.33.0이다. `.node-version`과 루트 `packageManager`에 고정했다. 공개 패키지는 @tryce/cli이며 실행 명령은 tryce다. 나머지 workspace 패키지는 private이다. 0.1.0은 Node.js 24 계열을 지원 범위로 선언한다.

pnpm이 없는 환경에서는 `npx pnpm@10.33.0`을 아래 명령의 `pnpm` 대신 사용할 수 있다. 전역 도구나 사용자 설정을 바꿀 필요는 없다.

저장소 루트에서 실행한다.

```sh
pnpm install --frozen-lockfile
pnpm browser:install
pnpm check
```

`browser:install`은 Playwright 검증용 Chromium을 사용자 캐시에 내려받는다. Linux에서 브라우저 실행에 필요한 시스템 라이브러리가 없으면 해당 환경에 맞게 준비해야 한다. 현재 실행 검증 환경은 Windows다.

```sh
pnpm build
pnpm cli browser
```

현재 checkout을 읽는 서버가 127.0.0.1의 빈 포트에서 실행된다. 터미널에 표시된 URL로 접속하고 Ctrl+C로 종료한다. 브라우저는 자동으로 열지 않는다. 화면은 browser-design-v2의 구조를 적용한 읽기 전용 브리핑·요구사항·판단 기록·Git 상태를 제공한다. 전체 추적 그래프·건강 검사·스킬 탐색은 아직 제공하지 않는다.

화면 개발 중에는 두 터미널에서 각각 실행한다.

```sh
pnpm cli browser --dev --port 4317
```

```sh
pnpm dev
```

Vite 주소는 `http://127.0.0.1:5173`이다. `/api`를 CLI 서버로 전달한다. API 포트를 바꾸려면 Vite 실행 환경의 `GITIFACT_API_PORT`도 맞춘다. Vite만 켜고 CLI 서버가 없으면 화면은 열리지만 세션 요청이 502로 실패해 불러오지 못했다는 상태가 뜬다. 통합 실행은 `--dev` 없이 사용한다. 상세 계약은 [로컬 브라우저 서버](https://github.com/dev-goraebap/tryce/blob/479d392a93fa40e7a95993d4979417beae869723/docs/specs/browser-server.md)를 따른다.

```sh
pnpm build
pnpm cli --help
pnpm cli --version
pnpm cli status --format text
```

CLI는 현재 인자 없이 실행하면 도움말을 표시한다. 도움말·버전 출력은 stdout과 종료 코드 0을 사용하고, 지원하지 않는 명령·옵션은 stderr와 종료 코드 1로 거부한다. 이후 제품 검사 결과의 종료 코드 계약은 별도로 명세한다.

status의 기본 형식은 JSON이다. 성공은 stdout·종료 코드 0, 조회 실패는 stderr·종료 코드 1을 사용한다. 기계가 출력을 읽을 때는 pnpm의 실행 안내가 섞이지 않도록 빌드한 실행 파일을 직접 호출한다.

```sh
node apps/cli/dist/main.js status
```

다른 프로젝트에서는 빌드한 `apps/cli/dist/main.js`의 절대 경로로 실행한다. 실행 위치의 checkout을 조회한다. 파일 변경이 없거나 충돌이 있어도 tryce 검사는 항상 미실행으로 표시한다. 상세 계약은 [저장소 상태 조회](https://github.com/dev-goraebap/tryce/blob/479d392a93fa40e7a95993d4979417beae869723/docs/specs/repository-status.md)를 따른다.

CLI를 수정하는 동안 `pnpm dev:cli`를 실행하면 core·contracts를 먼저 빌드하고 세 패키지의 변경을 함께 감시한다. 별도 터미널에서 `pnpm cli`로 실행한다. watcher가 CLI 명령을 자동 실행하지는 않는다.

## 명령과 검증 범위

| 명령 | 수행 내용 |
| :--- | :--- |
| `pnpm build` | core·contracts 타입 선언과 JS, CLI 번들, 브라우저 정적 파일 생성 |
| `pnpm typecheck` | 공통 패키지 선언 생성 후 네 패키지의 소스와 브라우저 설정·테스트 타입 검사 |
| `pnpm test` | 전체 빌드 후 CLI·패키징·브라우저 테스트 |
| `pnpm test:built` | 현재 제품 빌드 결과로 테스트 실행. CLI 내부 모듈은 테스트용으로 별도 컴파일 |
| `pnpm check` | 타입 검사, 빌드, 테스트를 순서대로 실행 |

Node.js 기본 test runner로 core 집계·실패 전파, 출력 계약, Git 파서와 재시도, CLI의 stdout/stderr·종료 코드·저장소 무변경을 검사한다. Git 통합 시험은 임시 저장소에서 수행한다. 별도의 패키징 검사에서는 CLI를 pack하고 새 임시 폴더에 오프라인 설치한 뒤 도움말·버전·status를 확인한다. 내부 workspace 패키지는 게시하지 않으며 CLI의 실행 의존성은 번들에 포함한다.

Playwright는 Vite preview의 실제 빌드 결과를 Chromium에서 검사한다. Astryx 테마와 버튼, 키보드 활성화, 경로 이동·새로고침·뒤로 가기, 없는 경로의 안내와 복귀를 확인한다. 검증 서버는 127.0.0.1:4173을 사용하며 기존 서버를 재사용하지 않는다. 포트가 사용 중이면 기존 프로세스를 임의로 종료하지 말고 충돌 원인을 확인한다.

core의 관측 모델과 contracts의 `repository-status` 버전 1은 개발용으로 구현했다. 부분 staging과 충돌 집계, 잘못된 계약·object ID·경로의 거부를 고정 입력으로 확인한다. 이것을 요구사항·승인·영속 형식의 검증 성공으로 확대하지 않는다.

## 도구 선택과 생성물

직접 의존성은 정확한 버전으로 선언하고 `pnpm-lock.yaml`에 전체 해석 결과를 보관한다. 현재 조합은 TypeScript 7.0.2, React 19.3.0, Vite 8.3.0, Astryx core·neutral 0.6.0이다. 전체 버전은 각 `package.json`에서 확인한다.

- CLI는 [Commander](https://github.com/tj/commander.js)로 입력을 처리하고 [esbuild](https://esbuild.github.io/getting-started/)로 ESM 실행 파일을 만든다. CommonJS 의존성이 Node 내장 모듈을 사용할 수 있도록 `createRequire`를 연결한다.
- 출력 계약은 Zod 4.6.4로 런타임 검증한다. contracts는 Node 전용 모듈을 가져오지 않으며 브라우저에서도 같은 검증기를 사용할 수 있다.
- Router의 Vite 플러그인과 별도 생성 스크립트는 같은 `tsr.config.json`을 읽는다. 생성 스크립트는 router-generator의 ESM API를 사용한다. 설치한 router-cli에서 확인된 CommonJS 순환 참조 경고를 피하고 생성기 버전을 일치시킨다.
- `routeTree.gen.ts`는 Git에서 제외한다. 타입 검사·빌드 전에 다시 생성하며 개발 중에는 Vite 플러그인이 갱신한다.
- 패키지 설치 스크립트는 esbuild만 허용한다. 확인한 Astryx core 0.6.0의 postinstall은 에이전트 문서 초기화를 권하는 안내이므로 실행하지 않는다. 실제 CSS와 테마는 배포 파일을 사용한다.
- `node_modules`, `dist`, 브라우저 테스트 결과와 압축 패키지는 Git에서 제외한다. pnpm lockfile은 제외하지 않는다.
- 2026-09-15부터 루트 `.gitattributes`로 모든 텍스트 파일을 LF로 저장·checkout한다. 운영체제나 core.autocrlf와 관계없이 명세·코드의 바이트를 같게 유지하기 위해서다. 추가 시점에 추적 텍스트 218개가 이미 LF로 커밋돼 있어 정규화 커밋은 필요 없었다. 바이너리 PNG·woff2는 binary로 명시했다. 미커밋 변경을 보존하려고 기존 작업 폴더를 다시 checkout하지 않았으므로 일부 파일은 커밋 전까지 CRLF로 남을 수 있다. init이 사용자 프로젝트에 같은 파일을 만들지는 결정하지 않았다.

빌드는 공통 패키지·브라우저·CLI 순서로 수행한다. CLI에 브라우저 자산을 포함하므로 설치한 패키지만으로 서버를 실행할 수 있다. 패키징 검증은 설치된 CLI의 HTML·JS·CSS·직접 URL과 실제 API 새로고침까지 포함한다.

## 프로토타입 기록 실행

첫 활성화는 `pnpm cli note enable --dry-run`으로 계획을 확인한 뒤 `pnpm cli note enable`로 수행한다. init-1 원본을 보존하고 format만 prototype-1로 전환한다. 모드와 기준선은 유지한다. 명세는 [프로토타입 기록](https://github.com/dev-goraebap/tryce/blob/479d392a93fa40e7a95993d4979417beae869723/docs/specs/prototype-notes.md)을 따른다.

본문을 보완하려면 새 기록에서 `--ref`로 연결하고, 정정하려면 `--supersedes`로 이전 기록을 지정한다. 기존 기록은 그대로 남는다. list는 현재 작업 폴더의 전체 기록을 읽으며 아직 커밋되지 않은 파일도 포함한다. 자동 stage·commit은 하지 않는다.

`.tryce/.notes.lock`이 남아 있으면 다른 작업이 실행 중인지 확인한다. 중단된 작업의 잠금임을 확인한 경우에만 해당 파일을 수동 정리하고 재실행한다. 실패 후 성공 여부가 불확실하면 list로 생성된 기록을 확인한다. 같은 본문으로 add를 재실행하면 별도 기록이 된다.

측정은 `node scripts/benchmark-commit.mjs [--cli 경로] [--flow both|legacy|merged]`로 재현한다. 매 실행마다 독립 fixture 저장소를 복사하며 현재 checkout은 건드리지 않는다. `scripts/benchmark-commit-trace.mjs` preload가 CLI 번들을 바꾸지 않고 Git 프로세스·파일 접근 시간을 기록한다. fixture 준비와 명세 편집은 측정 구간에서 제외했다. 시나리오별 5회를 실행했고 표는 첫 실행을 제외한 중앙값이다. 환경은 Windows 11, AMD Ryzen AI MAX 390, Node.js 24.17.0, Git 2.53.0.windows.1(system core.autocrlf=true)이며 fixture에는 훅과 서명이 없다.

0.4.0 흐름은 changes·prepare·commit-plan·commit-apply와 시작 시 working을 포함한다. Git 프로세스를 237~265회 순서대로 실행했고 시간의 86%가 Git 대기였다(호출당 평균 62ms). 저장소 크기보다 호출 수가 시간을 결정했다. 반복 원인은 명령마다의 사전 검사(status 2회 포함), 한 명령 안에서 반복한 저장소 위치·HEAD 조회, commit-apply의 계획 전체 재구성이었다. 같은 환경에서 `git --version` 한 번은 59ms, CLI 시작은 128ms였다.

단독 `changes`는 1.5~1.7초에서 0.64~0.69초(Git 10회)로 줄었다. spec commit의 남은 시간은 대부분 Git 24~25회이며, 커밋 파일이 많으면 파일 지문 계산이 약 0.8초를 더한다. 기본 Git과의 차이는 잠금 아래 재대조·격리 index·결과 검증을 유지한 비용이다. 결과는 이 컴퓨터의 로컬 측정이며 macOS·Linux, 훅·서명이 있는 저장소, 더 큰 명세 집합은 측정하지 않았다. 원자료는 `.tmp/commit-performance/baseline-0.4.0.json`과 `after-single-commit.json`에 있다.

Tryce 복제 시나리오는 autocrlf=false로 복제했다. 기본 autocrlf=true 복제에서는 명세가 CRLF로 checkout돼 commit-plan이 변경되지 않은 명세를 미선택 변경으로 거부했다. 같은 CRLF 복제본에서 새 빌드의 spec commit도 dry-run과 실행 모두 같은 오류로 거부했고 파일은 쓰지 않았다. 별도 결함으로 남기고 이번 범위에서 고치지 않았다.

새 개발 번들 SHA-256은 `9dedcb5f4635a11be8f2cd3c10ef40dc4c2f39a6f72ca8d2fb9cd5644f5f6dc9`이며 프로젝트 사용 빌드로 지정하지 않았다. 0.4.0 지정 바이트는 `.tmp/commit-performance/record-cli-0.4.0.mjs`에 보존했다. 최종 소스의 `pnpm check`가 통과했다. 타입 검사·빌드, core 20개·contracts 7개·CLI 131개(새 spec commit 8개 포함)·브라우저 17개·스킬 동기화 5개와 workspace 밖 패키지 오프라인 설치·실행을 확인했다. 새 테스트는 SHA-1/SHA-256 dry-run 무변경과 단일 커밋, 이유 누락 경고, 생략한 이유 유지, 오래된 expected·미선택 명세·기존 staging·intent-to-add 거부, 훅 거부 후 이유 파일·index 복원과 재시도, 외부 편집 보존, HEAD 변경 후 복구 자료 보존을 검사한다. 루트 커밋·푸시·npm 게시는 하지 않았다.

## 2026-09-15 구형 명령 삭제

사용자 결정에 따라 deprecated였던 `req`·`note`·`mode`·`init --mode`·`spec-preview` 호환 이름과, 표시가 없던 구형 `commit plan/apply`·`brief`를 삭제했다. 이들만 쓰던 저장소·출력 코드, core의 note·요구사항 JSON·brief 모듈, contracts의 brief·notes·workflow·browser-project·project-init v1/v2 계약도 제거했다. 브라우저 화면은 `/api/v1/project`를 호출하지 않아 해당 API와 클라이언트도 제거했다. `spec`의 `prepare`·`verify`·`commit-plan`·`commit-apply`는 0.6.0 제거 일정대로 deprecated 상태로 남긴다.

init은 schemaVersion 1 설정만 만든다. init 실패 출력은 기존 project-init version 1 오류 형태를 유지한다. 구형 설정 파서는 구형 프로젝트를 새 형식으로 오인하지 않고 MIGRATION_REQUIRED 등으로 거부하기 위해 남겼다. spec commit의 구형 기록 삭제 선택도 유지한다. 구형 JSON 프로젝트의 기록은 0.4.0 이하 CLI로 읽는다.

구형 init 테스트는 삭제하지 않고 명세 기반 init으로 옮겼다. 무시 규칙·추적 설정 삭제·진행 중인 Git 작업·링크·병렬 실행·강제 종료·worktree·clone·submodule 검사를 유지했다. 옮기는 중 차이 하나를 확인했다. 초기화 도중 다른 쪽이 config.json을 만들면 구형 init은 기존 설정으로 받아들였지만, 명세 기반 init은 기록 검사가 먼저 실행돼 EXISTING_RECORDS로 거부한다. 두 경우 모두 파일은 덮어쓰지 않는다. 동작은 바꾸지 않고 테스트를 실제 동작에 맞췄다. spec-preview 테스트는 초기화된 fixture와 `spec` 이름으로 옮겼다.

최종 소스의 `pnpm check`가 통과했다. 타입 검사·빌드, core 14개·contracts 4개·CLI 98개·브라우저 17개·스킬 동기화 5개와 workspace 밖 패키지 설치 후 init·spec save/commit/read·skills·status·browser 실행을 확인했다. 테스트 수 감소는 삭제한 명령의 테스트 제거에 따른 것이다. 개발 번들 SHA-256은 `8af110810dd896fa580ca7f91918e8363395b349415bfd15e1a84fe798533d00`이며 프로젝트 사용 빌드로 지정하지 않았다. 이 저장소의 명세는 명령 이름이 아니라 동작을 기술하므로 수정하지 않았다. 루트 커밋·푸시·npm 게시는 하지 않았다.

## 0.5.0 프로젝트 사용 빌드

위 두 절의 변경을 담아 CLI 버전을 0.5.0으로 올렸다. deprecated 명령은 0.6.0에서 제거한다.

같은 버전에 CRLF checkout 결함 수정을 포함했다. core.autocrlf=true로 복제하면 LF 명세가 CRLF로 checkout돼 spec commit이 변경되지 않은 명세를 미선택 변경으로 거부했다. 이제 변경 여부를 Git이 저장할 blob ID로 비교하고, 필터 검사는 줄바꿈 변환만 허용한다. 판단과 기각한 대안은 [MVP 전환 계획](mvp-transition.md)의 단일 커밋 명령 절에 둔다. 실제 Tryce를 autocrlf=true로 복제한 저장소에서 요구사항 수정과 README 변경을 dry-run·커밋했고 커밋 후 작업 폴더가 깨끗했다. 새 테스트는 CRLF checkout에서 건드리지 않은 명세를 다시 쓰지 않고 커밋하는 경우와, 내용을 바꾸는 clean 필터가 계속 거부·복원되는 경우를 검사한다. deprecated commit-plan에는 적용하지 않았다.

최종 소스의 `pnpm check`가 통과했다(core 14개·contracts 4개·CLI 100개·브라우저 17개·스킬 5개, workspace 밖 패키지 설치·실행). `tryce --version`은 0.5.0을 출력하고, 이 저장소에서 `spec working`(명세 6개)과 `spec changes`(변경 0건)가 정상 동작했다.

이 빌드를 프로젝트 사용 대상으로 지정한다. 실행은 `node apps/cli/dist/main.js` 또는 `pnpm cli`, SHA-256은 `41223f684db38ea8d8032d6e30a6535b1dcd75ce96d2421887638acf378e1e83`이다. 커밋은 `spec commit`으로 한다. 직전 0.4.0 지정 바이트는 `.tmp/commit-performance/record-cli-0.4.0.mjs`에 보존했다. npm 게시 전이므로 공개 레지스트리의 최신 버전은 0.4.0이다. 루트 커밋·푸시·npm 게시는 하지 않았다.
